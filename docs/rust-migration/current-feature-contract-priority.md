## 3. 현재 보호해야 할 명시적 개선의 예 (전체 목록 아님)

- 주문 처리 상태: `처리 중 / 엑셀 추출 대기 / 엑셀 추출 완료 / 공장 회신 완료`.
- 운임 용어: `선불 / 착불`, 공장/매장 배송 원천 구분 및 실제 운임 변경 보존.
- 상품명·색상·대표 상품군: 사용자 확정 명칭/묶음 원칙, `-1` 무타공은 보면대 계열로 한정.
- 상품군 UI: 그룹 이름 → 상품 추가 → 등록한 상품 → 목록 안 `대표 지정`.
- 저장 흐름: 저장 완료 뒤 다시 '변경 취소'로 이미 확정한 데이터를 날리지 않는다.
- 카카오톡·발주서 인식: 거래처명/원문 근거·수취인과 연락처 근접성, 복수 수취인 보존.
- 공장 회신: 오류 알림은 상단 `알림` 센터와 연결, 직원 검토/수정과 원본 기록 보존.
- Windows DEV UI: 정상 단가·배송건수·VAT가 관계없는 Rust 호출 중 잠시 사라지지 않는다.

각 기능의 **승인 날짜/문장/정확한 테스트 사례/실행 경로**는 35차 기능군 표와 연결해 추가해야 한다. 위 예시는 보존 원칙을 위한 출발점이며, 각 영역 전수 검증 완료 판정이 아니다.

## 5. CI 및 판정

- `scripts/audit-original-ts-coverage.mjs`: 역사적 소스 비교만. `CHANGED_SINCE_BASELINE`은 승인된 개선도 포함할 수 있음.
- 현재 TS 대비 Rust 차등 PASS = **현재 코드끼리 해당 사례에서 같음**.
- 과거 TS 대비 Rust 차등 PASS = **그 역사적 사례에서 같음**.
- 최신 승인 기능 보존 PASS = **구체적 승인 요구/입력/상태 변화/출력/Windows 시나리오 확인**.
- 전체 버전 동등성 PASS = 앞선 검증 결과만으로 자동 승격 불가.

## 7. 가격/운임 프리뷰에서 오래된 금액 표시 방지

- `useNativeOrderPreview`의 Rust 결과 표시용 키가 `shippingFee`, `shippingVersion`, `vatAmount`, `vatDefault`, `pricesLocked`, `clientSnapshot`, 계좌/그룹 정보 등을 누락하여 변경된 주문에도 이전 Rust 금액을 노출할 위험을 확인.
- `native-order-display-key.ts`로 순수 UI freshness 시그니처를 분리하고, 금액·배송분류·단가·부가세 및 수취인 관련 모든 입력을 포함시켰음. 이 로직은 금액을 계산하지 않음.
- 상태 revision/원문 참고글 변화만으로는 이미 확정된 Rust 견적을 숨기지 않지만, 재계산에 영향을 주는 실제 주문 변경은 즉시 기존 값을 무효화함.
- `tests/tauri-native-order-display-key.test.mjs`: 실제 계산이 아닌 원천 비교의 양성/음성 변경 검사. 최신 CI·Windows는 커밋별 별도 판정.
