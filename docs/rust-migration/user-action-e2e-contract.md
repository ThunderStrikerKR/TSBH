# 실제 사용자 행동 시나리오 계약 (단순 함수/코드 일치로 완료 판정 금지)

**적용:** [AGENTS.md](../../AGENTS.md) 및 [검증 누적표](verification-ledger.json). 아래 시나리오는 **검증 요구사항**이며 완료 보고가 아니다.

## E2E-01 발주서 붙여넣기 → 거래처 확인 → 저장 → 재실행

| 구간 | 조작과 입력 | 반드시 확인할 중간 상태 | 기대되는 결과/증거 |
| --- | --- | --- | --- |
| S0 | 새 주문·거래처 미선택 | 수취인·상품·배송 수량이 초안 상태 | 정식 SQLite 주문 생성 없음 |
| S1 | 복수 수취인/연락처/상품이 있는 발주서 원문 붙여넣기 | 인식 중에는 '확인 사항 없음' 또는 유효성 검증 PASS를 허위 표시하지 않음 | Rust 인식 결과, 원문 스팬·연락처 귀속·후보 및 오류 목록 저장 |
| S2 | 카카오톡 제목·원문 근거에 따라 발주처 추천 | 충돌 또는 불명확할 때 자동 확정 금지 | Rust 매칭 출처, 거래처 ID, 근거 증거 보존 |
| S3 | 사용자가 거래처 직접 확정 | 상품별 Rust 가격·수량·운임·VAT, 계좌와 상태 기록 | 입력 단가와 수량은 화면에서 임의 산술로 결정하지 않음 |
| S4 | 품목·수량 수정, 수동 단가/운임 확정, 다른 거래처 선택 | 이전 비동기 응답이 사용자 확정값 덮어쓰기 금지 | 수정 전후 품목·운임·청구 스냅샷 보존 |
| S5 | 미리보기 완료 | 84,000원, 택배 2건, 부가세 별도 등 해당 fixture의 금액·건수 안정 | Rust `preview_order_lines`, `preview_order` 상태와 UI 일치 |
| S6 | 정식 주문 저장 → SQLite 재조회 | 이전 시점에 이미 확정된 거래처/단가/옵션·수취인 정보 유지 | 실제 저장 전후 JSON/감사 이력 차등 |
| S7 | Windows Tauri 재실행 후 재조회 | 같은 주문, 가격·운임·회신/이력 상태 | WebView2 스크린샷·DB 결과·실행 SHA 기록 |

## E2E-02 비동기 응답 역전 (최소 검증 행렬)

1. `분석 A` 요청 후 `분석 B` 요청: **B가 먼저 완료**, A가 나중에 도착해도 A가 B의 최종 발주원문·상품·수취인·거래처를 덮지 않아야 한다.
2. 상품 A 단가 조회 후 상품 B 또는 거래처 B로 변경: **이전 가격 응답이 나중에 도착**해도 B의 단가/수량·확정값을 유지해야 한다.
3. 운임·VAT 변경 직후 예전 `preview_order` 응답 도착: 이전 총액을 새 총액으로 오인하여 표시하거나 저장하지 않는다.
4. 수량 편집 후 Rust 직원확인 응답 역전: 구버전 이슈는 최신 `issueId`·`canApproveOne` 승인을 오염시키지 않는다.
5. 저장을 연속 누르거나 저장 중 화면 이동: SQLite 단일 트랜잭션·중복 실행 방지·실패 재시도 시 동일 업무 상태를 유지한다.
6. 새 주문으로 전환한 뒤 이전 주문의 주소 검증·발주인식 응답 도착: 새 주문으로 결과가 유입되지 않는다.

각 사례마다 **고정 fixture+기준 TS/승인 변경 출처+Rust 실제 실행+React IPC+정상/역전 중간 상태+SQLite 최종값**을 기록한다. `unit`, `differential`, `action`, `ci`, `windows` 각각 PASS가 아니라면 기능별 `overall=OPEN`을 유지한다.

## 점검 시 변경 금지

- 역사적 `30a19cd2`과 다르다는 이유만으로 최신 합포장 `maxBundle` 정책, Rust 단가×수량 계산, UI 개선을 과거 코드로 되돌리지 않는다.
- 이 문서는 **실행 계획/정답 조건**이다. 자동 실행한 테스트로 착각해 `PASS`로 승격하지 않는다.
