# BANDO HUB egui UI 재구축 계약 (초안, 2026-11-19)

> 목적: 기존 React 화면의 실무 친화적인 정보 구조·외형·밀도를 최대한 유지하면서, egui의 공통 컴포넌트와 테마 규칙으로 8개 화면을 새로 구성한다. 과거 egui 시제품은 **기능 검증 참고자료**이지 디자인 레퍼런스가 아니다.
>
> 상태: **디자인 시스템 기초 계약**. 현재 사용자가 제공할 React 실제 화면 캡처를 대조하기 전에는 최종 시각 검수 완료로 간주하지 않는다. 이 문서를 생성했다고 egui UI가 구현된 것은 아니다.

## 0. 기준선·우선순위

1. 최신 사용자 승인 동작과 UI 지시(2026-11-19 포함).
2. 실제 운영 중인 React + Tauri 화면과 기능별 실행 경로, 사용자가 제공한 화면 캡처.
3. [현행 UI 설계 문서](ui-design-system.md)와 [기존 역할·숫자 토큰](../src/ui/design-system.json).
4. egui 기능 검증 시제품(원문 하이라이트·위치 스크롤·복수 발주서 전환·카카오톡 도킹 확인용). **시제품 디자인은 복제하지 않는다.**

기존 문서의 오래된 값과 현재 구현/사용자 합의가 충돌할 때, 문서를 맹목적으로 적용하지 않는다. 외관 변경과 업무 의미 변경을 분리한다.

## 1. 절대 원칙

- **하나의 테마, 하나의 역할 체계**: 색상·글씨·여백·모서리·크기·상태색은 Rust egui 공통 모듈에서 관리한다. 화면 파일에 임의 숫자와 RGB 색을 흩뿌리지 않는다. 디자인 토큰 소유권과 공통 컴포넌트 소유권을 명확히 한다.
- **기존 기능을 지우지 않는다**: 재구축은 외관만을 이유로 화면·입력·버튼·메시지·설정·자동저장·업무 흐름을 제거하거나 임시 동작으로 대체하지 않는다. Rust 업무 엔진을 원칙적으로 재사용한다.
- **계층과 강조 구별**: 메인 메뉴/섹션/하위 탭의 정보 위계와 저장/삭제 등 작업 중요도는 별개다. 같은 역할은 같은 높이·글씨·상태 표현을 갖는다.
- **레이아웃 안정성**: 호버·선택·알림·입력 수정으로 버튼 위치, 카드 높이, 스플리터 기준점이 의도 없이 움직이지 않는다. 포커스·테두리는 기존 기하를 밀지 않는 방식으로 표시한다.
- **중복 테두리 금지**: 큰 섹션은 외곽선, 내부 연속 정보는 구분선/여백을 활용한다. 수취인 이름·연락처·주소 각 항목을 불필요하게 별도 카드로 만들지 않는다.
- **사용자 주도**: 새로운 모달과 저장 확인창을 편의상 추가하지 않는다. 저장/이탈 정책은 Rust/SQLite의 기존 확정 동작을 따른다.
- **문서보다 실제 화면**: 정적 코드 검사는 외형/상호작용 합격의 근거가 아니다. Windows 실화면과 실제 동작을 기능별로 확인한다.

## 2. 공통 토큰: 기존 React 기준의 최초 이식값

최종 픽셀 차이는 React 스크린샷 대조에서 확정한다. 운영 중 실제 창 배율과 DPI를 구분하여 egui points로 적용한다.

| 유형 | 기준 |
| --- | --- |
| 배경 / 패널 / 입력 / 상승 표면 | `#101010` / `#202020` / `#292929` / `#303030` |
| 기본 글자 / 보조 글자 / 구분선 | `#ededed` / `#b9b9b9` / `#3f3f3f` |
| 확인 필요 / 완료 / 오류 / 원문연계 | `#f2ba64` / `#a9dab5` / `#ffb4b4` / `#70b4ff` |
| 글씨 | 브랜드 24/700(사용자 승인 확대), 메인 메뉴 16/650, 화면 제목 20/700, 주요 섹션 16/650, 하위 제목 14/650, 본문 14, 레이블 13/600, 보조 12 |
| 버튼 | primary 36px/14, standard 34px/13, emphasized 34px/13, quiet 32px/13, danger 34px/13, icon 32px |
| 입력 / 표 | 입력 높이 36px, 라벨 정렬 통일; 표 헤더 최소 36px, 행 최소 42px, 금액 우측 정렬·자리수 정렬 |

모든 수치는 **역할 토큰**으로 사용한다. 다른 화면에서 같은 역할을 다시 정의하지 않는다. 한국어 텍스트 렌더링/폰트 폴백, 글자폭 및 DPI 배율을 고려해 실제 결과를 맞춘다.

## 3. 재사용 UI 역할

- 레이아웃: `PageFrame`, `PrimarySection`, `NestedSection`, `FieldGroup`, `RecordCard`, `InformationBlock`, `SummaryStrip`, `ToolbarGroup`, `Divider`.
- 입력/작업: `ActionButton(role)`, `TextField(kind)`, `SelectField`, `CheckField`, `SearchField`, `AmountField`, `QuantityField`, `InlineHelp`.
- 정보: `StatusText`, `DataTable`, `NotificationCenter`, `ModalHost`, `EmptyState`, `LoadingContent`.
- 네비게이션: `MainNavigation`, `SectionTabs`, `SubsectionTabs`, `ResizablePane`.
- 원문/업무 전용: `SourceDocument`, `LinkedEvidenceHighlight`, `WorkflowCard`, `WorkflowPreviewOverlay`, `KakaoToolbar`.

구현은 이 역할을 충족하는 적절한 egui 위젯 조합을 허용하며 위 이름을 무조건 실제 구조체 이름으로 쓰라는 뜻은 아니다. **스타일 역할과 업무 로직 역할을 분리**한다. egui 기본 위젯 모양이 원본과 다르면 개별 화면의 즉흥적인 재도색 대신 공통 위젯에서 수정한다.

## 4. 화면 구조와 레이아웃

### 전역

- 전역 메뉴 8개: 접수 / 주문 내역 / 엑셀 관리 / 일일 결산 / 상품 관리 / 운임 관리 / 거래처 관리 / 설정. 탭·모달·검색·알림 위치는 기준 화면 캡처에서 대조한다.
- 콘텐츠에 필요한 화면 폭을 먼저 확보한다. 컨트롤을 한 줄에 유지해야 하는 헤더에서 임의 줄바꿈을 허용하지 않는다.
- 모든 화면과 하위 탭은 동일한 제목 정렬·여백·검색/필터 그룹 구조를 따른다.

### 접수 화면

- **카카오톡 / 발주원문·메시지 / 확인·수취인 / 처리 중인 주문**의 4영역 의미를 보존한다. 기존 초기 비율 `[20,29,29,22]`는 참고값이며 사용자의 조정 비율은 유지한다.
- 기존 React 접수 내부 패널의 최소 폭 개념과 분할 드래그를 재현한다. 좁은 창에서는 읽을 수 없게 압축하는 대신 명시적인 패널 최소 폭과 지역별 스크롤 정책으로 처리한다.
- 발주 원문 섹션은 **제목 → 거래처 정보 → 원문 표시창**, 상단 오른쪽 새 주문, 원문과 메시지 사이 높이 드래그, 원문 빈 상태의 접수 방법을 보존한다.
- 원문 하이라이트·영역 밖 텍스트로 자동 스크롤·복수 발주서 전환은 egui 시제품의 **이미 관찰된 정상 사례**다. 새 UI에서도 원문/분석 항목의 정확한 위치·업무 ID 연결을 유지하고, 원문 스크롤을 다른 패널과 혼동하지 않는다.
- 카카오톡 패널 상단에 **함께 보기 / 나누어 보기 / 연결 해제** 컨텍스트 작업을 두고, 외부 Windows 카카오톡 도킹 영역에 겹치지 않게 한다. 연결 전은 연결 버튼만 표시한다.
- 임시 호버 미리보기는 주문을 확정하거나 저장하지 않는다. 실제 선택과 미리보기의 색상, 강조 범위, 오버레이 위치를 구분하고 주변 카드/버튼을 밀지 않는다.

### 관리 화면

- 상품·거래처·운임·설정의 검색창은 해당 주 섹션 내부의 도구 모음에 둔다. 동일 역할의 저장/취소/추가 버튼은 같은 행과 동일한 높이를 쓴다.
- 금액·수량·운임·전화 등 필드의 내용 길이에 맞는 폭을 쓰고, 긴 상품명 열과 주소 정보는 충분한 가로 영역을 보존한다.
- 테이블은 내부 스크롤, 고정 또는 읽기 쉬운 헤더, 숫자 정렬을 기본으로 하며, 창 크기가 바뀌어도 불필요한 전역 스크롤바를 만들지 않는다.
- 설정의 운영 탭은 기본 설정 / 파일 관리 / 데이터 관리 / 시스템 4개를 기준으로 한다.

## 5. 상태·상호작용 계약

- 스타일 상태를 기본/호버/선택/포커스/비활성/오류/미리보기로 분리하고 **업무 선택과 일시적 표시 상태**를 혼합하지 않는다.
- **원문 연계 호버 최신 구현 기준: 진입 200ms, 이탈 250ms**. 구버전 문서의 100ms/150ms는 현재 코드(`HubWorkspace.tsx`)와 2026-11-18 최신 사용자 지시에 충돌하므로 egui에 복사하지 않는다. 적용 대상에 따라 별도 확정값이 있으면 해당 기능 규칙을 우선한다.
- 처리 중인 주문 원터치 미리보기: 진입 250ms / 복귀 250ms. 미리보기 중 원본 카드 재배치 금지, 실제 주문 선택을 임의 변경하지 않는다.
- 원문 연계 파랑, 실제 주문 선택 주황, 일시 미리보기 파랑을 혼동하지 않는다. 텍스트 선택과 복사·편집 기능도 보존한다.
- 주문/배송 변경에 따른 비동기 Rust 응답은 현재 식별자/버전이 일치할 때만 UI에 반영한다. 지연 응답이 사용자의 새 선택이나 수정값을 덮어쓰지 않도록 한다.
- 다섯 데이터 영역(발주원문, 확인할 내용, 메시지, 수취인, 품목/운임)은 준비 상태를 조율한다. 프레임·제목·테두리는 고정하고 **실제 데이터만** 준비 후 전환한다. 매 입력마다 전체 카드가 반짝이거나 크기가 움직이면 안 된다.
- 자동 저장되는 접수 상태에 불필요한 페이지 이탈 확인창이나 별도의 임시 주문 보관 개념을 추가하지 않는다. 실패는 명확하게 안내한다.
- 단가·수량·부가세·운임·상품 매칭·주소·도서산간 판정 등 업무 결정은 기존 Rust 업무 엔진의 출력을 사용한다. UI 쪽에서 재구현하지 않는다.
- 카카오톡 도킹·포커스·다중 모니터/DPI·창 크기 기억은 egui로 전환할 때 Windows 네이티브 어댑터의 책임을 명확히 한다.

## 6. 구현 순서 및 검수

1. React 주요 8개 화면 및 상태별 캡처를 고정한다. 각 캡처에 창 크기와 DPI, 선택 탭을 남긴다.
2. egui 공통 테마·폰트·색상·컴포넌트와 전역 레이아웃을 만든다. **스크린별 임시 스타일을 금지**한다.
3. 접수의 4패널 골격·원문·메시지·배송 카드 구조를 먼저 재구현한다. 검증된 시제품의 연결 코드를 재사용할 수 있으면 사용한다.
4. 그다음 주문 내역 / 엑셀 관리 / 일일 결산 / 상품 관리 / 운임 관리 / 거래처 관리 / 설정을 동일 컴포넌트로 채운다.
5. 화면별 실제 캡처 비교와 업무 입력→Rust→출력 연결을 확인한다. 전체 자동 회귀 테스트를 무조건 확대하지 않고 **변경된 기능과 Windows 실제 사용 동작**을 검수한다.
6. 시각적 합격과 기능 합격을 별도로 기록한다. 처음 한 화면이 비슷하다는 이유로 전체 egui 전환 완료로 선언하지 않는다.

## 8. 사용자 제공 React 안정화 화면 기준 (2026-11-19)

기준 이미지: 2026-11-19 사용자 제공 접수 화면 전체 캡처(1649×928). 이 화면은 **카카오톡 미연결·발주원문 빈 상태·기존 처리 중 주문 2개**를 보여 준다. 현재 React의 구조적 기준이며 **기존 스타일 완성 판정 기준은 아니다**. UI 공통수칙이 적용되지 않은 글씨/버튼/테두리/여백은 그대로 복제하지 않는다.

### 8-1. 유지할 화면 구조

1. 상단 단일 헤더에는 BANDO HUB 브랜드, 보조 테스트 표시, 8개 전역 메뉴, 알림 및 창 제어가 있다. 헤더 콘텐츠는 수직 중앙 기준선을 공유하고 2차 기능 버튼보다 명확히 우선해야 한다.
2. 본문은 가로 **네 열**: 왼쪽 카카오톡 / 발주원문+복사용 메시지 / 확인할 내용+수취인별 주문 정보+품목 및 운임+총 주문 / 오른쪽 처리 중인 주문. 네 열의 독립 스크롤·리사이즈 개념을 보존한다.
3. 발주원문·메시지는 같은 열에서 수직 분할, 확인·수취인·품목·총 주문은 세 번째 열에서 위아래로 구획한다. **총 주문**은 아래쪽 요약 스트립이므로 더 큰 외곽 상자가 필요한 것은 아니다.
4. 오른쪽 처리 중인 주문은 상단 헤더와 개별 주문 카드를 가진 목록이다. 실제 접힌 카드의 업무 상태등·금액·작업 버튼·묶음 관리는 한눈에 읽혀야 한다.
5. 카카오톡 미연결 빈 상태에는 연결 버튼이 화면 중앙에 있고, 원문 빈 상태에는 클립보드 접수/다른 방법/폴더 자동 인식 세 영역이 구분되어 나타난다.
6. 상단 우측 \`TEST / 격리 DB / 외부 발송 금지\` 표시는 **운영·시험 분리 의미**가 있으므로 삭제하거나 장식으로 오해하지 않는다.

### 8-2. 시각적 리팩터링 필수 항목

- **글씨**: 실제 캡처의 섹션 제목·하위 제목·본문·설명 글자가 섞여 보인다. 기존 \`typeRoles\`를 공통 font style로 구현하고 화면마다 독립 fontsize 선언을 금지한다. 긴 한국어 거래처명과 정보 밀도를 위한 폰트 폭·줄높이를 Windows 실제 렌더링으로 재검증한다.
- **버튼**: \`새 주문\`, \`카카오톡 연결\`, \`대리발송\`, \`대리점 납품\`, \`직접 입력\`, \`캡처 범위 지정\`, 처리 중 주문 단계 버튼을 역할별로 같은 높이·좌우 패딩·텍스트 정렬·호버 효과를 갖게 한다. 버튼 크기는 **텍스트 길이에 따른 너비만 달라지는 것을 기본**으로 하되, 카드 단계 버튼의 가용 폭처럼 기능상 고정 제약이 필요하면 역할 변형에 명시한다.
- **구획**: 최상위 4열 경계 / 각 열의 주요 섹션 외곽 / 카드 내부 행 구분선을 **세 수준**으로 분리한다. 연속된 1px 밝은 실선이 겹쳐 2px 또는 이중 박스로 보이지 않게 한다.
- **여백**: 헤더/섹션 제목/본문/작업행의 수직 리듬을 통일한다. 카드 외곽 padding, 정보 라인 gap, 입력 라벨과 값 사이 간격이 제각각이면 불합격. 공통 spacing scale만 사용한다.
- **빈 상태**: 내용이 없더라도 섹션을 필요 이상 축소하거나 경계를 옮기지 않는다. 빈 상태용 설명은 패널 내 의미 단위에 배치하고 무조건 전체 중앙 정렬하지 않는다. 카카오톡 연결과 원문 접수 안내는 배치 목적이 다르다.
- **상태색**: 처리 상태등은 단계별 의미를 유지한다. 선택(주황), 임시 미리보기/원문연결(파랑), 성공/오류/확인 필요와 충돌하지 않도록 각각 별도의 상태값으로 렌더한다. 호버와 선택은 다르다.
- **스케일**: 픽셀 기준 스크린샷은 화면 비교용이고 egui는 points/DPI를 고려한다. 창 크기를 줄였을 때 제목·버튼을 무작정 축소하지 않고, 합의한 최소 패널 폭과 영역별 스크롤로 읽기 가능성을 유지한다.

### 8-3. 공통 컴포넌트 재구축 순서

\`ThemeTokens\` → \`Typography\` → \`Surface/SectionFrame/Divider\` → \`ActionButton/Input\` → \`MainNav/PaneSplitter\` → \`OrderCard/StatusLights\` → \`SourceDocument/MessagePanel\` → \`Modal/Toast/Notification\`.

공통 레이어를 구축한 뒤 첫 접수 화면(빈 상태)을 **실제 React 캡처와 나란히 비교**하고, 이후 발주 입력 상태·복수 배송·수정·오류 상태로 확장한다. 이를 건너뛰고 화면별 하드코딩 스타일을 추가하지 않는다.

### 8-4. 구현 경계

- 2026-11-19 화면 스크린샷은 외관 참고이며 **별도 수정·추가된 업무 규칙을 되돌리는 근거가 아니다**.
- 현재 단계에서 캡처 분석·공통 수칙을 작성한 것이지 egui 실제 Windows 렌더링 완료가 아니다.
- 사용자 제공 추가 화면 캡처는 상태별 사례로 대조한다. 다른 상태의 UI를 첫 빈 화면의 임의 추측으로 채우지 않는다.

## 11. 기능 이전 시 레이아웃 비율 불변 계약 (2026-11-19)

**원본 측정 기준:** React 접수 1920×1080 캡처 `image(20261119-030859).png`. 네 열 내부 폭(분할선과 바깥 여백 제외)은 카카오톡 390px, 발주원문/메시지 531px, 주문 정보 529px, 처리 중 주문 418px. 기준 비율 `20.9 : 28.4 : 28.3 : 22.4`.

- 기준 화면에서 최소폭 때문에 기본 비율을 왜곡해서는 안 된다. egui 기본 최소폭은 `[200,250,250,350]pt`이고 4열 간격은 6pt. 작은 창에서는 가로 스크롤과 최소폭 유지가 우선이다.
- 세로: 원문/메시지 `50:50`, 확인할 내용은 작업 영역의 `26.4%`, 수취인 정보의 하단은 원문/메시지 가로 경계와 동일한 좌표. 품목/운임은 아래쪽 나머지 공간을 차지한다.
- 개별 섹션은 레이아웃 시스템이 할당한 `Rect` 내부에서만 정보를 표시·편집·스크롤한다. **업무 로직의 데이터 개수·수신 상태·오류 문구·hover·카카오톡 연결 여부에 따라 패널 경계가 이동해서는 안 된다.**
- 사용자 수동 드래그로 저장한 `layout.txt`의 비율은 보존한다. 오래된 기본 프리셋 `20,29,29,22`과 정확히 일치하는 저장값만 새 기준 프리셋으로 이전한다.
- 업무 기능 이전 작업은 `layout.rs`, `theme.rs`의 분할 관련 상수, `main.rs`의 pane 범위를 임의 변경하지 않는다. 이 영역을 바꿔야 한다면 변경 전후 같은 창 크기·DPI 캡처의 경계 좌표를 비교해 별도 승인받는다.
- `layout.rs`의 집중 검증 3건: (1) 기준 창 크기에서 비율 강제 보정 발생 여부 (2) 수동 저장값 보존 (3) 가운데 열 구분선의 동일 좌표. 대규모 회귀 테스트나 Windows CI를 새로 추가하지 않는다.
- 아직 실제 Windows 컴파일·변경 후 캡처 검증을 완료한 것은 아니다. 정적 코드 기준 통과와 시각적 합격은 구분한다.

## 12. 폰트 적용 및 타이포그래피 역할 기준 (2026-11-19)

- **화면 폰트:** Windows에서는 운영체제에 설치된 `C:\\Windows\\Fonts\\malgun.ttf`(맑은 고딕 일반)를 egui proportional UI의 첫 번째 글꼴로 사용한다. 포함되거나 배포되는 별도 폰트 파일은 없다. 파일이 없을 때는 개발 로그에 기록하며 실제 글씨 균형이 같다고 판정하지 않는다.
- **고정폭 문자:** monospace 계열에는 기존 고정폭 글꼴을 먼저 유지하고 한글 시스템 글꼴을 마지막 폴백으로 둔다. 숫자·코드·표의 고정폭 정렬을 임의로 해치지 않는다.
- **공통 역할:** 브랜드 24, 페이지 제목 20, 전역 메뉴 16, 섹션 16, 하위 제목 14, 본문 14, 필드 레이블 13, 메타데이터 12. 주요 버튼 14/일반 버튼 13. 승인된 egui 브랜드 확대 24는 React 원본 `src/ui/design-system.json`의 19를 변경하지 않고 egui 전용 오버라이드로 기록한다.
- **적용 책임:** `typography.rs`가 글꼴 선택·한글 폴백·역할별 글씨 크기·`TextStyle`·문자 스타일 함수(`brand_heading`, `page_heading`, `section_heading`, `subsection_heading`, `body`, `field_label`, `caption`)를 전담한다. `theme.rs`는 색상·공간·테두리·버튼·패널 스타일만 관리하며, 버튼 글씨 크기도 `typography` 상수를 참조한다. 폼과 표의 레이블은 `typography::field_label`로 통일한다. 개별 화면에 `RichText::size(숫자)`를 추가하지 않는다.
- **굵기 한계:** 기존 React 타이포그래피의 600/650은 egui 기본 `strong`만으로 숫자상 정확한 중간 굵기를 보장하지 못한다. Bold 파일도 자동 선택하고 있지는 않다. 현재는 역할별 '기본/강조'를 통일한 것이며 **실제 폰트 웨이트 일치까지 검증한 상태는 아니다.**
- **시각 검증:** Windows 실화면에서 한글-영문 혼용 줄높이, 버튼 중앙 정렬, 필드 텍스트 베이스라인, 100/125/150% 배율과 글꼴 로딩 로그를 확인해야 한다. 정적 코드만으로 타이포그래피 완성 판정 금지.

## 13. 글꼴 모듈 분리 및 의존성 계약 (2026-11-19)

- `typography.rs` 전담: Windows 시스템 글꼴 로딩, 폰트 폴백, 기본 TextStyle, 글씨 크기 토큰, 공통 텍스트 역할 함수. 별도 글꼴 파일을 저장소에 넣거나 EXE에 배포하지 않는다.
- `theme.rs` 전담: 팔레트, 여백, 구조 크기, 모서리, 프레임, 작업 버튼의 형태 및 색상. 텍스트가 필요한 곳에서는 typography 역할을 참조하고 글꼴 크기 상수를 재정의하지 않는다.
- `components.rs`와 각 화면: 폼·표·제목·본문은 typography를 직접 사용한다. 폰트 변경 시 비즈니스 실행·Gateway·레이아웃 비율을 건드리지 않는다.
- 설치 순서: 앱 생성 시 theme::install(ctx) 실행 후 typography::install(ctx) 실행. 두 호출 모두 기존 egui 스타일을 복사하여 자신의 책임 범위만 변경한다.
- 검증 범위: 소스에 반영했지만 Windows Cargo 빌드 및 폰트 메트릭은 아직 검증하지 않았다.
