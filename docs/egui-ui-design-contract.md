> 목적: 기존 React 화면의 실무 친화적인 정보 구조·외형·밀도를 최대한 유지하면서, egui의 공통 컴포넌트와 테마 규칙으로 8개 화면을 새로 구성한다. 과거 egui 시제품은 **기능 검증 참고자료**이지 디자인 레퍼런스가 아니다.
>
> 상태: **디자인 시스템 기초 계약**. 현재 사용자가 제공할 React 실제 화면 캡처를 대조하기 전에는 최종 시각 검수 완료로 간주하지 않는다. 이 문서를 생성했다고 egui UI가 구현된 것은 아니다.

4. [React 현행 UI 설계 문서](ui-design-system.md)와 [기존 역할·숫자 토큰](../src/ui/design-system.json).

기존 문서의 오래된 값과 현재 구현/사용자 합의가 충돌할 때, 문서를 맹목적으로 적용하지 않는다. 외관 변경과 업무 의미 변경을 분리한다.

## 1. 절대 원칙

- **하나의 테마, 하나의 역할 체계**: 색상·글씨·여백·모서리·크기·상태색은 Rust egui 공통 모듈에서 관리한다. 화면 파일에 임의 숫자와 RGB 색을 흩뿌리지 않는다. 디자인 토큰 소유권과 공통 컴포넌트 소유권을 명확히 한다.
- **기존 기능을 지우지 않는다**: 재구축은 외관만을 이유로 화면·입력·버튼·메시지·설정·자동저장·업무 흐름을 제거하거나 임시 동작으로 대체하지 않는다. Rust 업무 엔진을 원칙적으로 재사용한다.
- **계층과 강조 구별**: 메인 메뉴/섹션/하위 탭의 정보 위계와 저장/삭제 등 작업 중요도는 별개다. 같은 역할은 같은 높이·글씨·상태 표현을 갖는다.
- **레이아웃 안정성**: 호버·선택·알림·입력 수정으로 버튼 위치, 카드 높이, 스플리터 기준점이 의도 없이 움직이지 않는다. 포커스·테두리는 기존 기하를 밀지 않는 방식으로 표시한다.
- **중복 테두리 금지**: 큰 섹션은 외곽선, 내부 연속 정보는 구분선/여백을 활용한다. 수취인 이름·연락처·주소 각 항목을 불필요하게 별도 카드로 만들지 않는다.
- **사용자 주도**: 새로운 모달과 저장 확인창을 편의상 추가하지 않는다. 저장/이탈 정책은 Rust/SQLite의 기존 확정 동작을 따른다.
- **문서보다 실제 화면**: 정적 코드 검사는 외형/상호작용 합격의 근거가 아니다. Windows 실화면과 실제 동작을 기능별로 확인한다.

### 56차 — 공통 표 교차 행 명도 단계 및 색상 소유권 (2026-11-20, 최신 승인)

표를 읽기 쉽게 만드는 중립 교차 행에 입력창·보조 버튼과 같은 색상 단계를 사용하지 않는다.
**상품 관리 등 한 줄 목록이 체스판처럼 보이는 강한 교차 명도 차이를 금지**한다.

| 단계 | 토큰 | 배경색 | 용도 |
| --- | --- | --- | --- |
| 1 | `CANVAS` | `#101010` | 전체 작업공간/섹션 사이 |
| 2 | `PANEL` | `#181818` | 주요 섹션, 표 기본 행 |
| **2.5** | **`TABLE_ROW_ALT_BG`** | **`#1e1e1e`** | **중립 표의 짝수/홀수 교차 행만** |
| 3 | `INPUT` | `#292929` | 실제 입력창과 독립 업무 카드 |
| 4 | `RAISED` | `#303030` | 보조 버튼, 상위 정보 표면 |

- 중립 목록의 기본/교차 행 차이는 RGB 채널 **6**으로 제한한다(`#181818` → `#1e1e1e`). 기존 `#181818` ↔ `#303030`(24 차이) 교차 패턴을 사용하지 않는다.

- 실제 색상값의 실행 소유자는 `egui-app/src/theme.rs`; 문서화된 기준 소유자는 `src/ui/design-system.json`의 `palette.tableRowAlternate`이다. **값을 다시 조절할 때 이 둘을 동기화하면 연결된 모든 표가 함께 바뀐다.**
- `egui::Visuals::faint_bg_color` 전역값은 의도적으로 바꾸지 않는다. 표 안에서만 스타일을 적용해 입력창, 버튼, 다른 정보 블록에 영향을 주지 않는다.
- 선택·임시 미리보기·마우스 호버·가격 편집·업무 상태 신호등은 교차 행 명도와 **별개**이며 기존 색과 동작을 유지한다. React 레거시 CSS는 Rust/egui 토큰과 자동 연결되지 않는다. Windows 실제 렌더링 검증은 별도다.

- 모든 **Rust + egui** 화면에서 `theme::PANEL`을 사용하는 주요 섹션, 설정/관리 패널 및 공통 프레임은 공통 토큰 변경을 자동 공유한다. `CANVAS`, `INPUT`, `RAISED` 같은 다른 표면 역할은 그대로 유지한다.
- 역할별 단일 소스는 `egui-app/src/theme.rs`이고, `src/ui/design-system.json`의 기준 `palette.panel`도 함께 동기화한다. 과거 React CSS에 하드코딩된 `#202020`은 **현재 egui 실행 토큰과 직접 연결되지 않은 레거시 기준**이므로 이번 수정에서 강제 치환하지 않는다.
- 창 폭·높이, 카드 간격, 접수 분할선, 선택 동작과 저장값 등 레이아웃/업무 기능은 수정하지 않는다. Windows GUI 직접 검증은 최신 사용자 정책에 따라 기본 제외한다.

- 입력 테두리 및 내부 데이터 표시는 유지한다. React 업무 배치와 데이터, 버튼 문구·크기·상태를 색상 복원 명목으로 바꾸지 않는다.
- Windows 실제 렌더에서 카카오톡 예비 영역은 더 어둡고, 나머지 블록은 서로 맞붙는 PANEL 카드이며, 유휴 상태 분할 조절 막대는 눈에 띄지 않아야 한다. **코드 확인과 시각적 검수는 별개**다.

- **최신 승인(2026-11-20): 흰색 배경 버튼의 글씨는 모든 화면에서 Regular.** 접수·카카오톡 연결·처리 중인 주문의 원터치 버튼 등 위치나 이름에 관계없이 적용하고, 배경·크기·활성 상태는 바꾸지 않는다.

모든 수치는 **역할 토큰**으로 사용한다. 다른 화면에서 같은 역할을 다시 정의하지 않는다. 한국어 텍스트 렌더링/폰트 폴백, 글자폭 및 DPI 배율을 고려해 실제 결과를 맞춘다.

구현은 이 역할을 충족하는 적절한 egui 위젯 조합을 허용하며 위 이름을 무조건 실제 구조체 이름으로 쓰라는 뜻은 아니다. **스타일 역할과 업무 로직 역할을 분리**한다. egui 기본 위젯 모양이 원본과 다르면 개별 화면의 즉흥적인 재도색 대신 공통 위젯에서 수정한다.

## 5. 상태·상호작용 계약

- 스타일 상태를 기본/호버/선택/포커스/비활성/오류/미리보기로 분리하고 **업무 선택과 일시적 표시 상태**를 혼합하지 않는다.
- **원문 연계 호버 최신 구현 기준: 진입 200ms, 이탈 250ms**. 구버전 문서의 100ms/150ms는 현재 코드(`HubWorkspace.tsx`)와 2026-11-18 최신 사용자 지시에 충돌하므로 egui에 복사하지 않는다. 적용 대상에 따라 별도 확정값이 있으면 해당 기능 규칙을 우선한다.
- 처리 중인 주문 원터치 미리보기: 진입 250ms / 복귀 250ms. 미리보기 중 원본 카드 재배치 금지, 실제 주문 선택을 임의 변경하지 않는다.
- 원문 연계 파랑, 실제 주문 선택 주황, 일시 미리보기 파랑을 혼동하지 않는다. 텍스트 선택과 복사·편집 기능도 보존한다.
- 주문/배송 변경에 따른 비동기 Rust 응답은 현재 식별자/버전이 일치할 때만 UI에 반영한다. 지연 응답이 사용자의 새 선택이나 수정값을 덮어쓰지 않도록 한다.
- 다섯 데이터 영역(발주원문, 확인할 내용, 메시지, 수취인, 품목/운임)은 준비 상태를 조율한다. 프레임·제목·테두리는 고정하고 **실제 데이터만** 준비 후 전환한다. 매 입력마다 전체 카드가 반짝이거나 크기가 움직이면 안 된다.
- 자동 저장되는 접수 상태에 불필요한 페이지 이탈 확인창이나 별도의 임시 주문 보관 개념을 추가하지 않는다. 실패는 명확하게 안내한다.
- 단가·수량·부가세·운임·상품 매칭·주소·도서산간 판정 등 업무 결정은 기존 Rust 업무 엔진의 출력을 사용한다. UI 쪽에서 재구현하지 않는다.
- 카카오톡 도킹·포커스·다중 모니터/DPI·창 크기 기억은 egui로 전환할 때 Windows 네이티브 어댑터의 책임을 명확히 한다.
- **egui 카카오톡 소유 창·정렬 기준 (50차):** 원래 소유자가 없는 독립 카카오톡 최상위 창만 반도허브 HWND의 임시 소유 창으로 연결한다. 명시적인 연결 해제 및 정상 종료 `on_exit`에서 **소유 관계 먼저 해제 → 원래 창 스타일·위치 복원 → 반도허브 종료** 순서를 유지한다. 카카오톡 내부 소유 관계는 덮어쓰지 않는다. 이 방식 이후 옛 `WinEvent` 포커스 훅 및 32ms 포커스 감시는 사용하지 않는다. 새 창 탐색·영역 재배치에 필요한 350ms 갱신과 소유 관계를 설정할 수 없는 창에 대한 제한적 앞뒤 순서 보정만 유지한다.
- **겹쳐 보기 높이 제한 (50차):** 기본창 상단/좌우는 카카오톡 본문 배치 영역에 맞춘다. 기본창 아래쪽은 **할당 영역 하단 + 측정된 광고 푸터 높이**만큼만 연장하며, 광고 자식 HWND를 측정하지 못하면 DPI에 따른 한정된 기존 푸터 보정값을 사용한다. 모니터 맨 아래와의 거리를 추가로 더하지 않는다. 창 밖 DWM 표시 경계로부터 얻은 이상한 음영·테두리 높이를 반복 누적하지 않는다. 대화창은 푸터를 추가하지 않고 본문 영역에 정확히 맞춘다.
- **egui 모달 표준 (49차 확정):** Dim은 상단 헤더와 카카오톡 예약 패널을 포함한 **반도허브 앱 화면 전체**에 적용한다. 거래처 변경·검색·수동 분류 등 **팝업 본체의 배치와 크기만** 카카오톡 영역을 제외한 작업 영역에 제한한다. Dim 영역과 팝업 배치 영역을 같은 값으로 계산하지 않는다. 팝업의 **가로 중심은 카카오톡을 제외한 작업 영역**, **세로 중심은 상단 헤더를 포함한 전체 앱 창**을 기준으로 계산해 아래로 치우치지 않게 한다. 별도 Windows 카카오톡 실제 창의 Z-order 제약은 도킹 기능에서 다룬다.

## 56차 확정 — 전체 egui 팝업 우상단 텍스트형 취소/닫기 (2026-11-20, 최신 승인)

- **공통 제목줄**: egui 네이티브 팝업은 공통 `components::modal_window` / `decision_window`에서 기본 창 제목줄을 숨기고(`title_bar(false)`), 본문 맨 위 `components::modal_header(ui, title, close_label, enabled)`를 한 번만 그린다. 왼쪽은 제목, **오른쪽 끝은 텍스트 버튼 `취소` 또는 `닫기`**다. `X`, `닫기 ×`, 하단 중복 취소/닫기 버튼을 넣지 않는다.
- **동작별 레이블**: 편집·생성·선택 취소 및 저장/삭제/이탈 확인창은 `취소`; 단순 조회 전용 창(예: 접수 원문 감사 보관함, 상품 검색 등)은 `닫기`. 선택 결과가 전혀 없는 상태로 닫으면 이전 화면으로 돌아간다. 사용자가 실제 데이터를 수정했다면 버튼 위치가 바뀌어도 기존 미저장 확인 로직을 반드시 호출한다.
- **하단 버튼**: 오른쪽 끝에 `확인`·`저장`·`등록`·`생성`·`적용`·`교체` 등 최종 실행 버튼을 배치한다. `저장 안 함` 등 별도 명시적 선택지가 필요하면 실행 버튼의 왼쪽에 둔다. 편집 본문에서의 `삭제`는 독립 위험 작업일 경우 왼쪽 분리; 삭제 확인 모달의 최종 `삭제`는 오른쪽으로 둔다. 모든 버튼에 기존 `theme::ButtonRole`을 적용한다.
- **기능 보호**: 우상단 `취소`는 기존 취소·닫기 핸들러에 연결한다. 미저장 변경 사항, 백그라운드 저장 중 비활성화, 중첩 확인, 위험 작업 확인, 현재 선택과 입력 값 보존 규칙은 UI 위치 이동으로 변경하지 않는다. 버튼을 숨겼다 다시 표시해 위치가 움직이게 하지 않는다.
- **현행 범위**: `egui-app/src`에서 `components::modal_window` / `decision_window`로 열리는 37개 호출부(카테고리, 상품, 거래처, 운임, 브랜드, 별칭, 모델군, OCR, 수동 분류, 설정 등)를 같은 헤더로 통일한다. Windows 운영체제의 네이티브 파일/폴더 선택창은 애플리케이션의 egui 모달이 아니므로 이 지침의 대상이 아니다. 관리 페이지 본문 자체의 `닫기`·가격 셀 `취소`도 팝업 제목줄이 아니므로 변경하지 않는다.
- **검증 구분**: 소스 전체에서 각 팝업 호출과 `modal_header`의 1:1 대응·`.open(&mut ...)` 기반 기본 X 제거·하단 중복 취소 제거를 정적으로 점검한다. 실제 Windows 화면 및 컴파일·업무 검증은 별도 결과로 보고하고, 실행하지 않았다면 통과를 주장하지 않는다.
## 53차 팝업 고정 배치 및 조절 기능 제거 (2026-11-20)

- **모든 egui 앱 팝업은 이동 불가·크기 조절 불가**가 기본이다. 공통 `components::modal_window()`에서 `.movable(false)`와 `.resizable(false)`를 함께 지정한다. 개별 화면에서 `resizable(true)`로 다시 켜지 않는다. 창 제목을 끌어 이동하거나 테두리·모서리 드래그로 크기를 바꾸는 동작은 허용하지 않는다.

- **배치**: 기존 카카오톡 제외 작업영역 기준의 팝업 가로 중앙 및 전체 창 기준 세로 중앙 정렬, 각 팝업의 기본/최대 너비·높이와 `constrain_to(work_area)`를 유지한다. 작은 화면에서는 **팝업 본체가 아닌 내부 내용만 스크롤**한다. 메뉴/입력/확인/닫기 기능은 변경하지 않는다.
- **기타 떠 있는 UI**: 도움말 호버창, 처리 중 주문 호버 미리보기, 카테고리 편집 모달과 모달 뒷배경은 고정 좌표로 배치하며 움직일 수 없도록 한다. 마우스 호버·클릭·내부 스크롤은 유지한다.
- **예외**: 반도허브 **메인 창**의 운영체제 창 이동/최대화/크기 조절 및 사용자가 승인한 접수 4열 분할 막대 드래그는 팝업 조절 기능과 무관하므로 그대로 둔다. 카카오톡 외부 HWND 이동·분할 배치는 기존 전용 도킹 기능에서만 수행한다.
- **검수**: 실제 Windows에서 팝업 제목 드래그·네 모서리/가장자리 드래그 시 화면 위치와 크기가 유지되는지, 내부 내용 스크롤과 모달 버튼 클릭/취소, 작은 창에서의 클리핑 여부를 확인한다. 코드 정적 확인만으로 Windows 시각 검증을 완료 판정하지 않는다.

## 52차 운임관리 우선순위 조정 (2026-11-20)

- `배송 그룹 편성` 화면의 그룹 목록을 **운임 기준을 수정하는 주요 위치**로 삼는다. 그룹별 이름·연결된 상품 수·확정된 최대 묶음포장 수량·수량별 배송비(1~6개, 실제 등록 값만)를 우선 표시한다.
- 각 그룹의 `묶음 수량·배송비 설정`은 기존 공통 `RateEditor`를 열고 `save_group_rule` Rust 명령을 재사용한다. 확정되지 않은 수량이나 등록되지 않은 배송비는 계산하거나 추정하지 않는다. 이전 그룹 운임은 기존 `history` 보존 규칙을 따른다.
- 상품 편성표는 **그룹 미지정 상품을 우선 표시**하며, 그룹 필터나 검색 결과를 사용자가 지정한 경우에는 그 의도를 우선한다. 미저장 그룹 변경 중에는 행 위치를 재정렬하지 않는다.
- **그룹에 속한 상품의 개별 운임 수정 버튼과 개별 기준 초기화 버튼을 숨긴다.** 해당 상품의 운임은 그룹 목록에서만 수정하도록 안내한다. 그룹을 해제한 상품에는 기존 개별 운임 규칙을 다시 사용할 수 있으나 과거 기록을 삭제하거나 임의 초기화하지 않는다.
- `그룹 미지정 상품만` 필터는 실제 그룹 소속 상태만 기준으로 한다. 상품에 개별 운임 규칙이 있다는 이유로 그룹 소속 상품을 잘못 분류하지 않는다.
- 별도의 `그룹 운임표` 탭 및 기준 변경/이력 기능은 유지한다. 화면 변경만으로 Rust 업무 판단, 운임 계산, DB 스키마 또는 주문·정산 이력을 바꾸지 않는다.
- 검증 분리: 소스/서식 확인만으로 Windows egui 실화면 조작 및 Rust 영구 저장 PASS를 선언하지 않는다.

- React 원본 `src/OrderDesk.tsx`의 `.recipient-fields`/ `.recipient-phones` 구조를 따른다. 이름·주소·메시지는 각각 **한 행 전체**를 사용한다. 수취인 정보 화면에서는 기존 `요청 메시지` 표기를 **`메시지`**로 줄이며 원문 데이터 키 `note`는 그대로 유지한다. **휴대폰 레이블+입력과 전화 레이블+입력은 반드시 하나의 같은 높이(36pt) 수평 행**에서 렌더한다. 두 개의 별도 `horizontal` 행을 다시 중첩하지 않는다. 휴대폰 입력 시작점은 이름·주소·메시지 입력 시작점과 동일하며, 전화 레이블/입력도 해당 행에 수직 중앙 정렬한다. 휴대폰 최소 150pt(11자리 및 구분기호), 일반전화 최소 120pt를 확보하되 **남는 너비는 입력칸 둘이 약 55:45로 나누어 행의 우측 끝까지 채운다**. 연락처 그룹 사이 8pt, 레이블과 입력 사이 6pt를 유지한다. 사용자가 섹션을 최소 너비보다 좁힌 경우에만 연락처 행 내부에서 가로 스크롤한다.
- `phone` 값이 비어도 전화 칸을 숨기지 않는다. 기존 인식값과 `mobile` / `phone`의 구별, 원문 연결 하이라이트, 표시 전용 경계는 유지한다. 처리 중 주문의 읽기 전용 상세 표시에서도 같은 컴포넌트를 사용한다.
- 필드 사이 6pt, 연락처 열 사이 8pt, 공유 입력창 높이 36pt를 적용한다. 수취인 정보의 레이블은 **각 행의 왼쪽 좌표에 고정해서 왼쪽 정렬**하며, 공통 레이블 영역을 68pt에서 **56pt**로 축소한다. 이름·주소·메시지의 입력칸은 남은 행 너비 전체를 사용하고, 긴 값은 해당 입력창 안에서만 처리한다. 섹션 크기와 드래그 좌표는 건드리지 않고 내부 필드 영역만 스크롤한다.

### 52차 주문 카드의 회색 보조 버튼 공통 규격 (2026-11-20)

- 처리 중인 주문 카드의 `관리`·휴지통(삭제)·이전 단계 아이콘은 **같은 비활성 Standard형 보조 작업 컨트롤**을 사용한다. 카드 내부에서 서로 같은 시각적 중요도를 갖되 원터치(Emphasized) 버튼과 혼동하지 않는다.
- 같은 공통 구성요소 `components::workflow_auxiliary_button`에서 **높이 34pt**, 모서리 **6pt**, 배경 `#303030`, **1pt** `BORDER` 테두리, 글자/아이콘 `MUTED`, 아이콘 정확한 중앙 정렬을 통일한다. `관리`는 52×34pt, 두 아이콘은 34×34pt이고 간격은 공통 `SPACE_4`다. 하단 작업 행은 배송/금액 정보를 위해 36pt 예산을 유지하되 이전 단계 컨트롤 자체는 34pt로 한다.
- 전역 `action-icon`(32pt·투명)은 독립 아이콘용으로 유지한다. 주문 카드의 아이콘 두 개는 인접한 `관리`와 같은 시각적 버튼군이므로 **카드 보조 작업 그룹 변형**을 적용한다. 화면 전용 하드코딩 없이 egui `theme.rs`·`components.rs`가 역할을 소유한다.
- 현재 세 보조 컨트롤의 **비활성 상태**는 유지한다. 시각적 수정만으로 관리·삭제·이전 단계 명령을 새로 연결하거나 동작을 가장하지 않는다. 상태가 실제로 활성화되는 후속 구현에서도 같은 외곽 규격을 사용하고 위험 동작은 해당 상태에서 별도 검토한다.

### 8-2. 시각적 리팩터링 필수 항목

- **글씨**: 실제 캡처의 섹션 제목·하위 제목·본문·설명 글자가 섞여 보인다. 기존 \`typeRoles\`를 공통 font style로 구현하고 화면마다 독립 fontsize 선언을 금지한다. 긴 한국어 거래처명과 정보 밀도를 위한 폰트 폭·줄높이를 Windows 실제 렌더링으로 재검증한다.
- **버튼**: \`새 주문\`, \`카카오톡 연결\`, \`대리발송\`, \`대리점 납품\`, \`직접 입력\`, \`캡처 범위 지정\`, 처리 중 주문 단계 버튼을 역할별로 같은 높이·좌우 패딩·텍스트 정렬·호버 효과를 갖게 한다. 버튼 크기는 **텍스트 길이에 따른 너비만 달라지는 것을 기본**으로 하되, 카드 단계 버튼의 가용 폭처럼 기능상 고정 제약이 필요하면 역할 변형에 명시한다.
- **구획**: 최상위 4열 경계 / 각 열의 주요 섹션 외곽 / 카드 내부 행 구분선을 **세 수준**으로 분리한다. 연속된 1px 밝은 실선이 겹쳐 2px 또는 이중 박스로 보이지 않게 한다.
- **여백**: 헤더/섹션 제목/본문/작업행의 수직 리듬을 통일한다. 카드 외곽 padding, 정보 라인 gap, 입력 라벨과 값 사이 간격이 제각각이면 불합격. 공통 spacing scale만 사용한다.
- **빈 상태**: 내용이 없더라도 섹션을 필요 이상 축소하거나 경계를 옮기지 않는다. 빈 상태용 설명은 패널 내 의미 단위에 배치하고 무조건 전체 중앙 정렬하지 않는다. 카카오톡 연결과 원문 접수 안내는 배치 목적이 다르다.
- **상태색**: 처리 상태등은 단계별 의미를 유지한다. 선택(주황), 임시 미리보기/원문연결(파랑), 성공/오류/확인 필요와 충돌하지 않도록 각각 별도의 상태값으로 렌더한다. 호버와 선택은 다르다.
- **스케일**: 픽셀 기준 스크린샷은 화면 비교용이고 egui는 points/DPI를 고려한다. 창 크기를 줄였을 때 제목·버튼을 무작정 축소하지 않고, 합의한 최소 패널 폭과 영역별 스크롤로 읽기 가능성을 유지한다.

## 12. 폰트 적용 및 타이포그래피 역할 기준 (2026-11-19)

- **화면 폰트:** Windows에서는 운영체제에 설치된 `C:\\Windows\\Fonts\\malgun.ttf`(맑은 고딕 일반)를 egui proportional UI의 첫 번째 글꼴로 사용한다. 포함되거나 배포되는 별도 폰트 파일은 없다. 파일이 없을 때는 개발 로그에 기록하며 실제 글씨 균형이 같다고 판정하지 않는다.

- **공통 역할(역사적 기준):** 브랜드 34, 페이지 제목 20, 전역 메뉴 16, 섹션 16, 하위 제목 14, 본문 14, 필드 레이블 13, 메타데이터 12. **최신 관리 UI의 전역 메뉴는 18pt, 관리 하위 탭은 16pt이고, 해당 관리 표 헤더·본문은 14pt로 확정**한다([최신 기준](egui-management-ui-reference.md)). 주요 버튼 14/일반 버튼 13. 승인된 egui 브랜드 확대 34는 React 원본 `src/ui/design-system.json`의 19를 변경하지 않고 egui 전용 오버라이드로 기록한다.
- **적용 책임:** `typography.rs`가 글꼴 선택·한글 폴백·역할별 글씨 크기·`TextStyle`·문자 스타일 함수(`brand_heading`, `page_heading`, `section_heading`, `subsection_heading`, `body`, `field_label`, `caption`)를 전담한다. `theme.rs`는 색상·공간·테두리·버튼·패널 스타일만 관리하며, 버튼 글씨 크기도 `typography` 상수를 참조한다. 폼과 표의 레이블은 `typography::field_label`로 통일한다. 개별 화면에 `RichText::size(숫자)`를 추가하지 않는다.
- **굵기 기준:** Windows 맑은 고딕 일반(`malgun.ttf`)과 Bold(`malgunbd.ttf`)를 별도로 로딩한다. 제목·선택 메뉴·위험 버튼은 Bold를 유지하되, **모든 흰색 배경 작업 버튼(Primary·Emphasized)은 화면에 관계없이 Regular**를 사용한다. 본문·보조 문구도 Regular다. Bold 파일이 없으면 일반 서체로 폴백한다. React의 600/650 웨이트와 **정확히 같은 중간 굵기**를 제공한다고 주장하지 않는다.
- **시각 검증:** Windows 실화면에서 한글-영문 혼용 줄높이, 버튼 중앙 정렬, 필드 텍스트 베이스라인, 100/125/150% 배율과 글꼴 로딩 로그를 확인해야 한다. 정적 코드만으로 타이포그래피 완성 판정 금지.

## 13. 글꼴 모듈 분리 및 의존성 계약 (2026-11-19)

- `typography.rs` 전담: Windows 시스템 글꼴 로딩, 폰트 폴백, 기본 TextStyle, 글씨 크기 토큰, 공통 텍스트 역할 함수. 별도 글꼴 파일을 저장소에 넣거나 EXE에 배포하지 않는다.
- `theme.rs` 전담: 팔레트, 여백, 구조 크기, 모서리, 프레임, 작업 버튼의 형태 및 색상. 텍스트가 필요한 곳에서는 typography 역할을 참조하고 글꼴 크기 상수를 재정의하지 않는다.
- `components.rs`와 각 화면: 폼·표·제목·본문은 typography를 직접 사용한다. 폰트 변경 시 비즈니스 실행·Gateway·레이아웃 비율을 건드리지 않는다.
- 설치 순서: 앱 생성 시 theme::install(ctx) 실행 후 typography::install(ctx) 실행. 두 호출 모두 기존 egui 스타일을 복사하여 자신의 책임 범위만 변경한다.
- 검증 범위: 소스에 반영했지만 Windows Cargo 빌드 및 폰트 메트릭은 아직 검증하지 않았다.

## 14. 실제 타이포그래피 디자인 명세 (2026-11-19)

이번 단계는 파일 분리가 아니라 화면 내 정보의 시각적 위계를 실제로 설계·적용한 것이다. **font-size만이 아니라 글꼴 굵기, 자간, 줄높이, 색 대비**가 하나의 역할을 구성한다.

| 오류·확인 상태 | 13pt | Bold | 20pt | 0 | 의미별 기존 상태색 |

- **2026-11-20 최신 관리 탭:** 전역 메뉴 18pt/44pt, 하위 탭 16pt/38pt, 분리형 KPI 숫자 28pt·라벨 13pt/카드 80pt. 관련 상세·여백·정렬 및 예외는 [관리 UI 기준](egui-management-ui-reference.md)에 모은다.
- **액션:** 메인 내비게이션은 선택 상태일 때만 Bold. **흰색 작업 버튼은 전부 Regular**(Primary·Emphasized 모두 포함), 위험 버튼은 Bold, 일반/조용한 버튼은 Regular. 버튼 글꼴 크기는 기존 공통 수치(주요 14, 일반 13, 메뉴 16)를 유지한다. 화면별 흰색 버튼 예외 스타일을 만들지 않는다.
- **입력:** 높이 36pt는 변경하지 않으며 텍스트를 세로 중앙에 놓고 안쪽 여백은 공통 필드 처리에서 관리한다. 원문 편집은 Body 14pt를 유지한다.
- **실물 폰트:** Windows 맑은 고딕 Regular/Bold를 시스템 설치본에서 읽는다. 두 파일이 없을 때는 앱 자체의 폰트 폴백을 사용한다. 폰트 파일 자체는 저장소에 추가하지 않는다.
- **화면 기하 보존:** 외곽 4열 비율, 제목 패널 높이, 리사이즈바, 업무 로직, Gateway API, 데이터 저장 경로를 이번 타이포그래피 작업에서 바꾸지 않는다.
- **검증:** 위 디자인은 코드에 연결했다. Windows에서 컴파일 및 100/125/150% DPI 캡처의 실제 베이스라인 정렬·줄바꿈까지 합격했다고 주장하지 않는다.

## 15. 서체 계열별 타이포그래피 디자인 (2026-11-19)

글씨 크기만 역할별로 나누는 것이 아니라 **서체의 형태가 다른 3개 계열**을 의도적으로 운용한다. 각 섹션마다 별도 글꼴을 쓰는 방식은 피한다.

| 사용 영역 | 우선 시스템 서체 | 대체 순서 | 적용 규칙 |
| --- | --- | --- | --- |
| BANDO HUB 영문 브랜드 | Bahnschrift | Segoe UI Semibold → 한국어 UI Bold | 브랜드에만 사용. 34pt/42pt 줄높이, -0.60pt 자간, 읽기 전용 표시 |
| 한국어 업무 UI | 맑은 고딕 Regular/Bold | egui 기본 폰트 | 메뉴·섹션·본문·입력·상태·버튼 전체에서 Regular/Bold 역할별 위계 |
| 수량·금액 등 숫자 데이터 | Consolas | egui 기본 고정폭 폰트 → 한글 폴백 | 수량과 합계 표시 등 정렬이 필요한 숫자 역할에만 사용. 일반 상품명·주소까지 고정폭으로 바꾸지 않는다 |

- 글꼴 바이너리를 저장소에 추가하거나 배포하지 않고 설치된 운영체제 글꼴을 읽는다. 설치되지 않은 시스템에서는 폴백을 사용하며 개발 로그에 실제 선택된 서체를 기록한다.
- 세 서체는 `typography.rs`가 등록하고 `brand_heading`, 본문·제목 역할, `quantity`/`summary_value`에서 선택한다. 화면이 서체의 내부 이름이나 파일 경로를 직접 알 필요가 없다.
- 원래 확정한 4열 폭과 세로 경계, 헤더 높이 62pt, 브랜드 34pt, 패널·버튼 크기, 업무 동작 및 문구는 유지한다.
- 시스템 서체별 영문 자폭·폰트 메트릭이 달라질 수 있다. Windows 100/125/150%에서 브랜드·메뉴 줄바꿈과 금액/수량 정렬은 아직 실화면 검수 전이다.

## 16. 세 서체의 실제 입력·표시 적용 범위 (2026-11-19)

- 브랜드 영문 `BANDO HUB`: `brand_heading()`에서 전용 Bahnschrift 계열을 선택하며, 없을 경우 Segoe UI Semibold → 한국어 강조 서체로 대체한다.
- 한글 화면 본문·메뉴·섹션·주소·전화·일반 입력: 맑은 고딕 Regular/Bold를 사용한다.
- 숫자 데이터: 수량 표시 `quantity()`, 합계 표시 `summary_value()`, `FieldKind::Money`와 `FieldKind::Quantity` 입력은 Consolas를 최우선으로 한다. 숫자 입력도 별도 `numeric_editor_font()`에서 중앙 관리한다.
- 원문 편집기는 자유 형식 한국어 업무 텍스트이므로 기존 `Body` 계열을 유지한다. 전화·주소를 숫자로 오인해 monospace로 바꾸지 않는다.
- **한계:** 실제 숫자·금액 표가 아직 구현되지 않은 화면에서 새로운 표를 추가하지 않는다. 추후 구현할 명세에는 텍스트·숫자 타입을 명시하여 같은 계열을 재사용한다.
- **검증:** 정적 코드상 각 폰트 역할과 입력 호출 경로를 확인했다. Windows 실제 빌드·3종 설치 글꼴의 실렌더링은 별도다.

## 17. 기능 이전·UI 변경의 여섯 가지 불변 원칙 (2026-11-19)

이 규칙은 화면/서비스의 신규 기능 이전, 버그 수정, 디자인 개선, 컴포넌트 리팩터링 모두에 적용한다. 기존 승인사항보다 임의 설계를 우선할 수 없다.

1. **Layout** — 승인된 섹션별 너비·높이 비율, 분할선, 드래그 후 저장값을 유지한다. 내용물이 늘어도 상위 패널의 경계와 비율을 움직이지 않는다.
2. **Typography** — BANDO HUB 브랜드/한국어 업무 UI/숫자 세 서체 계열과 역할별 크기·대비·굵기·줄높이를 유지한다.
3. **Theme / Components** — 같은 역할의 버튼·입력·정보 표시는 동일 공통 컴포넌트/디자인을 통해 렌더링한다. 증상 패치로 개별 화면에 중복 스타일을 만들지 않는다.
4. **Gateway / Service** — 기존 Rust 업무 판단을 호출·재사용한다. UI에 가격·수량·운임·주소 분류 등 업무 결정을 재구현하거나 중복시키지 않는다.
5. **화면/업무 흐름** — 승인되지 않은 버튼·문구·임시 저장 단계·팝업·업무 전환을 추가하지 않는다. 기존 명령과 실데이터 경로를 임의 대체하지 않는다.
6. **상충/불확실성** — 위 원칙 또는 기존 확정 동작이 양립할 수 없는 경우, **임의의 우선순위·절충안·예외를 결정하거나 구현하지 않는다.** 충돌되는 원칙, 실제 코드 근거, 선택지와 예상 영향을 사용자에게 명확하게 제시하고 **질문 후 결정받는다.** 단순 버그 수정에서 상충이 없으면 승인된 원칙 범위 내에서 바로 처리한다.

이번 발주원문 편집기 침범 수정의 범위: 제1원칙에 따라 **기존 4열/세로 비율 및 제목·분할선 위치는 그대로 두고**, 제3원칙에 따라 일반적인 섹션 크기 예산을 공통 계산으로 적용한다. 원문 편집기의 너비·높이 제한 및 내부 스크롤 외에 접수 방식 전환·업무 상태·버튼을 변경하지 않는다.

## 18. 접수 버튼 그룹 정렬 및 클립보드 활성화의 기능 계약 (2026-11-19)

- 접수 화면의 세 쌍 버튼은 `components::paired_actions()`를 사용하여 같은 폭·높이·정렬·간격을 공유한다. `theme::action_full_width()`는 기존 역할별 디자인을 재사용한다.
- 내부 가용 폭이 280pt 이상이면 같은 폭의 2열, 그보다 좁으면 같은 폭의 세로 2행으로 배치한다. 이는 **섹션 내부 배치만 변경**하며 기존 4열/세로 분할 비율과 사용자 저장값을 바꾸지 않는다.
- 좁은 영역에서 내용이 늘어나는 경우 `발주 원문` 빈 상태의 접수 안내만 자기 섹션 내부에서 스크롤한다. 자동 메시지의 복사 버튼 높이 예산도 세로 2행에 맞춘다.
- 버튼의 명칭·중요도·기존 활성화/비활성화 상태 및 클릭 결과는 이번 디자인 변경에서 바꾸지 않는다.
- **클립보드 활성화 추가 요구:** 클립보드에 텍스트나 이미지가 없으면 `대리발송`·`대리점 납품` 버튼을 비활성화하고, 실제 접수 가능한 데이터가 들어올 때 활성화한다. 단, 현재 egui의 두 버튼은 접수 클릭 이벤트/텍스트·이미지 수신 경로가 모두 미구현이라 현재 무조건 비활성화되어 있다. 클릭해도 아무 반응 없는 활성 버튼을 만들면 `화면` 원칙과 충돌한다. 클립보드 감지와 실제 접수 기능 연결의 구현 시점을 사용자에게 질문하여 결정하기 전까지 단독 활성화 패치는 하지 않는다.
- Windows 실화면/실기기 렌더링과 클립보드 텍스트·이미지 판정은 현재 실행 환경에서 검증되지 않았다.

## 19. 상단 브랜드·창 제어 정렬과 클립보드 접수 이전 (2026-11-19)

- **브랜드:** 원본 반도 로고(38pt 캔버스)와 `BANDO HUB`(34pt/42pt 줄높이)는 하나의 높이 62pt 슬롯에서 동일한 세로 중심을 기준으로 직접 그린다. 글꼴의 잉크 영역이 위로 치우치는 정도는 `typography::BRAND_OPTICAL_CENTER_Y`에서만 보정한다. 로고 PNG 투명 여백과 영문 B의 왼쪽 사이드베어링 때문에 **캔버스 간격은 `BRAND_WORDMARK_GAP = -4pt`**로 지정해 실제 그림 사이의 간격을 좁힌다. 이는 그림의 충돌이 아닌 시각적 밀착을 위한 광학적 오버랩이다. 로고와 글씨에는 클릭·더블클릭·드래그·호버 인터랙션을 만들지 않는다.
- **창 제어:** 최소화·최대화·닫기 세 버튼은 같은 32pt 클릭 영역과 중앙 벡터 아이콘을 사용한다. 글꼴 유니코드 문자 모양에 따라 기준선이 달라지지 않도록 한다. 기존 우측 `알림`과 창 제어 기능 순서는 유지한다.
- **클립보드 버튼:** 텍스트가 실제로 비어 있지 않거나 RGBA 이미지를 읽을 수 있을 때 `대리발송`/`대리점 납품`을 활성화한다. 둘 다 동일한 클릭 흐름을 사용하고 AGENCY/DEALER는 접수 유형으로 지정한다.
- **텍스트:** 승인된 Rust 인식 엔진으로 분석하고 격리 egui SQLite에 원문·접수 유형을 원자적으로 자동저장한다. 다른 원문이 이미 존재하면 교체 전 확인한다.
- **이미지:** 기존 PaddleOCR 스크립트와 모델을 호출하고 `OCR 문자 인식 검토`에서 이미지·문자를 보여준다. 검토 이전에 원문/DB를 변경하지 않는다. `원문에 추가`/`원문 교체`/`닫기`의 기존 업무 흐름을 유지한다.
- **기본 레이아웃:** 4열 비율, 원문/자동메시지 세로 비율, 기존 분할선 좌표·클리핑, 공통 3개 서체와 버튼 토큰을 변경하지 않는다.
- **상충 규칙:** 기존 React/Tauri 전체 접수 구조는 여러 발주서를 개별 작업으로 보존하지만, 현재 egui는 원문 1건만 저장하는 격리 프리뷰다. 이 작업에서 임의로 새로운 `처리 중인 주문` 모델을 구성하거나 단일 원문을 여러 주문으로 가장하지 않는다. 복수 주문과 전체 운영 DB 이전은 별도 작업으로 남긴다.
- **검증 상태:** GitHub 정적 소스 대조만 수행했다. Windows Rust 컴파일·3종 클립보드 상태 전환·PaddleOCR runtime 경로·실화면 픽셀 정렬 확인은 아직 수행하지 못했다.


### 54차 공통 자동 성공·오류 문구 제거 및 거래처 목록 정렬 (2026-11-20, 최신 승인)

- **전역 egui 화면 공통 규칙:** 사용자가 별도로 요청하지 않은 `저장했습니다`, `삭제했습니다`, `처리에 실패했습니다`, `조회가 중단되었습니다` 등의 자동 성공/오류 문구를 페이지·모달·알림창에 표시하지 않는다. 상단의 사용하지 않는 `알림` 버튼과 자동 오류 팝업도 제거한다. 화면 전환·메시지 표시를 위한 새 팝업을 임의로 추가하지 않는다.
- **거래처 관리:** 목록 위의 `현재 연결된 거래처 명단은 읽기 전용입니다.` 안내를 완전히 제거한다. 검색·거래처 표·관리 버튼은 기존 순서와 크기를 유지하며, 중복 상태 표시로 표 헤더를 아래로 밀지 않는다. 표와 검색창의 외곽 패널은 기존 6pt 작업공간 여백 및 단일 카드 규칙을 따른다. 검색 입력과 오른쪽 버튼 사이 불필요한 예약 폭을 줄인다.
- **기능과 판정은 유지:** 성공/실패/저장 대기/리비전 충돌·미저장 변경 상태는 내부 Rust Result·상태값으로 유지하며, **실패한 저장을 성공으로 처리하거나 편집창을 자동으로 닫지 않는다.** 거래처 운영 DB의 읽기 전용 보안 제약을 풀지 않으며, 미저장 이탈·삭제 확인 등 원래 필요한 선택 창을 삭제하지 않는다.
- **구분:** 미분류 건수, 상품 확인 필요 건수, 가격 규칙 영향, 별칭 충돌, 삭제 전 실제 참조 상품과 같이 사용자가 처리해야 하는 **업무 데이터·검증 조건**은 일반 성공/실패 알림과 다르므로 해당 기능의 맥락 안에서 유지한다. 단순 조회·저장 결과에 대한 별도 성공/오류 문장과 팝업은 생성하지 않는다.
- **범위:** 현재 실행 중인 Rust/egui 화면의 거래처·상품·운임·설정·카테고리·브랜드·별칭·모델군·수동 분류·거래처 선택 및 접수 패널에 적용한다. 기존 React 레거시는 이번 UI 수정 대상이 아니다.

- **상황별 공통 안내**: React에 존재하는 **20개 정의를 정확히 동일한 ID·라벨·기본 문구·범주·샘플·허용 변수·필수 변수**로 보여준다. 선택, 기본 문구 복원, 수정/기본 상태 표시, 미리보기, 명시적 저장을 제공한다. 기본값과 동일한 문장을 입력해도 실제 변경이 없다면 저장을 요구하지 않는다. 저장 유효성은 기존 Rust `validate_automatic_templates` 단일 판단으로만 결정한다.
- **잠정 상품 선택 안내**: `registeredProducts`와 동일하게 활성·비삭제·비대체 상품만 선택한다. 검색어가 비어 있으면 안내문 등록 상품만 표시하고, 검색 중에는 상품명/부제 검색 결과에서 **등록 항목 우선·최대 80개**를 보여준다. 선택한 상품별 문구 등록·삭제·입력 및 **상품/운임/합계·입금계좌 → 안내 문구 → 상품 링크** 배치 미리보기를 제공한다. `validate_provisional_product_notices`의 제품 ID·2000자 규칙과 기존 Rust `selectionEvidence` 소비 조건은 바꾸지 않는다.
- **저장과 데이터 보호**: `BandoGateway::load_settings / patch_settings` 및 운영 v2 `patch_settings_v2`의 기존 필드별 CAS를 이용한다. Tauri에서 원래 하던 것처럼 운영 DB 변경 전 기존 백업 서비스가 먼저 성공해야 하며, egui 격리 미리보기 DB는 운영 백업·고객 자료와 섞지 않는다. 권한 부족/백업 불가 시 저장을 가장하거나 우회하지 않는다. 원본/수정본/비동기 저장 결과를 분리하고 실패 시 입력값을 유지한다.
- **미저장 이동**: 메시지 유형 선택, 상품 선택, 두 하위탭 전환, 거래처 목록 전환, 전역 내비게이션 이탈에 동일한 기존 **저장 안 함 / 저장하고 이동 / 취소** 확인 흐름을 적용한다. 공통 팝업 계약대로 `취소`는 **우상단 텍스트 버튼 하나**, 하단은 별도의 선택지/실행 버튼만 둔다. 저장 중에는 중복 저장·이동을 방지한다.
- **검증 구분**: Rust/React 템플릿 20개 ID·라벨·본문 대조, Gateway 호출 경로, 상태·CAS·백업 흐름 등 수행한 정적 점검만 정적 PASS로 기록한다. 컴파일·실행하지 않았다면 미검증으로 남기고 Windows 실화면은 사용자 정책대로 수행하지 않는다.
### 49차 거래처 관리 이전 기준

- 기존 React `src/ClientManager.tsx`는 **업무 정보·데이터 필드·상호작용 기준**이며 화면이 완성된 디자인이라고 간주하지 않는다. 기존 스타일의 불일치·임의 배치까지 복제하지 않는다.
- 공통 `PageHeading`·탭·검색툴바·목록 표·버튼·모달 역할을 egui `theme.rs`/`components.rs`에서 재사용한다. 목록은 거래처 30% / 발송인 38% / 거래 조건 32% 비율을 유지하되 긴 주소를 강제로 좁히지 말고 해당 표 안에서 가로 스크롤한다.
- 검색은 주 섹션의 왼쪽, `Excel 관리` 및 `＋ 거래처 등록` 작업 버튼은 같은 툴바의 오른쪽에 정렬한다. 필드는 식별/발송인/거래 조건/특수 단가 순으로 묶고 편집창은 내부 스크롤과 하단 작업 버튼 접근성을 보장한다.
- 거래처 검증·신규/수정·소프트 삭제·검색 판단을 egui에 재구현하지 않는다. Tauri와 egui에서 같은 Rust 소유 모듈을 호출하고 저장 revision을 확인한다.
- 개발용 격리 DB와 운영 DB 거래처를 자동 병합하지 않는다. 운영 DB를 명시적으로 연결한 경우 읽기 전용 경계를 지키며, 연결되지 않은 모듈/탭을 가짜로 작동시키지 않는다.
- 문서·Cargo 컴파일 성공은 Windows 실제 UI 디자인/작업 흐름 최종 합격의 근거가 아니다.

### 56차 최종 — 카테고리 집계의 이름 옆 표시 규칙 (2026-11-20)

- 트리에서 각 카테고리명 바로 오른쪽에 8pt 간격을 두고 **하나의 괄호**로 집계를 표시한다: `반도스탠드 (상품 358 · 하위 분류 7)`, `고정형 보면대 (상품 15)`.
- **`상품`은 현재 카테고리와 모든 하위 카테고리의 상품 수**, **`하위 분류`는 직접 연결된 하위 카테고리 수**이다. 데이터가 0이면 `(상품 0)`을 숨기지 않고 표기한다. 하위 분류가 0이면 그 부분은 생략한다.
- 분류명은 기존 글꼴과 강조 위계를 유지한다. 괄호 안 집계는 **12pt 보조 글자색**, 이름과 같은 행의 수직 중앙에 표시하며 두 개의 별도 괄호로 분리하지 않는다.
- 긴 분류명은 이미 적용된 `fit_category_path` 규칙에 따라 앞부분을 먼저 줄인다. **집계 문자열에 필요한 폭을 먼저 확보한 뒤 나머지 폭에 이름을 맞춘다.** 원문 카테고리명은 호버로 확인 가능하며, 집계는 우측 끝에 보내지 않는다.
- 이는 `category_manager.rs`의 카테고리 트리 집계 표시 정책이다. 다른 메뉴의 상품/운임 표가 의도적으로 우측 정렬하는 수량 열과 혼동하지 않는다.

### 56차 후속 — 윈도우 탐색기형 카테고리 트리 연결선·구분선 (2026-11-20, 최신 승인)

- **Windows TreeView 계층 탐색 방식:** 트리는 들여쓰기(깊이당 24pt), 오른쪽/아래 펼침 표식, 작은 중립 폴더 아이콘, 부모–자식 연결선, 선택된 행의 전폭 배경 강조를 함께 사용한다. 루트·하위·말단 분류 모두 동일한 왼쪽 좌표 체계를 지킨다.
- **연결선:** 부모의 펼침 표식 위치에서 아래로 이어지고 자식 행 중간에서 오른쪽으로 꺾인다(`│`, `├`, `└`). 뒤에 형제 분류가 남은 조상만 그 아래 자손 행까지 세로 연결선을 유지한다. 마지막 자식에서 세로선은 끝난다. 검색 시에는 실제 표시되는 형제 순서를 기준으로 계산한다.
- **행 구분선:** 잔잔한 1pt 하단 선으로 각 분류명과 바로 옆 집계 수량이 한 행임을 알린다. 일반 행 `treeRowRule #282828`, 상위 루트 경계는 공통 `dividerSoft #3f3f3f`, 계층 연결선은 `treeGuide #4a4a4a`이다. 해당 값은 `theme.rs`와 `src/ui/design-system.json` 및 토큰 투영을 동기화한다. 체스판형 교차 배경을 카테고리 트리에 넣지 않는다.
- **영역 구분 (최신 수정):** [표식]–[폴더]–[분류명]–[(상품 N · 하위 분류 N)]을 왼쪽부터 연속 배치한다. 수량을 화면 오른쪽 끝에 두지 않는다. 이름은 왼쪽 시작점에 그리고, 긴 이름은 앞부분부터 생략한다. 연결선·행 경계는 선택·호버 배경을 덮지 않도록 색을 약하게 사용한다.
- **동작 보존:** 행 클릭 선택 및 접기/펼치기, 검색 자동 펼침, 전체 원문 이름 호버, 분류·상품 ID·Rust 저장은 변경하지 않는다. 스크롤 중에도 선이 이어지도록 트리 행 사이 자동 세로 간격은 0으로 설정하고, 명시된 섹션 간 공백만 유지한다.

### 56차 후속 — 카테고리 트리 행 정렬 복구 (2026-11-20)

- 분류 행은 **[계층 들여쓰기 + 펼침 표식 + 폴더 + 분류명 + 집계]를 왼쪽 연속 배치**한다. 이름과 집계는 8pt 간격으로 인접시키며, 부모·자식 이름이나 수량을 화면 중앙 또는 오른쪽 끝에 따로 놓지 않는다.
- 분류명이 길어도 텍스트를 배치하기 위해 행 전체를 차지하는 큰 `egui::Label`을 사용하지 않는다. 계산된 이름 영역의 **왼쪽 절대 좌표**에서 동일 폰트로 텍스트를 직접 그리며, 이름 영역 밖은 클리핑한다.
- 최하위 이름을 보존하는 앞부분 생략과 전체 이름 호버 표시는 유지한다. 행 클릭 및 펼침·접힘·선택·루트 서체·우측 집계는 변경하지 않는다.
- 화면 폭이 바뀌어도 펼침 표식과 분류명이 서로 분리되거나, 우측 집계가 이름 열의 가운데로 밀리지 않아야 한다.

### 56차 최종 — 선택 분류 편집창 정보 밀도 및 수직 정렬 (2026-11-20)

- 이 팝업은 **편집 폼**이지 요약 대시보드가 아니므로 큰 수치 카드 3개를 사용하지 않는다. 경로 바로 아래에 한 줄 메타데이터 `직접 연결 상품 N개 · 하위 분류 N개`만 보인다.
- **필요한 구분선만 유지**: 보조 정보와 첫 입력 필드 사이 1개, 폼과 하단 버튼 사이 1개. 구 카드 영역의 구분선·패딩·공통 컴포넌트 `management_summary_card` 및 전용 폭 토큰 `CATEGORY_MODAL_STATS_MIN_WIDTH`는 제거한다.
- `상위 카테고리` 라벨은 별도 윗줄이며, 그 아래 `[현재 상위 분류 경로] [위치 변경]`은 같은 줄에서 **세로 가운데 정렬**한다. 실제 텍스트와 버튼 사이 8pt 간격, 버튼은 공통 34pt 높이. 다른 화면과 동일하게 긴 경로는 왼쪽부터 생략해 마지막 분류를 보존한다.
- 현재 분류 직접 연결 수와 직속 하위 분류 수만 표시하며 Rust 작업, 분류 경로, 저장·삭제·이동·미저장 확인은 바꾸지 않는다.
### 56차 후속 — 배송 그룹 편성 레퍼런스 기반 카테고리 팝업 재편성 (2026-11-20, 최신 승인)

- **강한 시각 기준:** `docs/egui-management-ui-reference.md`의 운임 관리 → 배송 그룹 편성 확정 화면. 다만 업무 내용이 없는 4개 KPI나 목록 표를 강제하지 않고, 정보 위계·분리 카드·기본 간격(4/8/12/16pt)·컨트롤 높이·중립 단계색·버튼 역할을 팝업에 맞게 재사용한다.
- **선택 분류 편집 (최신 승인):** 중앙 560pt 모달에서 [분류명 + 오른쪽 닫기] → [전체 카테고리 경로] → [작은 보조 정보 한 줄: `직접 연결 상품 N개 · 하위 분류 N개`] → [구분선] → [분류 이름 입력 + 상위 카테고리/위치 변경] → [구분선 + 하단 작업 버튼] 순서로 구성한다. 숫자 KPI 카드 3개는 제거한다. 편집 목적과 중복되는 `하위 포함 상품` 수치도 표시하지 않는다. 상위 카테고리의 **라벨은 위**, 실제 경로명과 `위치 변경`은 **아래 같은 가로줄의 수직 중앙**으로 맞추며, 두 요소 사이 가로 간격은 8pt다. 폰트 폭이 길면 경로 앞부분을 줄이고 전체 이름은 호버로 제공한다. 삭제는 왼쪽 위험 작업, 저장은 오른쪽 Primary 버튼이다. 카드 제거 후 비어 있는 전용 컴포넌트·토큰·중복 구분선·여백을 남기지 않는다.
- **하위 카테고리 추가:** [생성 위치(보조 라벨 + 전체 너비의 한 줄 경로)] → [얇은 구분선] → [한 줄 전체 너비 `새 하위 분류 이름` 입력] → [기존 직접 연결 상품에 관한 필수 체크박스(해당될 때만 단일 중립 카드)] → [구분선 + 오른쪽 취소·분류 생성] 순서로 구성한다. 불필요한 별도 입력 라벨은 복구하지 않는다.
- **동작 불변:** 첫 하위 분류 생성 시 직접 연결 상품의 이동 동의를 강제하는 기존 체크/버튼 활성 규칙은 그대로 유지한다. 이미 하위 분류가 있는 경우의 기존 체크 확인 동작도 이번 **시각 개편에서는 변경하지 않는다**. 분류 변경·이동·삭제·미저장 확인·중첩 모달 및 Rust 저장을 수정하지 않는다.
- 색상·서체·간격·팝업 위치·버튼 크기는 `theme.rs`/`typography.rs`/`components.rs` 공통 소유권을 따른다. 배송 그룹 화면의 6열 상품 목록이나 228pt KPI 카드 폭을 팝업에 그대로 복제하지 않는다.

### 56차 후속 — 하위 분류 생성 위치의 2행 배치 (2026-11-20)

- `하위 카테고리 추가` 확인창의 `생성 위치` 라벨은 첫 행에 작은 보조 글씨로 표시하고, 전체 경로는 둘째 행에서 팝업의 가용 너비를 사용해 **한 줄만** 표시한다. 가용 폭을 넘으면 기존 `fit_category_path`로 경로의 앞부분을 생략하고, 원문은 호버로 제공한다.

- **선택 분류 편집 중앙 모달 (56차 최신 승인)**: 기존 React의 오른쪽 고정 사이드 패널은 egui에서 제거했다. `components::modal_window`를 사용하여 카카오톡 할당 영역을 제외한 `work_area`의 중앙에 고정 배치한다. 기존 분류명·경로·집계·이름 수정·상위 분류 위치 변경·삭제·저장·닫기 및 미저장 변경 확인은 그대로 유지한다. 배경은 공통 `modal_backdrop`을 사용하며, 분류 이동/삭제 등 후속 확인창이 열리면 원본 편집창은 비활성화하고 확인창을 그 위에 표시한다.

### 56차 후속 — 무제한 깊이 카테고리의 앞부분 생략 (2026-11-20, 최신 승인)

- 카테고리 경로는 생성 가능한 하위 분류 깊이를 제한하지 않는다. **렌더링 폭이 부족하면 최상위 이름부터 생략하고 최하위 분류와 가까운 조상을 우선 노출**한다. 예: `반도스탠드 > 보면대 > 이동형보면대` → `… > 보면대 > 이동형보면대`. 뒤쪽을 `반도스탠드 > 보면대 > 이동…`처럼 자르는 것은 금지한다.
- 고정 폭 표 셀, 상품 관리 카테고리 선택·수정 및 옵션 메뉴, 운임 관리 카테고리 열, 카테고리 관리 트리·수정·이동창, 주문 상품 검색/별칭 연결 분류 드롭다운에 같은 규칙을 적용한다. **레이아웃의 실제 글꼴과 가용 폭을 측정**한 후 가능한 많은 후행 분류를 남긴다. 마지막 이름 하나도 길면 앞 글자부터 생략하고 끝 글자를 보존한다.
- egui 공통 `typography::fit_category_path(ui, path, max_width, CategoryPathFont)`가 표시만 처리한다. 축약 문자열을 상품/카테고리 DB에 저장하거나 Rust 검색/분류 판단에 전달하지 않는다. 전체 경로는 호버 툴팁으로 제공한다.
- 실제 분류 트리 전체 경로는 `ProductCategoryPaths`를 사용하고, 목록 검색은 **축약하지 않은 전체 경로**를 사용한다. 선택 값은 표시 문자열이 아니라 기존 카테고리 ID다.
- 텍스트를 오른쪽부터 잘라내는 기본 `.truncate()`에 전체 카테고리 경로를 직접 맡기지 않는다. 값이 길어지면 화면별 임의 문자 수 제한이나 별도 글씨 크기를 추가하지 않는다.

### 56차 후속 — 상품 카테고리의 전체 경로 표시 규칙 (2026-11-20)

- **반도스탠드와 반도몰은 실질적인 최상위 카테고리**이며, 트리 화면뿐 아니라 운임 관리 등 상품 카테고리를 표시하는 모든 관리 화면에서 경로의 첫 단계에 포함한다.
- 상품의 현재 카테고리 경로는 **`product.categories`의 마지막 유효 ID → 최신 `state.categories[*].parentId`**로 구성하며, `catalog-root:BANDOSTAND` / `catalog-root:BANDOMALL` 가상 루트도 같은 트리에 포함한다. 예: `반도스탠드 > 보면대 > 보면대 악세사리`.
- 단순 문자열인 `product.category`는 과거 저장 시점의 경로일 수 있다. 유효한 카테고리 ID가 있으면 이를 직접 렌더하지 않는다. 운임 관리 검색과 표시는 **같은 전체 경로**를 사용한다.
- 실제 분류 ID 또는 상위 연결이 없는 레거시 상품은 임의로 반도스탠드/반도몰에 소속시키지 않는다. 기존 표기를 임시 유지하고 분류 연결 상태를 별도 확인한다. **색상·상품 소속·운임·가격·저장 데이터는 표시 보정 과정에서 수정하지 않는다.**
- egui의 읽기 전용 경로 구성은 카테고리 맵과 같은 트리 탐색 함수인 `category_manager::ProductCategoryPaths`로 공유한다. 다른 관리 화면에 같은 목적의 자체 문자열 조합 로직을 추가하지 않는다.

### 52차 후속: 상품관리 카테고리 관리

- **최신 기준:** `src/CategoryManager.tsx`, `src/native-category.ts`, `src/category-tree.ts`, `src/category-roots.ts`, `src/styles/product-admin-redesign.css`와 실제 덮어쓰기 스타일인 `src/styles/tauri-stage2-products.css`의 카테고리 맵 및 오른쪽 편집 레이어를 따른다.
- **화면 구조 (56차 최신 수정, 2026-11-20):** 상품관리의 `카테고리 관리` 하위 탭은 기존 상품 가격표와 별도 화면이다. 전체 너비의 카테고리 트리·검색·선택 분류 편집·하위 분류 추가를 제공한다. **원본 React에 있던 `전체 접기`/`전체 펼치기`는 중복된 보조 기능으로 판단하여 egui 상단에서 제거**하며, 각 분류 행의 접기/펼치기와 검색 결과 자동 펼침은 유지한다. 작업 버튼 2개는 제목 행 오른쪽에 정렬한다. 검색 입력 폭은 `theme::CATALOG_SEARCH_WIDTH`로 제한하고, 별도 `카테고리 검색` 라벨은 표시하지 않는다. 트리 화살표는 누락 폰트에 의존하지 않는 벡터를 사용한다. **분류명 바로 옆에 `(상품 N · 하위 분류 N)`을 표시**하며, 하위 분류가 없으면 `(상품 N)`만 표시한다. 분류 편집도 생성·이동·삭제와 동일한 중앙 모달 호스트를 사용한다. 분류 편집 기본 폭은 공통 중앙 모달 560pt 기준이며, 작업공간의 가용 폭으로 제한한다.
- **분류 자료:** 기존 카테고리·상품 ID를 변경하지 않고 가상 반도스탠드/반도몰 루트를 UI 읽기에서 보충한다. 과거 최상위 분류의 소속은 자동 이동하지 않고 별도 소속 확인 영역에 노출한다. 트리 검색은 이름/전체 경로/하위 분류를 포함하고, 상품 개수는 직접 연결 및 하위 포함을 구분한다.
- **수정 규칙:** 기존 Rust `catalog_clients::change_category`와 `delete_category`를 원본 Tauri helper `--bando-egui-product-patch`로 호출한다. 하위 분류 추가 시 연결된 상품 이전 동의를 확인하고, 타 쇼핑몰로 이동하는 경우 기존 상품 카탈로그 충돌을 거부하며, 직접 상품 또는 하위 분류가 있으면 삭제를 금지한다. 거래처·주문 정보는 변경하지 않는다.
- **저장 보호:** `BANDO_EGUI_BUSINESS_DB` + `BANDO_EGUI_TAURI_HELPER` + `BANDO_EGUI_ENABLE_PRODUCT_WRITE=1` 명시 설정이 있어야 저장된다. 원래 Rust 업무 결과만 `write_snapshot`의 SQLite revision 검사로 기록한다. 카테고리 전용 UI에서 임의의 판정/영속 저장 엔진을 만들지 않는다.
- **미저장 변경:** 인라인 분류 이름 변경과 분류 추가/이동 입력은 독립된 편집 상태다. 모달 닫기·상품관리 탭 이동·전역 페이지 이동에서는 원본의 저장/버리기/취소 흐름을 따르며, 한 편집을 버리는 이유로 다른 편집의 수동값을 소거하지 않는다.
- **미이전:** 모델군·별칭·브랜드 관리, 상품 Excel 및 공식 페이지 동기화/이미지 기능. 카테고리 범위만 근거로 상품관리 전체를 완료 판정하지 않는다.

- **검증**: OCR 위치·폭·단일 본문 경계·이미지 확대와 스크롤·텍스트 수정 및 학습 체크박스·취소·적용이 이전과 시각적·기능적으로 동일한지 확인한다. Windows CI 컴파일과 실제 DPI별 팝업 화면 검수는 별도 기록한다.

### OCR 마스터 기반 기존 팝업 정리 — 2026-11-22

- **공통 헤더 전환**: `components::modal_header` 및 `modal_header_in_rect`/ `modal_header_chrome`은 모두 OCR 승인형 `modal_master_header_in_rect`로 라우팅한다. 제목은 좌측, 취소/닫기/돌아가기는 우측, `PANEL` 배경과 하단 `DIVIDER`는 한 번만 그린다. 설명 없는 확인창은 56pt 컴팩트 헤더로 유지하고 OCR의 84pt 보조설명 헤더를 강제하지 않는다.

### 65차 OCR 정정 이력·선택적 학습 모델 (2026-11-22)

- **보존 근거**: 직원이 OCR 검토 후 적용한 경우에만 최초 PaddleOCR 전문과 최종 직원 수정 전문, 줄 단위 변경 로그를 로컬 격리 `ocr_feedback` 테이블에 남긴다. 취소·교체취소·OCR 실패에서는 학습용 성공 이력을 남기지 않는다. 원본 이미지 바이너리는 이 테이블에 저장하지 않는다.
- **분석 상태 대조**: 접수 원문 저장 성공 후 비동기 작업에서 기존 Rust `AnalyzeOrder` 업무 엔진을 최초 전문과 수정 전문에 각각 적용한다. 동일 카탈로그 스냅샷으로 비교한 두 분석 JSON, 변경 필드 경로 및 분석 상태(`pending/complete/failed`), 엔진 명칭·카탈로그 리비전·오류를 별도로 보존한다. 분석 실패는 기존 접수·편집·적용을 중단시키지 않는다. `PreviewStore::load_ocr_audit`로 두 전문과 분석을 다시 조회할 수 있다.
- **학습 모델 사용**: 오른쪽 OCR 편집 영역 제목 앞의 체크박스이며 기본값은 꺼짐. 꺼지면 인식문 그대로 편집하며, 켜지면 별도 작업 스레드가 최대 1,000건의 기존 정정 이력을 읽어 빈번한 문자열·띄어쓰기 정정 후보를 제안한다. 학습 사용은 검토 및 제안에만 적용하며 무조건 자동 적용·발주서 저장은 하지 않는다. 제안 실패나 빈 데이터는 기존 OCR 검토로 즉시 복귀한다.
- **안전장치**: 3개 이상의 독립 접수 건에서 같은 패턴이 반복되어야 추천한다. 전화번호·수량·상품 모델 번호 등 숫자가 포함된 자동 치환은 금지한다. 모델 제안을 직원이 그대로 승인한 사례는 독립적인 학습 지지 표본으로 다시 계산하지 않아 자기강화 오류를 제한한다. 학습 모델 사용 여부와 제안문도 이력에 기록한다.
- **개인정보 및 운영 범위**: 학습 이력에는 주소·전화번호·수취인 등 개인정보가 포함될 수 있으므로 로컬 격리 DB로만 보관하며, 별도 외부 학습 업로드를 추가하지 않는다. 사용자가 삭제를 명시하지 않는 한 정정 전문은 자동 요약·삭제하지 않는다. 장기적으로 이력 열람·삭제·재학습 관리화면은 별도 검토 사항이다.

#### 거래처별 표 형식 OCR 줄바꿈 학습 (2026-11-22)

- **화면 문구**: 오른쪽 편집 헤더 체크박스는 `학습 모델 사용 (시험 기능)`으로 표시한다. 기본 체크 해제, 기존 OCR 검토 흐름 완전 유지.
- **구조적 오류 분리**: 표 열 너비 때문에 수취인 한 글자씩, 전화번호 중간, 주소 단어, 상품명·수량 등이 행 단위로 끊어지는 문제는 일반 한 글자 오타와 별도의 `layout_trace_json`으로 수집한다. 최초 전문과 직원 수정 전문이 공백을 제외하고 동일한 경우에만 각 줄바꿈의 `유지/공백으로 변경/삭제` 관계를 문자 위치별로 안전하게 정렬한다. 글자 자체가 달라진 사례도 전문 보존 후 재분석 가능하도록 `contentAligned=false`로 남긴다.
- **거래처 연결**: 직원이 거래처를 수동 확인한 경우에만 기존 `ocr_feedback`의 `client_id`를 연결·갱신한다. 인식문만으로 특정 거래처를 사실처럼 확정하지 않는다. 거래처 지정이 OCR보다 나중에 이루어져도 동일 접수 ID로 갱신한다.
- **시험용 템플릿 제안**: 동일 거래처에서 독립 접수 3건 이상으로 확인한 **동일한 표 줄 형식**의 정정만 고려한다. 거래처 미확정 시에는 고유 형식이 한 거래처로만 판별된 경우에 한해 실험적으로 제안하고, 여러 거래처의 형태가 겹치면 원문을 유지한다. 각 줄 경계의 처리 결과가 모두 일치하지 않으면 그 부분은 적용하지 않는다. 반드시 원문 이미지와 수정 가능한 텍스트를 나란히 보여주며 직원의 `적용` 클릭이 필요하다.
- **내용 무결성**: 표 구조에 대한 학습은 **공백과 줄바꿈만** 제안하며 전화번호 숫자·모델명·이름·주소 내용 자체를 바꾸지 않는다. 원문 글자가 실제로 틀린 경우는 별도 문자 오타 정정 데이터로 분석하며, 아직 자동 복원 성공을 보장하지 않는다. 실사용 양식에 따라 줄 수가 달라지면 추천을 보류한다.
- **검증 근거**: 실제 고객 전문은 코드나 테스트에 넣지 않는다. 가상의 3글자 이름, 분리된 전화번호, 끊긴 주소, 상품·수량, 메모의 줄바꿈을 대상으로 안전 복원·3건 미만·거래처 간 중복 양식 거부를 검증한다. 실제 데이터 학습 효과는 Windows 배포 후 별도 측정한다.
