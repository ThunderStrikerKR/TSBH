# 반도허브 UI 실화면 검증 및 완료 판정 계약 (84차)

**적용 범위:** egui 및 React의 모든 UI 화면 변경. 특히 공통 컴포넌트·모달·스크롤·타이포그래피 변경.  
**원칙:** 커밋, 정적 검사, 테스트, CI 빌드의 성공은 **시각적 합격을 의미하지 않는다.**

## 1. 서로 다른 5개 판정을 하나로 합치지 않는다

| 게이트 | 성공의 정확한 의미 | 성공이라고 말할 수 없는 것 |
| --- | --- | --- |
| PATCH | 코드가 특정 커밋으로 저장소에 반영됨 | 작동·화면 품질 |
| STATIC | 규격·공통 컴포넌트 참조·코드 구조 검토 | 실제 렌더링 |
| UNIT / ACTION | 해당 자동 테스트/사용자 동작 테스트가 실행되고 통과함 | 다른 동작·실기기 시각 품질 |
| CI | 해당 SHA에서 지정된 자동 작업이 통과함 | UI 클리핑 없음 |
| VISUAL WINDOWS | **현재 코드로 빌드한 Windows 앱에서** 지정된 뷰포트와 DPI로 실제 캡처 및 조작 확인 | 미검증 해상도·플랫폼 |

**UI 전체 개선 완료**라는 표현은 VISUAL WINDOWS가 PASS이고 중요 업무 회귀검증도 통과한 경우에만 사용한다. 그렇지 않으면 정확히 **코드 반영, 실화면 미검증** 또는 **실화면 불합격**으로 보고한다. 사용자 캡처에서 클리핑이 확인되면 코드가 이미 병합됐어도 FAIL이다.

## 2. 강제 검증 시나리오

모달/관리화면별로 다음 7개 항목을 실제 화면에서 각각 판정한다.

1. **noClipping:** 정보·버튼·테두리·스크롤바가 패널/팝업 경계 밖으로 잘리지 않음.
2. **footerVisible:** 팝업 푸터와 핵심 실행 버튼에 실제로 도달할 수 있음; 내부 스크롤과 겹치지 않음.
3. **scrollReachable:** 원문/표/세부 영역의 독립 스크롤; 마지막 행과 하단 경계 확인.
4. **inputReadable:** 이름·주소·숫자·단가·수량의 가독성, 읽기/편집 모드 글꼴 위치 일치.
5. **alignment:** 마스터 기준 여백, 구분선, 헤더·열·버튼 높이와 정렬.
6. **interaction:** 클릭, 직편집, 저장 실패, 취소, 행 전환, 다건 배송, 키보드·IME, 비동기 응답 확인.
7. **hoverAndFocus:** 양방향 하이라이트, 호버·포커스·비활성 스타일과 팝업 포인터 영역.

**화면 크기:** 1920×1080(기본) + 가로 1500px 이하의 작은 작업공간 **최소 2종**. Windows 배율(100% 외 설정 포함)을 필요에 따라 추가. 카카오톡 도킹 시에는 실제 카카오톡 영역을 뺀 작업 좌표를 확인한다. 작업영역 높이가 콘텐츠보다 작을 때 바깥 팝업 전체가 아니라 콘텐츠 영역의 스크롤로 모든 기능에 접근할 수 있어야 한다.

소스상의 \`available_height()\` 계산 또는 스냅샷 없는 단위 테스트로 noClipping/scrollReachable PASS를 대체하지 않는다. **위치를 픽셀 단위로 보려면 실화면에서 실제 화면 좌표·경계를 확인한다.**

## 3. 증거의 버전 결합과 개인정보

- \`docs/ui-visual-verification/audits/*.json\`에 검수 기록을 저장한다.
- UI 변경 시 관련 소스 경로가 **동일 변경 집합의 검수 JSON에 반드시 기록**되어야 한다.
- VISUAL PASS 조건: 실제 Windows 검수자, 검수일, 2개 이상 뷰포트, 각 7개 체크 PASS, 해결되지 않은 결함 없음, **동일 소스 Git blob SHA**, 캡처 PNG.
- 증거 PNG는 \`docs/ui-visual-verification/evidence/\`에 **가상 데이터·개인정보 제거한 이미지**만 저장한다. 운영 고객의 이름, 전화, 주소, 거래정보가 포함된 원본 캡처를 공개 저장소에 올리지 않는다.
- 변경된 UI 소스 blob과 검수 당시 blob이 달라지면 이전 스크린샷의 PASS 판정은 자동 무효 처리한다. 재검수한다.
- 컴퓨터로 자동 확인할 수 있는 것은 JSON·경로·PNG 형식·소스 일치뿐이다. **스크린샷의 실제 픽셀 품질은 검수자가 확인해야 한다.** 자동 검사 통과를 무인 시각 합격으로 주장하지 않는다.

## 4. CI 강제 검사

- 검사기: \`scripts/check-ui-visual-verification.mjs\`
- 워크플로: \`.github/workflows/ui-visual-evidence.yml\`
- 자체 테스트: \`tests/ui-visual-verification.test.mjs\`
- 전체 현황 확인: \`node scripts/check-ui-visual-verification.mjs --all\`
- 특정 화면 확인: \`node scripts/check-ui-visual-verification.mjs --audit docs/ui-visual-verification/audits/manual-classification-84.json\`
- 변경 범위 확인: \`node scripts/check-ui-visual-verification.mjs --base <비교-커밋-SHA>\`

**실패 조건:** UI 소스를 수정하면서 검수 기록을 빠뜨린 경우, FAIL/NOT_VERIFIED인 경우, PASS를 주장하지만 캡처·검수자·뷰포트·필수 항목이 없는 경우, 변경 소스와 blob이 다를 경우. 해당 워크플로는 빨간 실패가 정상적인 **미검증 상태 표시**일 수 있다. 실패를 자동으로 PASS로 무시하거나 다른 빌드 CI 성공으로 덮어쓰지 않는다.

GitHub의 브랜치 보호에서 이 워크플로를 **필수 체크**로 지정해야 병합 자체가 차단된다. 워크플로 파일을 추가하는 것만으로 보호 규칙이 자동 설정되지는 않는다.

## 5. 보고서·대화에서 허용하는 상태 표현

| 상황 | 허용 표현 | 금지 표현 |
| --- | --- | --- |
| 코드 커밋만 있음 | “코드 반영, 실행·실화면 미검증” | “화면 개선 완료” |
| CI는 성공, 실제 화면 미확인 | “빌드 검사 통과, UI 품질 미검증” | “UI 검수 통과” |
| 실제 캡처에서 잘림 발견 | “UI 불합격, 결함 OPEN” | “개선 완료, 추가 확인만 필요” |
| 실제 Windows 2종 캡처·조작·결함 검증 | “검증한 SHA/환경에 한해 UI PASS” | “모든 환경 완벽” |

## 6. 84차 수동 분류 재판정

\`docs/ui-visual-verification/audits/manual-classification-84.json\`의 현재 상태는 **FAIL**. 사용자가 2026-11-24 제시한 Windows 실행 화면에서 우측 **발송·운임 버튼 하단 클리핑**과 좌우 공간 밀도 불균형이 확인됐다. 이전의 “코드 반영”은 사실이나 “디자인 개선 합격”의 증거가 아니다. 재설계·실기기 검증 전까지 FAIL을 유지한다.
