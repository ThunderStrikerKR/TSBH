# 접수 화면 내비게이션 확인창 전수조사 및 자동저장 개정 (2026-11-19)

## 업무 규칙
- 처리 중인 주문: **접수 직후부터** SQLite `reception_working_orders`에 저장된다. 주문 확인 완료 전이어도 프로그램 재실행 후 복원한다.
- 확정 주문을 다시 수정: `reception_confirmed_edits`에 **작업본만** 자동 저장한다. 이때 `core_orders`, 청구 스냅샷, 업무 확정 이력은 절대 고치지 않는다.
- 주문 확인 완료: 기존 Rust 단계 검증·청구 스냅샷 절차가 실행되는 시점이며 이때부터 주문내역 노출이 가능하다.
- 원본 확정 주문이 다른 경로에서 변경된 경우 Rust가 기준 payload 충돌을 감지하고 이전 작업본을 SQLite에 보존한 채 저장/복원을 거부한다. 직원에게 저장 오류가 노출된다.

## 접수 → 다른 상단 메뉴 이동: 팝업과 실제 발생 조건

| 기존 문구/경로 | 예전 발생 조건 | 변경 후 |
|---|---|---|
| 「수정한 주문 정보가 저장되지 않았습니다」 (HubWorkspace.leaveGuard) | SQLite에 이미 확정된 주문을 접수 화면에서 편집하고 타 메뉴 이동 | **제거**. 수정된 확정 주문 전체를 별도 SQLite 작업본에 저장·완료 기다림, 업무 확정은 하지 않음 |
| 「접수 화면에 저장하지 않은 변경사항이 있습니다」 (useAppModel fallback) | leaveGuard가 처리하지 않은 dirty draft | **제거**. 보호 guard가 없는 비정상 상황에는 확인창이 아니라 저장 오류를 알리고 이동 차단 |
| 「저장하지 않은 편집창이 있습니다」 (useAppModel.hasPendingChanges) | 별도 활성 편집기가 미저장 상태 | 접수 이동에서 `requestPageLeave({autosave:true})`로 등록 편집기를 먼저 저장. 등록/처리되지 않은 미저장 편집이 남을 경우 오류 안내·이동 차단 |
| 「발주서 자동 저장 실패」 (SQLite) | DB 잠금, 디스크 용량 부족, 테이블/연결 오류, 충돌 | **유지**. 팝업 대신 `onNotice(...,"error")`를 통해 상단 알림에 영구 오류 기록. 이동 중단하고 모든 작업본 보존 |
| 「현재 작업의 저장이 끝난 뒤 이동할 수 있습니다」 (page-leave busy) | 활성 편집기 저장 중 이동 시도 | 접수 이동에서는 이전 저장 완료를 자동 대기. 정상 완료 후 이동; 지연/실패 시 오류와 이동 중단 |

## 다른 화면과 프로그램 종료
- 「새 주문」, 기존 주문 열기, 모바일/사진 발주서 수신, 처리 중 배송 건 전환에서도 접수 활성 편집기를 자동저장하고 SQLite 전체 작업본 저장 완료를 기다린다.
- 접수에서 프로그램 종료할 때도 활성 편집기 및 SQLite 저장 완료를 기다린 뒤 `requestClose(false)`를 호출한다. 정상 작업에서 브라우저의 종료 확인은 표시하지 않는다.
- 상품 관리, 거래처 관리, 설정, 운임 관리 화면의 **명시적 저장/등록 정책은 이번 변경 대상이 아니다**. 해당 화면에 고유한 저장·취소 확인 또는 신규 그룹 등록 유효성 검사는 유지한다. 다른 탭에서 닫기를 누르면 그 탭의 편집 보호를 먼저 수행한다.
- 관리자 테이블, Rust 원본 검증, 운임 실제 확정 단계 등 별도의 도메인 유효성 검사 팝업은 변경하지 않는다.

## 코드 경로
1. `AppHeader.onNavigate → useAppModel.navigate`
2. `requestPageLeave(...,{autosave:true})`: 활성 접수 편집기 자동 저장, 진행 중 쓰기 대기
3. `HubWorkspace.leaveGuardRef`: 미확정 접수 + 확정 주문 수정 작업본을 `WorkingReceptionAutosave.enqueue(workingCopies)`로 직렬화한 SQLite 트랜잭션 완료까지 대기
4. 정상 완료: `setTab(page)`; 실제 DB 실패: 경고 후 그 화면·편집 상태 유지
5. 프로그램 종료: 같은 저장 절차 후 `requestClose(false)`

## 검증 체크리스트
1. 접수 2건 입력 → 이동 → 재시작 후 원문·상품·수취인 동일 복원
2. 확정 주문 수정 → 이동 → 재시작 후 작업본만 복원, `core_orders` 원본/청구 스냅샷 변경 없음
3. 실제 출고 운임 편집 중 이동 → 저장 성공 시 자동 이동, 실패 시 내용 유지/알림
4. DB 저장 실패/확정 원본 충돌에서 기존 작업본 보존 및 이동 차단
5. 기존 '주문 확인 완료' 단계에서 정확히 한 번 주문내역 노출
6. 기존 상품/거래처/설정 화면의 명시적 저장 정책 불변

Windows 실행 및 재시작 복원은 CI 결과와 별도로 판정해야 한다.
