## 1. 적용 경계와 소유권

- 적용 기준은 `egui-app`의 Rust/egui **관리 화면**이다. 이전 React/CSS 화면의 숫자를 자동 이식하지 않는다.
- 같은 **역할**이면 수치와 컴포넌트를 공유한다. 역할이 다른 레이아웃은 별도의 명명된 규격을 둔다. 화면 파일에 같은 상수값을 새로 적거나, 기존 디자인 위에 1~3pt 임시 보정을 누적하지 않는다.
- 원본 코드: **`egui-app/src/theme.rs`**(색·간격·크기·마스터 표 사양), **`egui-app/src/typography.rs`**(서체·크기·행간·문자 광학 보정), **`egui-app/src/components.rs`**(공통 Rect 계산·컨트롤·고정 헤더·화살표).
- 두 공동 마스터의 실제 소비자: `egui-app/src/freight_manager.rs`와 `egui-app/src/order_history_manager.rs`. 업무 판단·DB·송장·저장은 이 디자인 계약으로 변경하지 않는다.
- 역사적 결정 기록: `egui-dual-master-ui-contract-draft.md`, 화면의 업무별 예외 참고: `egui-management-ui-reference.md` 및 `management-layout-rules.md`. **수치가 중복되면 이 문서에서 지정한 Rust 토큰을 단일 원본으로 취급**한다.

### 운임 관리 하위 탭 및 전체 기준 변경의 안전 경계

- 하위 탭은 **배송 그룹 편성 → 배송 그룹 관리 → 조합 / 기준 이력 → 운임 기준 관리**의 순서로 표시한다. 기존 관리 탭 컴포넌트와 38pt 높이를 그대로 사용한다.
- 배송 그룹 관리의 36pt 도구줄에는 **왼쪽 배송 그룹 검색**과 **오른쪽 배송 그룹 추가**만 표시한다. 그룹 이름은 버튼 클릭 후 팝업에 입력한다. 표는 **그룹명 / 묶음 한도 / 소속 상품 / 관리**의 4열로 고정하며, 상태·참고 메모/최근 수정·수량별 배송비 열을 표시하지 않는다. 폭 1265pt의 기본 배분은 `[450,112,551,128]pt + 8pt × 3`이고 가용 공간이 더 생기면 **소속 상품** 열만 확장한다. 그룹명은 배송 그룹명을 그대로 표시한다. 소속 상품은 배송 그룹 편성 화면과 같은 실제 등록 상품의 `shippingGroupId`로 연결하고 이름·부제를 표기한다. 단일 행 높이를 유지하면서 공간에 맞는 이름을 표시하고 나머지는 `외 N개`로 요약하며 전체 상품 이름은 호버로 확인한다. 각 행의 **관리** 버튼은 팝업 메뉴로 `운임 수정 / 기준 변경 / 이름 수정 / 삭제`를 제공한다. 해당 작업은 기존 Rust 수정·확인·이력 보존 경로를 호출하고, 그룹별 **기준 변경**은 전체 운임 기준 변경과 구분한다.
- **조합 / 기준 이력 첫 표**는 `조합 / 청구 운임 / 실제 운임 / 기준 / 상세정보`의 **5열**로 구성한다. 기존 `등록일 / 검증` 열은 제거하고, 행별 `상세정보` 버튼의 팝업에 등록일(`at`)·실배송 검증 기록(`verifiedAt`, `sampleCount`)을 보여준다. `예외 운임 변경`은 같은 팝업의 작업으로 보존하며, 기존 확인 모달 및 Rust `revise_combination` 경로를 변경하지 않는다. 청구 운임(`charge`)과 실제 운임(`actual`)은 독립적인 값이며, 실제 운임은 미등록일 수 있다. 기존 6열 이력 표의 최소 너비 1229pt를 5열 `[500,160,160,140,237]pt + 8pt × 4`로 유지하고, 아래 '이전 그룹 운임 기준'의 6열 표는 변경하지 않는다.
- **임시 비활성화(사용자 결정 대기):** `조합 / 기준 이력 → 이전 그룹 운임 기준`의 별도 목록 카드와 바로 앞 12pt 간격은 렌더링하지 않는다. 소스의 `SHOW_PREVIOUS_GROUP_FREIGHT_HISTORY=false`로 제어하고 저장된 `shipping.groups[*].history` 및 `save_group_rule`·`change_basis`에서 과거 운임을 보존하는 Rust 업무 기능은 변경하지 않는다. 이를 배송 그룹 관리의 관리 팝업으로 옮기지 않는다. 이후 표시 위치는 사용자가 결정한다.
- **조합 / 기준 이력 첫 표**는 제목 '확인된 배송 조합'을 렌더링하지 않는다. 실제 도구줄이 없으므로 36pt짜리 유령 위젯을 그리지 않고 `management_sticky_table_header_without_toolbar`의 **단일 57pt 전환 영역**(도구줄 기준 높이 36pt + 16pt 상단 여백 + 1pt 구분선 + 4pt 하단 여백)으로 36pt 표 헤더 시작 Y를 마스터와 같게 한다. 데이터가 없어도 헤더 좌표를 유지하고 빈 상태 문구는 표 본문에만 표시한다. **이전 그룹 운임 기준**은 임시 숨김을 유지하며 복원 시에만 아래 섹션의 별도 표·접기/펼치기 구조를 사용한다.
- **배송 그룹 편성 마스터 UI 재사용:** 배송 그룹 관리와 조합 / 기준 이력 모두 `management_master_header_begin`(36pt 배경·34pt 텍스트 영역), `management_master_header_sort_hover`(정렬 영역 호버 윤곽선), `management_master_header_finish`(내부 2pt 하단선)를 사용한다. 두 화면에서 1pt 임의 이동·1pt 경계선 대체를 금지한다. 현재 이력은 과거 그룹 운임 카드가 숨겨져 있으므로 **단일 표** 역할이며 바깥쪽 페이지 스크롤 없이 `management_master_table_frame`(16pt 안쪽 여백), `management_single_list_scroll_height`(카드 남은 높이), `management_table_scroll_track_rect`(공통 레일)를 사용해 데이터 본문만 스크롤한다. 60% 높이 제한과 바깥 페이지 스크롤은 과거 이력 섹션의 표시를 승인받아 실제 다중 표 구성이 복구될 때만 조건부 적용한다.
- **전체 운임 기준 변경**은 오직 마지막 **운임 기준 관리** 탭에만 배치한다. 현재 기준 번호 및 변경 영향 설명을 먼저 보여주고, 버튼 클릭은 기존 `freight-basis-confirm` 확인 모달을 여는 동작까지만 허용한다. 확인 전 Rust `change_basis` 명령을 호출하지 않는다.
- 전체 기준 변경과 개별 그룹 기준 변경은 업무 대상이 다르다. 기존 이력 보존, 저장 권한, 리비전 검사, 저장/실패 알림은 기존 Rust 경로를 유지한다.

## 3. 마스터 테이블 수치: 코드가 강제하는 원본

두 표는 같은 공통 헤더·기본 행·스크롤 문법을 사용하되 업무 열 구조는 **서로 다른 타입 사양**이다.

| 마스터 | 기본 열 너비(왼쪽→오른쪽, pt) | 열 간격 | 최소 폭 | 남는 데이터 폭 |
| --- | --- | --- | --- | --- |
| 배송 그룹 편성 | **44 / 202 / 104 / 258 / 150 / 144** | 8pt ×5 | **942pt** | 상품명 열 **64%**, 카테고리 열 **36%** |
| 주문 내역 | **112 / 156 / 300 / 126 / 124 / 112 / 264** | 8pt ×6 | **1242pt** | 배송 건/상품 열 **100%** |

- **유일한 선언**: `theme::FREIGHT_ASSIGNMENT_MASTER_TABLE` / `theme::ORDER_HISTORY_MASTER_TABLE`의 `base_columns`, `min_width`, `growth_shares`.
- **유일한 열 폭 산출**: `ManagementMasterTableSpec::widths_for(measured_data_width)`. 이 입력은 **스크롤바 할당폭을 제외한 실제 표 데이터 너비**이며 도구줄 너비를 넣지 않는다.
- 기존 상수 `FREIGHT_ASSIGNMENT_COL_WIDTHS`, `FREIGHT_ASSIGNMENT_TABLE_MIN_WIDTH`, `ORDER_HISTORY_COL_WIDTHS`, `ORDER_HISTORY_TABLE_MIN_WIDTH`는 중복 값이 아닌 **중앙 사양의 별칭**이다.
- **CONFLICT-002 확정**: 승인된 현행 코드 값을 보존한다. 옛 규격의 배송그룹 상품명 218/설정 128pt, 주문 처리 132pt/최소 1110pt를 다시 사용하지 않는다.
- 정식 코드의 `ManagementMasterRowPolicy`와 `ManagementMasterToolbarPolicy`를 아래 예외의 선언형 정책으로 사용한다.

## 5. 검증과 변경 통제

1. 공통 UI 값 변경 요청은 **역할 ID → 코드 토큰/함수 → 영향받는 화면 → 예외 충돌 여부** 순서로 평가한다.
2. 변경하려는 속성이 두 마스터에서 **같은 역할인데 서로 다른 값을 요구하면 사용자에게 먼저 충돌 결정**을 받는다. 예외를 승인 없이 지우거나 임의 보정값으로 덮지 않는다.
3. 소스에서 가벼운 검증을 수행한다. 현재 `theme.rs`에는 **두 마스터 최소 열 폭 = 열 너비 합 + 간격**, 잉여 폭 분배 합계 100%, 예외 정책 및 대표 너비 계산을 검사하는 집중 테스트를 정의했다. `components.rs`에는 도구줄 우측 끝·헤더 36pt·스크롤바 데이터 경계의 기하 불변식이 있다.
4. **컴파일·테스트 성공을 주장하려면 실제 실행 결과가 필요**하다. 테스트를 작성한 것과 실행한 것은 다르다. 이전에 실패한 대량 업무 회귀테스트를 UI 작업을 이유로 무작정 재도입하지 않는다.
5. 사용자 Windows 화면의 100%·125%·150% 배율에서 검수할 때 `pixels_per_point`도 기록한다. **물리 픽셀 = 논리 pt × pixels_per_point**; 글리프 잉크와 위젯 `Rect`의 시각적 중심은 별도로 확인한다.
6. **공동 마스터에서 다른 관리 화면으로 규격을 확장했다.** 실제 수정된 화면·기존값을 보존한 예외·사용자 결정이 필요한 충돌은 [타 화면 적용 기록](egui-management-ssot-rollout-20261121.md)에 기록한다. 전체 화면의 실시간 좌표를 수집·자동 대조하는 시스템과 Windows 실화면 판정은 여전히 별도 **Q2/Q3** 범위이며, 정적 연결 확인을 전체 UI 완전 통일로 보고하지 않는다.

### 접수 OCR 검토 팝업 공백·응답정지 대응 (2026-11-22)

- **재현 징후:** Windows에서 이미지 OCR 완료 직후 접수 화면이 어두워지고 큰 빈 검은 모달만 남음. 제목, 비교 이미지, 인식 텍스트, 적용/취소 버튼이 보이지 않음. 이 상태만으로 OCR 결과 데이터가 사라졌거나 실제 프로세스가 멈췄다고 단정하지 않는다.
- **소스 진단:** `show_ocr_review`는 `Window::fixed_size`로 외곽 크기를 지정하면서 **팝업 내부 전체 직사각형을 `ui.available_width()/available_height()`로 다시 할당**하고 있었음. egui 창 내부의 남은 가용 높이는 고정 콘텐츠 높이 계약이 아니므로, 전체 작업영역을 점유하거나 자식 섹션 클리핑이 잘못될 가능성이 있다.
- **우선 수정:** 창의 명시적 `dialog_width/dialog_height`에서 `MODAL_PANEL_PADDING_X/Y` 및 `FRAME_STROKE_WIDTH`를 제외한 유한 `body_size`를 만들고, 모든 OCR 헤더·설명·이미지·텍스트·하단 버튼 영역을 그 하나의 고정 rect에서 계산한다. `ui.available_height()`로 OCR 전체 본문을 할당하지 않는다. 기존 이미지 독립 스크롤, 확대, 텍스트 수정, 명시적 적용/취소, OCR 결과 원문 및 카카오톡 도킹 경계는 보존한다. OCR 결과 텍스처를 생성한 직후에는 `ctx.request_repaint()`를 명시적으로 호출하여 첫 비교 화면이 이전 프레임의 빈 표면에 머무르지 않게 한다.
- **검증 구분:** 수정 전 Windows egui 타깃 빌드는 성공했으나 팝업 렌더링 문제는 화면에서 관찰됨. 수정 후 소스/컴파일과 실제 Windows OCR 팝업 표시·버튼·이미지 스크롤 반응은 각각 따로 판정한다. 전체 업무 회귀테스트는 별도로 수행하지 않는다.

### 접수 클립보드 형식 검증 및 최종 저장 후 자동 비우기 (2026-11-22)

- **활성 조건:** 접수의 `대리발송`·`대리점 납품` 버튼은 `ClipboardMonitor.kind().has_intake()`가 참이고 OCR/클립보드 작업 중이 아닐 때만 활성. 판별기는 비어 있지 않은 텍스트 또는 길이 검증에 성공한 RGBA 이미지만 수락하며, 파일 목록/지원하지 않는 형식만 들어 있으면 `Empty`로 취급한다. Windows가 동시에 제공하는 텍스트·이미지가 있는 혼합 형식은 해당 유효 데이터로 인식할 수 있다.
- **삭제 시점:** 단순 버튼 클릭, OCR 처리 완료, 검토 팝업 열림, 인식 텍스트 편집, 원문 교체 대기 중에는 Windows 클립보드를 변경하지 않는다. 텍스트 접수 또는 OCR `적용` (필요 시 추가 `교체` 확인)으로 원문 저장을 요청한 후, **`SourceAutosave::Saved`의 주문 ID·원문·접수 유형이 해당 요청과 모두 일치할 때만** 비운다. 저장 실패/취소는 원본을 유지한다.
- **덮어쓰기 보호:** Windows `GetClipboardSequenceNumber`를 읽기 전후에 확인하고, 성공한 접수의 클립보드 변경 번호를 유지한다. 저장 완료 직전 다른 텍스트·이미지·파일을 새로 복사했다면 클립보드를 절대 비우지 않는다. 제거 직전 `OpenClipboard`로 잠근 후 변경 번호를 재검증하고 `EmptyClipboard`를 호출한다. 변경 번호가 확인되지 않는 환경에서는 안전을 위해 자동 비우기를 생략한다.
- **적용 범위:** 이번 자동 비우기는 **두 클립보드 접수 버튼**으로 시작한 원문에만 적용한다. 텍스트 편집창에 직접 입력·Ctrl+V, 카카오톡, 다른 메뉴의 복사 기능은 그대로 둔다. Windows 클립보드는 OS 전역이므로 실제 비우기 성공 후에는 다른 프로그램에서도 이전 내용으로 붙여넣을 수 없다.
- **검수:** 파일만 복사/빈 텍스트/이미지/일반 텍스트의 버튼 상태, 저장 성공 후 자동 비우기, OCR 취소·교체 거절·저장 실패 시 보존, OCR 중 새 복사 내용 보호를 Windows 실기기에서 확인한다. 소스 정적 검토와 CI 컴파일 결과를 실제 클립보드 실행 검수로 혼동하지 않는다.

### 접수 캡처 범위 지정 활성화 및 키캡 안내 (2026-11-22)

- **기존 오류:** egui 접수의 `캡처 범위 지정` 버튼은 `ButtonRole::Emphasized, false`로 강제 비활성화되어 있고 클릭 경로도 미연결이었다. 클립보드가 비어 있어도 화면에서 신규 캡처를 수행할 수 있어야 한다.
- **동작:** 클립보드의 내용과 **무관하게** 접수 메뉴에서 캡처 버튼 활성. 클릭하면 반도허브 창을 일시 최소화하고 Windows 기본 `Win + Shift + S` 선택 UI 호출 → **새롭게 생성된** 클립보드 이미지와 변경 번호만 수신 → 앱 창 복귀 → 기존 `clipboard_intake::recognize_image` 로컬 PP-OCRv5 → 직원의 단일 `OCR 문자 인식 검토` 창으로 연결한다. 기존 대리발송/대리점 납품의 텍스트·이미지 붙여넣기 활성 조건은 그대로 둔다.
- **안전성:** 창 최소화·복귀는 자동 복원 가드로 처리한다. `Esc` 또는 OCR 취소, 클립보드에 캡처 대신 다른 내용 복사, 75초 선택시간 초과, 인식 실패 시 발주 원문을 자동 반영하지 않는다. 검토 `적용` 이후 기존 원문 교체 확인 및 저장 완료에 의해서만 원문 데이터가 변경된다. 취소 시 기존 클립보드 내용은 자동 삭제하지 않는다.
- **안내 문구:** 잘못 표기된 `Ctrl + Shift + S`를 제거하고 `Win`, `Shift`, `S`, `Print Screen`을 각각 공통 `RAISED` 배경·`BORDER` 1pt·공통 반경의 키캡으로 표시한다. 가로 배치가 어려우면 접수 안내 영역에서만 줄바꿈하며, 키캡 행 높이를 28pt로 예약한다.
- **검수:** Windows 10/11에서 기존 클립보드가 비었을 때도 클릭 가능, 앱 최소화/복원, 신규 화면 선택 영역만 OCR, Esc 취소·기존 원문 불변, 인식 결과 적용·재접수, 좁은 창 키캡 줄바꿈/스크롤 검수. 실제 Windows GUI 검수 전에는 완전 해결이라고 단정하지 않는다.

### 접수 발주 원문 본문 16pt (2026-11-22)

- **발주 원문만 확대:** 클립보드로 접수한 원문 및 직접 입력 후 편집 중인 `TextEdit`, Rust 인식 구간 하이라이트 `source_highlight::layout`, 처리 중 주문을 선택했을 때의 읽기 전용 `source_raw`는 모두 `typography::FONT_RECEPTION_SOURCE_TEXT`를 사용한다.
- **OCR와 동일 기준:** `FONT_RECEPTION_SOURCE_TEXT = FONT_OCR_REVIEW_TEXT = 16pt`. 원문 표시와 인식 구간별 글자 위치 계산은 **같은 폰트 크기**를 사용해야 클릭/호버 범위가 어긋나지 않는다.
- **비대상:** 일반 본문 `FONT_BODY=14pt`, 현재 거래처 요약·수취인·상품 입력·자동 메시지·테이블, 섹션 제목은 기존 위계를 유지한다. 4열/세로 분할 크기, 소스 스크롤 및 OCR 검토 모달의 레이아웃은 변경하지 않는다.
- **검증:** 소스 토큰 및 세 렌더링 경로의 정합성 점검과 Windows 실제 DPI별 화면·줄바꿈 검수를 구분한다.

### 수취인별 주문 정보 — 제목 오른쪽 이동식 탐색기 (2026-11-22)

- **원칙:** 인식된 수취인/택배 건수가 2건 이상이면, 기존 이름 입력창 **위에 있던 수취인 목록 탭/가로 스크롤을 제거**하고 `수취인별 주문 정보` 섹션의 **34pt 제목 행 오른쪽**에 현재 수취인 탐색기를 배치한다. 1건이면 제목 옆 탐색기를 표시하지 않는다.
- **마스터 참조:** `주문 내역`의 날짜 선택 그룹과 동일한 단일 `INPUT` 배경, 둥근 외곽선, 내부 세로 `DIVIDER`, **28pt 좌우 화살표**, 공통 벡터 셰브론. 배열은 **`〈 | 현재 수취인 이름 | 〉 | 1/2`** 순으로 한다. 좌·우 화살표가 동일한 수취인 이름을 감싸고, 진행도는 오른쪽 독립 정보 셀로 표시한다. 날짜 선택기처럼 **외곽을 한 번만 예약**하고 내부 요소 높이를 제한하여 제목 행이나 섹션/표 구분선을 늘리지 않는다.
- **의미:** 이름은 선택된 수취인의 실제 등록/인식된 이름(없으면 `수취인 N`), 진행도는 `선택된 순서/전체 수취인 수`로 표시한다. 이름이 길면 고정 폭의 헤더 슬롯에서 줄임표로 축약하며, 호버 시 전체 이름을 보여주고 **잘린 이름을 클릭하면 최대 320pt 폭의 줄바꿈 팝업**에서 전체 이름을 확인한다. 첫 항목의 이전 버튼과 마지막 항목의 다음 버튼은 **별도 어두운 배경(RGB 27)과 낮은 대비의 화살표(RGB 72)**로 명확히 비활성화하고, 클릭/호버 안내 없이 순환하지 않는다.
- **업무/기하 보존:** 선택 이벤트는 기존 `selected_recipient`를 바꿔 아래의 연락처·품목·운임 표시를 같은 대상으로 유지한다. 처리 중 주문의 읽기 전용 상세는 동일한 컴포넌트로 `workflow_ui.select`에 연결한다. 하단 수취인 필드 36pt 행/8pt 간격, 4열 도킹, 분할 경계, 원문 연결 하이라이트는 변경하지 않는다.
- **검수 경계:** Rust 코드 정합성·Windows 컴파일과 실화면 좁은 창·2/3건 전환·빈 이름·긴 이름·읽기 전용 진행도 전환을 구분해 확인한다.

### 공통 셰브론 렌더링 정합성 — 날짜·수취인·목록 (2026-11-22)

- **진단:** 날짜 선택기의 이전/다음과 수취인 선택기의 양방향 셰브론은 `components.rs::paint_management_chevron_with_color` → `paint_chevron_at_angle`을 공유한다. 주문 내역 행 펼치기, 달력 월/연도 이동, 드롭다운도 같은 벡터 생성기를 사용한다. 버튼 배경·비활성 색상은 역할별로 다르지만 **화살표 기하와 획 렌더러는 공통**이다.
- **원인 수정:** 기존에는 화살표 두 대각선을 `painter.line_segment`로 **각각 독립적으로** 그렸다. 끝이 만나는 꺾임 부분의 반투명 안티앨리어싱 픽셀이 두 번 겹쳐 색 밀도가 달라질 수 있다. **단일 `egui::Shape::line(vec![start,tip,end], Stroke::new(1.8, color))`**로 한 번만 테셀레이션하도록 교체한다. 글리프 크기(10pt), 획(1.8pt), 회전 각도, 위치의 광학적 보정과 호출부 버튼 크기는 그대로 유지한다.
- **공유 범위:** 수취인 탐색기, 주문 내역의 이전/다음 날짜, 달력 이동, 드롭다운, 목록 펼치기 등은 별도 복사한 그리기 함수가 아니라 **공통 벡터 경로만 호출**한다. 색 조정으로 아티팩트를 가리는 접근을 반복하지 않는다.
- **실화면 검증:** Windows egui 100%/125% DPI에서 좌·우·아래 방향의 끝점과 꺾임 부분 색 균일성, 활성·비활성 대비, 달력·수취인·주문 내역을 실제 실행하여 비교한다. 소스 변경만으로 시각적 검증 완료를 선언하지 않는다.

## 6. 후속 변경 원칙

- 화면 개별 패치 대신 승인된 공통 소유자를 수정한다. 예외가 실제로 존재하면 문서와 코드의 역할 정책을 함께 유지한다.
- **정식 기준은 코드의 현재 토큰**이며, 이 문서는 의도·예외·검증 방법의 규범이다. 숫자 복사본을 다른 문서에 다시 추가하지 않는다.
- 새로운 레이아웃을 마스터에 반영하기 전, 기존 구조·클릭 영역·스크롤·표 헤더 오프셋·업무 흐름을 그대로 보존할 수 있는지 검사한다.

### CategoryTree 공통 규격 (2026-11-26)

- `components::category_tree_row` / `CategoryTreeGeometry`가 행, 선택·호버, 폴더, 화살표, 연결선, 이름·보조 수치 및 클리핑을 단일 관리한다. 카테고리 관리자는 데이터·검색·펼침·선택 상태와 업무 동작만 관리한다.
- 모든 깊이 42pt 행, 24pt 들여쓰기, 좌우 12pt 인셋, 16pt 공통 화살표 슬롯, 20pt 폴더 슬롯(1.5pt 선), 슬롯 및 이름 간격 8pt. 연결선 1pt, 화살표/폴더 슬롯 경계 전 4pt에서 종료. 말단은 빈 화살표 슬롯을 통과하여 폴더 직전까지 연결한다. 마지막 형제의 세로선은 행 중앙에서 끝난다.
- 접힘/펼침 폴더 벡터 형상 분리, 말단은 닫힌 폴더. 일반/최상위 행 모두 수평 구분선을 제거하고 계층 연결선으로 그룹을 표현한다. 미선택 호버는 기존 공통 파란색 배경·테두리, 선택은 기존 주황색 강조 배경·테두리·폴더 색상을 재사용한다. 선택 상태가 호버보다 우선한다.
- 기존 루트 제목 글꼴 및 보조 수치 글꼴을 유지하고, 좁은 폭에서는 텍스트를 잘라 표시한다. 행 클릭의 선택·펼침 전환 규칙과 검색 중 동작은 변경하지 않는다.
- `category_tree_geometry_tests`는 슬롯 크기, 중심선, 깊이, 말단 연결선, 마지막 형제 및 조상 레일을 검증한다.
