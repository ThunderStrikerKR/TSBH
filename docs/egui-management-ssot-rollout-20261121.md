# 관리 UI SSOT — 타 화면 실제 적용 기록 (2026-11-21)

> **적용 기준:** `docs/egui-management-ui-ssot.md`, 공동 마스터는 **운임관리 → 배송그룹 편성 / 주문내역**.
> **이번 적용은 두 마스터에서 승인한 동일 역할의 기존 치수를 중앙 소유권에 연결한 것**이며, 모든 화면이 두 마스터와 픽셀 단위로 일치한다는 최종 판정이 아니다.
> **검증:** GitHub `main`의 수정된 소스·함수 호출을 정적으로 재조회했다. Windows 빌드 / 실제 렌더링 / DPI / 업무 회귀테스트는 수행하지 않았다.

## 1. 실제 소스 적용

| --- | --- | --- |

| **운임관리 → 조합 및 이전 기준 이력** | 동일 공통 고정 헤더, 가중치 기반 공통 열 배분 | 조합/이력별 서로 다른 열·확장 기능·정렬 |
| **주문내역 마스터** | 고정 대표행에서 freight 전용 별칭 대신 의미 기반 `MANAGEMENT_COMPACT_ROW_HEIGHT` 사용. 필터 148pt 토큰 공유 | 7열과 가변 상세행, 날짜 줄바꿈, 마스터 헤더·표 레일 |
| **배송그룹 편성 마스터** | 기존 148pt 필터를 `MANAGEMENT_FILTER_DROPDOWN_WIDTH`에 연결 | 6열, 64/36 잉여 폭, 고정행, 최종 승인 화면 |

## 최신 정정 — 모든 관리 표 스크롤바 연장값 7pt 단일화 (2026-11-21)

- **사용자 실제 화면 검수 결과:** 배송 그룹 관리, 거래처 관리, 조합/기준 이력, 일일 결산에서 7pt를 적용해도 문제가 없으며 현재 화면들을 완성된 예외의 근거로 취급하면 안 된다.
- **현재 유효 소스:** `theme::MANAGEMENT_TABLE_SCROLL_RAIL_EXTENSION = 7pt` 및 `components::management_table_scroll_track_rect(ui,scroll_height)`. 모든 사용 화면은 숫자/역할 인자를 제거했다. 스크롤바 트랙 시작은 본문 시작, 끝은 본문 종료 Y + 4pt(7pt 연장 - 3pt 광학 보정)이다.
- **분리 원칙:** 카드·본문의 높이와 푸터 예약은 화면 업무에 따라 유지하되, *스크롤바 하단 연장값*을 화면별로 구분하지 않는다. Excel의 편집 상세와 파일 작성 푸터도 높이 예약값을 보존한다.
- 아래 과거 기록의 `0/1/16pt` 및 `ManagementTableScrollRole` 정책은 **이전 시도 기록**이며 더 이상 현재 구현을 설명하지 않는다. 다른 관리 화면들의 레이아웃은 아직 완성 판정이 아니다. 코드 반영과 Windows 실화면·배율 검수는 별도 판정한다.

## 1.1. 과거 스크롤바 정책 변경 기록 (폐기된 값 포함)

- **원인:** 배송그룹 편성만 카드 하단 패딩 16pt를 트랙에 더하고, 주문내역은 트랙을 표 본문에서 끝냈으며, 다른 목록은 자체 `ScrollArea` 기본값에 맡겨져 있었다. 같은 SSOT 토큰을 공유해도 표 하단 테두리와 레일의 길이가 달랐다.
- **수정 후 단일 소유자:** `components::management_table_scroll_track_rect(ui,scroll_height,bottom_extension)`가 모든 관리 표의 트랙 상단 +3pt 및 하단 좌표를 계산한다. `theme::MANAGEMENT_TABLE_SCROLL_TRACK_TOP_INSET=3pt`가 상단 규칙을 소유한다.
- **표 전용 공통 스타일:** `theme::management_table_scroll_style()`은 solid 10pt 레일·핸들 최소 44pt를 유지하고 내·외측 추가 여백을 각각 0pt로 설정한다. 페이지 전체나 일반 패널용 `management_scroll_style()`은 변경하지 않는다.
- **마스터 최종 정정(2026-11-21):** 기존에는 배송그룹 편성·주문내역이 스크롤바만 카드의 하단 16pt 패딩으로 연장했으나, 스크린샷에서 실제 행은 위에서 끝나고 레일만 아래로 이어지는 오류가 드러났다. **두 마스터 모두 `management_master_table_frame()`으로 상단·좌우 16pt, 하단 0pt를 적용하고 `management_master_table_card_min_inner_height()`로 표 본문 자체를 16pt 확장한다.** 공통 `management_table_scroll_track_rect()`에는 연장값 **0pt**를 넘긴다. 카드 외곽 크기는 유지한다.
- **일반 단일 목록:** 거래처 목록은 카드 1pt 내부 경계를 연장값으로 전달한다. 상품 목록은 빈 상태 안내를 위해 공간을 예약한 경우 0pt, 그 외에는 1pt를 전달한다.
- **Excel 관리:** 공장/매장 발송 대기 목록은 작성/폴더열기 푸터를 보호하므로 0pt, 이력의 상세/상태 메시지 또한 0pt를 사용한다. 하단에 다른 영역이 없는 이력 목록만 1pt를 사용한다.
- **운임관리 다른 표:** 그룹 운임표는 하단 빈 상태 메시지가 없는 경우 16pt, 메시지가 있으면 0pt. 조합·기준 이력은 복수 표이므로 0pt를 사용하고 기존 60% 스크롤 높이 제한을 유지한다.
- **일일 결산:** 여러 표·추가 카드가 이어지므로 0pt 연장, 기존 60% 높이 제한 유지.
- **범위:** 컨테이너 프레임·표 최소 너비·열 배분·행 높이·버튼·상태 메시지·업무 동작은 변경하지 않았다. 공통 트랙 Y좌표와 테이블 전용 스크롤바 스타일만 중앙화했다.
- **검증:** 정적 소스 대조 및 공통 좌표 함수의 소규모 기하 테스트 작성까지 완료했다. Cargo 테스트/Windows DPI 실화면 검수는 별도로 확인해야 한다.

## 2. 이미 공통을 사용하므로 레이아웃 변경하지 않은 영역

- **설정:** 상단 제목/탭/첫 카드 기준은 이미 공통 함수 사용. 설정은 세로 다중 카드와 입력폼 역할이어서 42pt 목록표를 강제할 대상이 아님.
- **거래처 → 자동 메시지 편집:** 기존 공통 탭, `section_frame`과 좌우 분리 편집 카드 사용. 독립 두 패널을 단일 표로 합치지 않음.
- **상품관리 내부 모델군/카테고리/별칭/브랜드:** 상품관리 상위 내비게이션과 외곽 기준을 상속하고, 개별 패널은 트리·폼·편집 도구 역할을 유지. 하위 편집 콤보박스를 목록용 필터 드롭다운으로 무차별 전환하지 않음.
- **발주서 상세/접수, 카카오톡 도킹, 그 밖의 비관리 화면:** 두 관리 마스터의 외곽 카드·열 너비를 강제하지 않음.

## 3. 코드 소유권 추가

- `components::management_list_table_header(ui,min_width)`: 기존 일반 관리 목록의 **36pt 고정 헤더와 데이터 가로폭**을 한곳에서 계산한다. **CONFLICT-003 A안 확정 후 실제 스크롤바 할당폭만 차감하고, 추가 4pt는 제거했다.** 내부 `management_table_data_width` 계산은 두 마스터의 헤더와 공유한다.
- `theme::management_weighted_columns`: 화면별 기본 열 폭과 남는 공간의 가중치 배분을 공통화한다.
- `theme::management_single_stretch_columns`: 남는 공간을 한 열에 집중하는 목록(상품, Excel, 결산)에서 위 배분 함수 재사용.
- `theme::MANAGEMENT_FILTER_DROPDOWN_WIDTH=148pt`: 마스터의 날짜 기준/상품 필터와 상품관리 브랜드 필터가 사용한다. **카테고리의 긴 경로는 기존 전용 280pt**를 유지.
- `management_dropdown_option`: 선택 직후 팝업 닫기 규칙을 유지하며 옵션의 `Response`를 노출해 카테고리 전체 경로 호버를 보존한다.

## 4. 사용자 결정이 필요한 충돌 (아직 수정하지 않음)

**CONFLICT-003 — 스크롤바 추가 여백 0pt 확정 (A안, 적용 완료)**
- **사용자 결정:** 관리 목록표의 추가 여백은 모두 0pt. 표 데이터 너비는 **뷰포트 폭 − 실제 스크롤바 할당폭**을 기본으로 계산한다(최소 표 너비 우선).
- **적용:** 거래처 목록, 상품 목록, Excel 대기/이력 표, 일일 결산 표, 운임 그룹 운임표와 조합·이전 기준 이력 표. 공통 `management_list_table_header`와 마스터의 `management_sticky_table_header`가 같은 `management_table_data_width`를 사용한다.
- **유지:** 최소 표 너비·열 분배·42pt 행·표 헤더 36pt·스크롤 자체는 변경하지 않는다. 스크롤바 트랙 상단 3pt 보정과 **현행 21pt** 도구줄→헤더 전환은 별개 계약이다. 추가 4pt 제거로 확보한 가로폭은 기존 화면별 잉여 폭 정책에 따라 분배된다.
- **검증:** 공통 함수와 사용 위치를 소스에서 확인했다. 실제 Windows 렌더링에서 헤더·데이터 끝점 및 스크롤바 트랙이 맞는지는 별도 검수해야 한다.

**CONFLICT-004 — A안 승인 및 목록 높이 코드 반영 완료 (2026-11-21)**
- **사용자 승인(2026-11-21):** 하나의 큰 목록이 중심인 화면에만 카드 내부의 남은 실제 높이를 최대한 할당한다. 여러 표·편집 패널이 이어지는 화면은 기존 높이 제한을 유지한다. 현재 `MANAGEMENT_TABLE_VIEWPORT_FRACTION=0.60`를 모든 화면에서 일괄 삭제하지 않는다.
- **기준 구현:** `freight_manager.rs::show_groups`는 이미 `card_inner_bottom = section.min_rect().top()+card_min_height`에서 본문 시작 `section.cursor().top()`을 빼 남은 높이를 계산한다. 새 적용 화면에서도 **실제 스크롤 영역 시작 Y**, 해당 카드의 아래쪽 경계, 그리고 표 뒤에 남겨야 할 요소를 기준으로 계산해야 한다.
- **적용 완료 1 — 거래처 관리/거래처 목록:** `management_list_frame`의 섹션 제목→검색/액션→고정 헤더를 유지하고, 이후 남은 카드 높이 전체를 단일 목록에 사용한다. 기존 60% 제한을 제거했으며 빈 검색 결과의 1개 자리표시 행을 유지한다.
- **적용 완료 2 — 운임관리/배송 그룹 관리:** 제목·그룹명 입력·추가 버튼 뒤의 단일 그룹 운임표에 카드 남은 높이를 사용한다. 그룹이 없으면 36pt를 예약해 하단 안내를 보호한다.
- **조건부 적용 완료 3 — 상품관리/상품 목록:** 상품 추가/Excel 패널과 검색·저장·로딩 상태줄 이후에 고정 헤더가 차지한 실측 높이를 빼고 목록을 확장한다. 등록 상품이 없고 로딩/오류 상태가 아닐 때는 안내용 36pt를 예약한다. 가격 수정 모드의 열 너비 및 가로 스크롤 동작은 유지한다.
- **조건부 적용 완료 4 — Excel 관리:** `ExcelTableHeightPolicy`를 도입했다. 공장/매장 대기에는 항상 **60pt**를 예약해 선택 건 Excel 작성·폴더 열기 푸터가 목록 아래에 유지되며, 빈 목록 안내에는 **36pt**를 추가 예약한다. 작성 이력도 빈 상태 메시지가 있으면 36pt를 예약한다. 선택 행 관리 편집이나 관련 주문 상세가 펼쳐지면 동적 콘텐츠가 가려지지 않도록 해당 표만 **기존 60% 상한**을 유지한다. 업무 동작은 변경하지 않았다.
- **A안 적용 제외 — 일일 결산:** `daily_settlement_manager.rs`는 페이지 전체 세로 스크롤 안에 주문 표, 입금 표, 추가 검토 카드가 순서대로 있다. 표마다 60% 상한을 유지한다.
- **A안 적용 제외 — 운임관리/조합·기준 이력:** 페이지 세로 스크롤 안에 여러 개의 카드와 펼침 이력 표가 있다. 표마다 기존 60% 상한을 유지한다.
- **A안 적용 제외 — 설정·자동 메시지·모델군 등 복합 편집 영역:** 설정 다중 카드, 자동 메시지 좌우 편집 패널, 모델군 목록+편집 패널은 단일 주 목록표가 아니다. 카테고리/별칭/브랜드 등의 트리·입력폼과 팝업도 이 60% 목록 상한을 사용하는 대상이 아니다.

## 5. 정적 검수와 한계

- 주요 파일의 공통 함수 호출·토큰 존재 확인. 4개 다른 관리 목록+운임 그룹/이력 테이블이 공통 헤더 함수를 사용.

- 전체 관리 UI가 Windows에서 완전히 동일하게 보이는지는 아직 확인할 수 없다. **CONFLICT-003·004·005는 승인 및 코드 반영 완료**했다. 상태 안내가 중간에 끼어드는 경로는 승인된 예외로 남겨두며 Windows 실제 렌더링 검수와 다중 DPI 검증은 별개다.
