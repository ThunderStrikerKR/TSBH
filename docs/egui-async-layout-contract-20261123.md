# 반도허브 egui 비동기 UI 레이아웃 불변 계약 — 설계수집 78차

> 적용 범위: `egui-app/src/`의 접수·상품·운임·거래처·주문 내역·Excel·결산·설정 UI. 기존 관리 UI SSOT(`docs/egui-management-ui-ssot.md`)에 종속되는 **비동기 상태 표현 규칙**이며, 새 디자인 숫자 원본을 만들지 않는다.
> 마지막 조사 기준: 2026-11-23. 코드 적용 여부와 Windows 실화면 확인을 분리해 관리한다.

## 핵심 불변식

1. 동일한 창 크기·DPI·선택 탭·데이터 개수에서 비동기 상태 `idle → loading → success/error`가 달라져도 **페이지 제목·하위 탭·KPI 바깥 Rect·도구줄·표 헤더·표 열·스크롤 레일·푸터 버튼**의 좌표와 크기를 변경하지 않는다. 임시 라벨, 추가 `ui.add_space`, Spinner/Frame을 기존 UI 앞에 삽입하지 않는다.
2. **본문 정보 자체는 바뀔 수 있다.** 새 상품·검색 결과·주문 상세 등 실제 데이터 행 개수/내용과 의도한 상세 펼침은 고정된 표/스크롤 뷰포트 *안*에서만 변한다. 이 변화를 전체 화면의 재배치로 오판하지 않는다.
3. **A. 성공·오류/검증:** `floating_notice` 또는 기존 승인 모달(작업 선택이 필요할 때)로 표시하며, 평상시 행을 추가하지 않는다. 필수 업무 오류를 단순 삭제하지 않는다.
4. **B. 진행 중:** 기존 작업 버튼을 **항상 동일한 라벨·최소 폭·높이**로 렌더링하고 `enabled=false` 등으로 잠근다. 진행 문구가 필요하면 기존 슬롯 안에 한정하거나 툴팁을 사용한다. 별도 '저장 중' 행을 생성하지 않는다.
5. **C. 빈 결과·초기 로딩:** `components::management_body_state_overlay(ui, viewport, caption)`로 **이미 할당한 본문 Rect에만 paint**한다. 상태에 따라 `management_single_list_scroll_height`의 reserve 값을 바꾸지 않는다.
6. **D. 초기 페이지 데이터 미준비:** 주 카드와 KPI가 명확한 관리 화면에서는 주 카드의 위치/폭/최소 높이를 먼저 확보한다. `management_pending_primary_card`는 기존 마스터 주 카드 자리만 예약한다. KPI는 `management_summary_card_value(...,"—")`로 값 미확정을 나타내며 **0건으로 위장하지 않는다**.
7. **E. 사용자 명시 작업:** 모달 열기, 펼침/접힘, 탭·카테고리 이동, 검색에 의한 실제 데이터 행 변경은 허용한다. 단 모달/드롭다운 자체는 별도 팝업 레이어 안에서 동작하고 부모 화면을 밀면 안 된다.
8. **표와 모달:** 전체 패널 높이가 아니라 개별 `ScrollArea`만 스크롤한다. 상태에 따라 헤더·레일 종료 좌표나 고정 버튼 위치를 수정하지 않는다. 카카오톡 도킹 영역 바깥의 가용 작업 영역을 사용한다.

## 검증 규칙

- Rust 단위 테스트: `components::management_async_layout_contract_tests`의 *상태 변경 전후 egui cursor 동일성*, 상품 목록의 본문 오버레이 사용, 일일 결산 KPI 슬롯 보존, 모델군 푸터 상시 렌더링을 검증한다.
- 주요 소비자에 대해 동일 데이터+화면 크기의 로딩 전/후 Rect를 수집하고 다음 차이가 **0.5 egui pt 이하**인지 검증한다: `title.min`, `toolbar.min`, `header.min`, `card.min`, `rail.min/max`, `footer button.center`. 반 픽셀 수준의 이미지 오차는 OS/DPI와 egui logical pt 차이를 구분한다.
- Windows 검수 조건: 1920×1080, 축소 창, 디스플레이 배율 변경; 검색 시작→취소→결과 도착, 빠른 연속 작업, 저장 성공·충돌·실패·재시도, 테이블 0건→다건, 카카오톡 연결/분리. 실제 좌표 로그 또는 전후 화면 캡처 없이는 '실화면 검증 완료'라고 하지 않는다.
- UI 회귀검증은 저장·권한·비동기 결과 순서·stale revision CAS·원본 수정 이력·송장/운임 비즈니스 로직을 변경하지 않고 수행한다.

## 남은 구조 개선 우선순위

1. **높음:** Windows 실제 화면에서 상품/운임/설정/자동메시지 초기 로딩과 실제 데이터 표시의 카드 `Rect`를 직접 비교. 소스 규격과 커서 불변 테스트만으로 완료 판정하지 않는다.
2. **중간:** 별칭 충돌 진단의 고정 세 번째 설명 슬롯과 설정의 복구 버튼 상단 고정 슬롯을 실제 좌표로 검증.
3. **중간:** 설명이 긴 필수 입력 검증은 모달 내부 고정 높이 또는 국소 스크롤로 제한.
4. **중간:** 카테고리 탐색기의 적용 버튼은 고정 너비 footer 및 오른쪽 정렬 슬롯으로 수정했다. 실제 `Rect` 기반 테스트와 Windows 화면을 통해 최종 확인할 것.

## 79차 추가 점검 — 거래처 태그와 주 사용 입금계좌

### 검색 태그 출처 확인

- 스크린샷의 `[TEST] 가상 거래처 01 · 표준형`은 `developer_ui_samples.rs`가 생성하는 합성 UI 테스트 거래처다.
- 테스트 원본:
  - `shortNames`: `가상01, 테스트거래처01`
  - `displayName`: `테스트 납품처 01`
  - `identifiers`: `UI-SAMPLE-C01`
- `client_names::normalize`는 과거 송장 상호 `displayName`을 기존 별칭 뒤에 `shortNames`로 이관한다.
- `client_search_tags::labels`는 `shortNames`를 먼저, `identifiers`를 다음에 원본 순서대로 표시한다.
- 따라서 화면의 네 태그 순서는 통폐합 과정에서 무작위로 섞인 것이 아니라 서로 다른 출처를 하나의 칩 목록에 합친 결과다. 업무 데이터를 삭제하거나 임의 정렬하지 않는다.
- 합성 테스트 거래처의 이관 후 정확한 태그 순서를 회귀 테스트로 고정했다.

### 주 사용 입금계좌 선택기 원인

- React `AccountPicker`와 설정 계좌 원본 스키마는 `{id, bank, number, holder}`다.
- 기존 egui 거래처 편집기는 존재하지 않는 `account.name`을 표시 라벨로 사용했다.
- 또한 완성되지 않은 계좌 레코드도 전부 선택지에 넣었다.
- 그 결과 계좌 행은 존재하지만 라벨이 빈 문자열로 렌더링되어 드롭다운에 `미지정`만 보이고 나머지는 빈 공간처럼 보일 수 있었다.

### 수정 사항

- 거래처 계좌 선택기는 React와 동일하게 `bank number holder`를 표시한다.
- 은행명·계좌번호·예금주가 모두 있고 ID가 유효한 계좌만 선택지로 노출한다.
- 계좌가 없더라도 `미지정 (상품군 추천 계좌 사용)` 선택지는 항상 제공한다.
- 선택값이 실제로 바뀐 경우에만 `preferredAccountId`를 수정한다. 목록에서 찾을 수 없는 기존 ID는 화면을 그리는 것만으로 자동 삭제하지 않는다.
