# BANDO HUB 전 화면 공통 UI 설계 계약 (2026-11-18)

> 사용자 확정 사항을 차수별 채팅이 아니라 **앱 소스 + 자동 검사**에 고정한다. 이 문서는 `AGENTS.md`와 함께 다음 세션에서 반드시 읽는다. 수치/색상 원본은 `src/ui/design-system.json`이며 `src/styles/tokens.css`의 `--ds-*`는 검증 가능한 CSS 투영이다.

## 범위와 상태

- 적용 범위: **접수·주문 내역·엑셀 관리·일일 결산·상품 관리·운임 관리·거래처 관리·설정** 및 그 아래 모든 탭, 표, 모달, 입력, 알림, 공통 상단 메뉴.
- **이 단계는 계약과 강제 검사를 설치하는 단계**이며 기존 화면의 실제 CSS를 일괄 치환한 것이 아니다. 화면별 반영은 사용자 지시 후 수행하고, 실제 Windows 스크린샷으로 검수해야 한다.
- 신규 UI 컨트롤이나 변경한 기존 컨트롤은 역할을 정하여 `data-ui-role`로 선언한다. 별도 `<Button variant="...">`는 사용 중인 공통 버튼의 변형을 유지할 수 있으나 신규/수정 시 의도를 명시한다.
- **정보 계층(메뉴 크기)과 업무 중요도(버튼 색상)는 서로 다른 축**이다. 하위 영역의 주요 작업 버튼도 Primary가 될 수 있지만 상위 네비게이션보다 메뉴처럼 커서는 안 된다.

- 버튼 높이와 글씨 대비 수직 여백 및 내부 정렬 기준 고정, 글자 수에 따라 **너비만 자연 증가**. 같은 행의 버튼 기준선 일치.
- 동일 레이블의 글씨 크기·모서리 반경·기본/호버/선택/비활성화 표현은 동일 역할에서 같아야 한다.
- **사용자 지정 밝은 작업 버튼:** 발주 원문의 `새 주문`, `대리발송`, `대리점 납품`, `직접 입력`, `캡처 범위 지정` 및 `카카오톡 연결`은 `action-emphasized`를 쓴다. 기본 표면 `#ffffff`, 글씨 `#171717`, 호버 `#70b4ff`이며, 파란색 호버는 선택 상태가 아니다. 키보드 포커스는 독립적인 외곽선이다. 다른 버튼·캡처 키캡·폴더 경로는 영향을 받지 않는다. 글씨 길이에 따른 버튼 너비와 34px 높이를 지킨다.
- 버튼 3개를 넣는다고 3개를 똑같이 강조하지 않는다. `action-quiet`은 주요 선택보다 시각적으로 작게 표시.
- **처리 중인 주문 원터치 버튼 미리보기 진입은 250ms**, 호버 해제 후 복귀는 260ms다. 발주 원문·수취인 연결 하이라이트는 **진입 200ms, 해제 250ms**를 적용한다.

## 3. 공통 컴포넌트와 색상

- 입력창: 36px 높이, 14px 본문, 6px 모서리; 필드 종류에 관계없이 동일 레이블 기준선과 좌우 시작점. 전화번호처럼 길이가 제한된 값은 **필요 이상 넓히지 않는다**.
- 표: 공통 헤더 13px/600, 행 13px, 헤더 최소 36px, 행 최소 42px. 금액 오른쪽 정렬 및 동일 자릿수 폭(tabular numerals). 스크롤은 표 내부에만.
- 카드: 패널 색 `#202020`, 반경 9px, 기본 패딩 16px. 제목·본문·하단 작업 행은 별개의 수직 리듬을 갖되 위아래 여백 균형 준수.
- 모달: 단일 레이어 정책, 제목 18px, 본문 14px, 동일 버튼 규격과 닫기 동작. 카카오톡보다 위에 표시.
- 툴바: 패널색, 8px 간격, 수평 12px·수직 8px 패딩. 검색·필터·작업은 같은 행에 논리적 그룹으로 배치.
- 알림: 13px, 단일 알림 센터. 업무 오류는 정보의 심각도에 맞는 색만 사용.
- 상태색: 기본 중립, **확인 필요 주황 `#f2ba64`**, 완료 초록 `#a9dab5`**, 오류/삭제 적색 `#ffb4b4`**, 선택·원문 연계 파란색 `#70b4ff`**. 장식만을 위한 상태색 금지.
- 거래처 등급은 도매(녹)·반도매(황)·소매(적)·특수(보라)의 기존 **의미와 색을 보존**하며 일반 오류색과 혼동하지 않도록 라벨 유지.
- 간격은 4·8·12·16·24px 계열만 원칙으로 사용. 모서리 규격은 컨트롤 6px / 패널·모달 9px. 화면 너비 예외는 근거와 실제 렌더링 증거가 있을 때만 허용.


## 3-A. 섹션별 테두리·구분선·정보 블록 역할 (2026-11-18 추가)

**규칙의 원본은 `src/ui/design-system.json`의 `structureRoles` 및 `colorRoles`다.** `src/styles/tokens.css`의 `--ds-structure-*`, `--ds-role-*`는 코드와 CI에서 값이 일치해야 하는 투영이다. 현재는 확정된 분류 기준이며, 접수·관리 화면의 기존 CSS를 일괄 변경했다는 의미가 아니다.

| 역할 | 쓰는 곳 | 테두리 / 배경 | 내부 여백 / 정보 배치 |
| --- | --- | --- | --- |
| `page-frame` | 화면 최상위 콘텐츠 | 외곽 테두리 없음 | 섹션 간 16px |
| `primary-section` | 발주 원문·관리 화면별 독립 업무 패널 | 일반 테두리 1px, 패널 배경, 9px 모서리 | 상하좌우 16px |
| `nested-section` | 주요 섹션 안의 하위 기능 | 은은한 테두리 1px, 한 단계 밝은 배경, 6px 모서리 | 상하좌우 12px |
| `field-group` | 레이블과 여러 입력창 | **불필요한 외곽 테두리 없음** | 필드 기준선 통일, 요소 간 8px |
| `record-card` | 주문·배송·거래처 반복 카드 | 테두리 1px, 패널 배경, 9px 모서리 | 상하좌우 12px |
| `information-block` | 주소·연락처·수량·금액 등 함께 읽을 데이터 | 은은한 테두리, 중립 배경, 6px 모서리 | 가로 12px / 세로 10px |
| `summary-strip` | 배송 건수·부가세·금액 한 줄 요약 | 추가 테두리·배경 없음 | 8px 간격, 금액 우측 정렬 |
| `toolbar-group` | 검색·필터·관리 버튼 한 묶음 | 은은한 외곽선 1px, 패널 배경 | 가로 12px / 세로 8px |
| `warning-block` | 사용자 확인이 필요한 업무 정보 | 경고색 테두리 + 저채도 경고 배경 | 이유와 해결 작업을 함께 표시 |
| `error-block` | 처리 실패·입력 오류 상세 | 오류색 테두리 + 저채도 오류 배경 | 오류 본문을 보조 글씨로 줄이지 않음 |
| `success-block` | 실제로 확인된 업무 완료 | 완료색 테두리 + 저채도 완료 배경 | 완료된 작업명 함께 표시 |
| `divider-soft` | 같은 섹션의 연속 항목 사이 | 옅은 1px 선, 별도 박스 없음 | 양쪽·상하 정렬 유지 |
| `divider-strong` | 성격이 다른 큰 항목의 경계 | 더 뚜렷한 1px 선, 별도 박스 없음 | 독립 섹션은 가능하면 공간+테두리로 분리 |

**이중 테두리 금지:** 이미 테두리로 둘러싸인 카드 안에서 같은 성격의 행마다 다시 테두리를 그리지 않는다. 동일 그룹은 구분선을 사용한다. 선택·호버 때문에 테두리 두께가 달라져 배치가 움찔거리면 안 된다.

**정보 블록화 규칙:** 입력값이 아니라 하나의 업무 정보 묶음인지 먼저 판단한다. 수취인 이름·주소·연락처는 관련 정보이므로 같은 정렬 체계를 적용하되, 개별 입력칸을 각각 카드로 만들지 않는다. 배송 건수·부가세·금액은 묶음으로 읽히되 금액은 오른쪽 정렬한다. 중요한 경고·오류만 의미 색상을 사용한다.

**색상 역할을 세 축으로 분리:** (1) 텍스트의 위계와 의미, (2) 표면/테두리의 목적, (3) 기본·호버·선택·포커스·비활성화 상태. 일반 검색창과 일반 입력창은 같은 `surface-input` 규칙을 쓰되 포커스 테두리와 선택 하이라이트는 별개다. 선택된 탭을 의미 없이 파랗게 칠하지 않으며, 발주 원문의 증거 연계 파란색과 키보드 포커스 색상을 혼동하지 않는다.

**새 기능 추가 시:** `structureRoles`에서 업무 의미에 맞는 구조 하나를 선택하고 `colorRoles`에서 색의 목적을 고른다. 새 RGB 값·선 굵기·패딩을 화면에 임의 추가하지 않는다. 현재 사용 중인 기존 스타일의 통합·삭제는 사용자가 재개를 지시한 후에만 수행한다.

## 4. 카카오톡 및 브랜드: 마지막 합의 우선

**카카오톡 보기 방식은 순환 구조가 아니다.** 카카오톡 패널 상단에 **세 개의 독립 버튼**을 배치한다.

1. `함께 보기` — OVERLAP 선택
2. `나누어 보기` — STACK 선택
3. `카카오톡 연결 해제` — 작은 보조 버튼, 연결된 외부 카카오톡 창 원상 복귀

세 버튼 모두 **전역 네비게이션이 아닌 카카오톡 패널의 컨텍스트 액션**이다. 선택 중인 보기 방식만 강조하고 클릭 시 그 모드로 직접 이동한다. 카카오톡 창은 앱 외부 Windows 창이므로, **조작용 헤더 공간을 native overlay_region에 포함시키지 않아야 버튼이 가려지지 않는다**. 연결하지 않은 상태에는 연결 버튼만 표시한다. 사용자가 다시 순환 방식을 요구하지 않는 한 단일 모드전환 버튼으로 합치지 않는다.

브랜드: B 심벌과 `BANDO HUB` 문구는 비슷한 **시각적 높이**로 맞추고, `/ 테스트`는 보조 레이블이다. 확인되지 않은 오른쪽 띠나 기능 없는 장식선은 추가하지 않는다.

## 5. 신규 기능 분류 순서 / 유지 검증

1. 전역 페이지인가? `nav-main` / 페이지 제목. 독립된 업무 기능 섹션인가? 섹션 제목. 페이지 안 탭인가? `nav-section` 또는 `nav-subsection`.
2. 클릭 가능한 작업인가? 완료/저장 `action-primary`, 일반 `action-standard`, 보조 `action-quiet`, 위험 `action-danger`, 아이콘 단독 `action-icon`.
3. 그 외는 input, table, card, modal, status, notification의 공통 역할에 배치.
4. 같은 역할에서 예외값이 필요하면 관련 폭·반응형 조건을 문서화하고 Windows **실제 스크린샷으로 비교**. 기존 화면을 스크린샷 없이 통과 처리하지 않는다.
5. `node scripts/check-ui-design.mjs`는 JSON↔CSS 토큰 동기화와 변경된 JSX 버튼의 신규 역할 부여를 검사한다. CI는 변경된 버튼에 `data-ui-role` 또는 공통 Button의 `variant`를 요구한다. 단, **이 검사는 실제 WebView2 시각적 균형을 증명하지 않는다**.
6. 점진적 이행: 기존 예외 CSS를 일괄 덮어쓰지 말고 화면별 차등 적용 후 제거. 8개 전 화면 및 모달·결산·Excel 표를 통과하기 전 **UI 통일 완료 선언 금지**.

## 접수 화면 원문 입력 영역 (2026-11-18 최신 사용자 승인)

- 상단 순서는 **발주 원문 제목 → 기존 대리점 정보(.source-top) → 원문 표시창(.source-document)**. 이 순서 및 거래처 표시·변경 기능은 변경하지 않는다.
- `＋ 새 주문` 버튼은 발주 원문 제목 오른쪽에 유지한다. 하단 메시지 패널과 영역 크기 조절 기능은 유지한다.
- 원문이 비었을 때에만 원문 표시창 내부에 **세 기능군**을 같은 왼쪽 기준선으로 정렬한다. ① 클립보드 접수: 대리발송 / 대리점 납품, 텍스트·이미지 인식 안내와 "이미지 캡처는 Ctrl + Shift + S 또는 Print Screen으로 복사하세요" 키캡 안내 ② 다른 방법으로 접수: 직접 입력 / 캡처 범위 지정(상시 구분되는 배경·테두리) ③ 폴더 자동 인식: 지정 경로가 있으면 경로를 클릭해 탐색기를 열고, 없으면 설정의 파일 관리에서 지정하라는 안내.
- 새 주문 포함 5개 접수 버튼은 내용에 맞춘 너비와 `action-emphasized` 높이 34px를 따른다. 가로 50:50 확장, 이중 카드 테두리, 임의 색상을 추가하지 않는다.
- 클립보드 이미지는 기존 PP-OCRv5와 검토창을 이용한다. 지정한 **발주 이미지 전용 폴더**의 새 PNG/JPG/BMP는 파일 안정화 뒤 OCR 처리하고 사용자가 검토 전에는 주문 원문을 변경하지 않는다. 공장 회신 Excel 폴더와 분리한다.
- 운영 설정 탭은 `기본 설정 / 파일 관리 / 데이터 관리 / 시스템` 4개다. 개발자 모드 탭과 패널은 숨기되 격리 시험 DB·Rust 검증 명령·테스트 소스는 유지하며, Windows 화면 검사 기준도 4개로 조정한다.
- 원문이 들어오면 입력 메뉴가 사라지고 기존 원문·하이라이트로 전환한다. 기존 주문 초안, OCR 취소·오류 및 수동 분류 흐름을 유지한다.
- 이것은 구현 계약이며 실제 Windows WebView2 렌더링의 시각 검증과 별개다.

## 처리 중인 주문: 원터치 호버 미리보기 (2026-11-18 사용자 승인)

- 원터치 단계 버튼은 업무 실행을 클릭으로만 처리한다. 호버는 **선택·주문 저장을 변경하지 않는 임시 미리보기**이며, 표시 시작은 250ms, 마우스를 떼었을 때 **260ms 후 복귀**한다. 다시 올리면 복귀 예약을 취소해 깜빡임을 줄인다.
- 원터치 버튼 호버는 기존 공통 토큰 `surface-emphasized-action-hover`의 파란색을 사용한다. 파란색을 실제 진행 완료/선택/오류로 오해하지 않도록 처리 상태와 구분한다.
- 배송 2건 이상인 발주서도 원터치 호버 시 **해당 주문 묶음의 수취인 배송 목록 전체를 임시로 펼친다.** 다른 묶음은 잠시 접고, 호버 해제 후 원래 선택된 묶음의 접힘/펼침 상태를 복원한다.
- 원문·상세정보에 실제로 표시 중인 배송 건은 우측 목록에서 **파란색 강조 및 '표시 중'** 텍스트로 분명히 식별한다. 다른 배송 건은 목록에 남겨두되 임의로 선택·수정·저장하지 않는다.
- 250ms 진입 지연, 다중 수취인 결정 규칙(`hoveredWorkflowSelection`), 선택 상태 및 Rust 업무 명령은 유지한다. 타이머는 컴포넌트 언마운트 시 해제한다.

## 발주 원문·수취인 연결 호버 안정화 (2026-11-18)

- 발주 원문·수취인·상품의 연결 하이라이트는 **마우스 진입 200ms 후 표시**하고, 마우스 해제 **250ms 후** 강조를 해제한다. 200ms 전에 스쳐 지나가면 강조하지 않는다. 다른 연결 항목에 들어가면 기존 진입·해제 예약을 취소한다. 키보드 포커스와 명시적인 선택은 즉시 처리한다.
- 호버는 주문 선택을 확정하지 않고 연결된 배송 건의 화면을 **임시로만 보여준다**. 사용자의 실제 선택 상태나 Rust/SQLite 업무 데이터는 바꾸지 않는다.
- 새 주문 또는 컴포넌트 종료 시 타이머를 정리하고 키보드 포커스·명시적인 클릭과 구분한다.
