# BANDO HUB — egui UI 재구축 1단계

현재 `main`에 존재하는 **독립 실행 UI 골격**이다. 사용자가 제공한 2026-11-19 React 접수 캡처와 `docs/egui-ui-design-contract.md`를 기준으로 한다.

## 실행

Rust toolchain 설치 환경에서 저장소 루트 기준:

```powershell
cargo run --manifest-path egui-app/Cargo.toml
```

이 실행파일은 기존 React/Tauri 운영 앱을 대체하지 않는다. egui 전용 SQLite에 **미확정 접수 작업본과 개발용 거래처 마스터를 별도 테이블로 저장**하며 운영 주문·결제·공장 기록을 임의로 변경하지 않는다. 실제 Tauri 거래처 DB 또는 내보낸 인덱스를 연결하면 **읽기 전용**으로만 표시한다. Windows 컴파일·실행 및 실화면 검증은 별도로 판정한다.

## 구현된 UI 기반

- 역할별 테마 토큰(다크 색상, 글꼴·간격·모서리·버튼 스타일), Windows 한글 폰트 로딩
- 전역 8개 탭과 카카오톡 / 발주원문·복사용 자동 메시지 / 확인·수취인·품목 / 처리 중인 주문의 4열 레이아웃
- 네비게이션 전환, 독립적 카카오톡·주문 목록 측면 패널 크기 조절, 빈 발주원문 표시
- 기존 React에 없는 샘플 모드·가짜 주문·개발 안내문을 화면에 표시하지 않는다. 실제 연결 전 원본 버튼은 비활성으로 유지한다.


## 2단계: 드래그 분할과 프레임리스 창

- **가로 4열**: 기존 React 1920×1080 기준 화면 실측 비율 `20.9 / 28.4 / 28.3 / 22.4`, 각 열 최소폭 `200 / 250 / 250 / 350`pt, 열 사이 6pt 드래그 핸들. 마지막 열 최소폭 420pt가 기준 비율을 강제로 바꾸던 문제를 수정했다. 양쪽 이웃 열만 크기가 바뀌고 나머지 열은 폭을 유지한다.
- **세로 분할**: 발주원문/복사용 자동 메시지 사이에 6pt 드래그 핸들, 최소 높이 275/160, 더블클릭으로 50:50 초기화.
- **리셋**: 가로 핸들 더블클릭은 4열 기본 비율 전체 복원, 세로 핸들 더블클릭은 원문/메시지 50:50 복원.
- **저장 위치**: Windows `%LOCALAPPDATA%\BANDO-HUB-egui-preview\layout.txt` (그 외 `~/.config/bando-hub-egui-preview/layout.txt`). 실운영 SQLite/React 설정과 절대 공유하지 않는다.
- **작은 창**: 패널 최소 폭의 합을 유지하고 가로 스크롤로 접근한다. 본문 폰트를 임의 축소하지 않는다.
- **기본 Windows 제목표시줄 숨김**: `ViewportBuilder::with_decorations(false)`. 로고 이미지와 BANDO HUB 글자는 **정적 표시만** 하며 호버·클릭·드래그·더블클릭 동작이 없다. 상단 헤더의 **빈 공간**만 드래그로 창 이동, 더블클릭으로 최대화·복원한다. 오른쪽 최소화·최대화/복원·닫기 버튼은 기존 업무 헤더의 순서와 동작을 따른다.
- **창 가장자리 크기 조절**: 각 방향 및 모서리 6pt 영역에서 네이티브 resize 명령을 보낸다.

### 검증 상태

GitHub `main`에는 소스 코드가 반영되었지만 이 환경에서 `cargo check`/Windows 실행, DPI 동작, 저장 복구, 실화면 캡처를 확인하지 못했다. **실사용 성공으로 판정하지 않는다.** 입력 버튼과 주문 업무는 여전히 비활성화된 별도 UI 프리뷰다.

### 다음 확인 지점

`DEV_WINDOWS_EGUI.cmd`를 실행하면 나타나는 별도 UI에서 창 이동·최대화·최소화·닫기, 가장자리 크기 조절, 4열 핸들, 원문/메시지 핸들, 더블클릭 초기화와 재실행 뒤 분할 비율 유지 여부를 확인한다.

## 현재 의도적으로 미구현

- React/Tauri 교체, 운영 주문 저장·승인·이력 결산, 원문 연결 하이라이트, 카카오톡 창 실제 도킹. egui 격리 SQLite에 여러 미확정 접수/분석 근거를 자동저장하며, 운영 DB는 명시적 읽기 전용 거래처 명단 조회를 제외하고 연동하지 않음
- 중앙 2열을 포함한 가로/세로 핸들 구현은 2단계 소스에 반영. 주문 카드 실사용 편집, 나머지 7개 화면의 전체 기능은 미구현
- Windows 실제 DPI와 색·글자 높이 대조

## 보호 대상

`backup/main-before-egui-20261119`를 수정하지 않는다. 운영 DB/설정/실행파일 백업은 Git 브랜치와 별도로 필요하다.

## 3단계: 공통 업무 위젯 (2026-11-19)

`src/components.rs`에 기존 React UI 계약을 기준으로 다음 공통 역할을 추가했다.

- `FieldKind` + `field` + `labeled_field`: Text, Telephone, Quantity, Money, Address 입력값 크기와 높이 및 공통 레이블
- `record_card`: 주문 및 반복 업무 카드의 패널·반경·패딩 통일
- `table_header` + `table_row`: 공통 13pt 글씨, 36pt 헤더와 42pt 행, 공통 구분선
- `status_dots`: 활성/완료/주의/오류/원문 연결에 해당하는 색상 역할
- `summary_strip`: 금액 오른쪽 정렬 및 배송/부가세 보조 정보
- `soft_divider`: 내부 데이터 목록에만 사용되는 단일 얇은 구분선

공통 위젯은 수취인 정보·품목 목록·요약 영역에 적용한다. 가짜 주문 카드와 가상 데이터는 화면에서 제거했다.

동시에 `layout.rs`에서 여러 패널이 최소폭에 걸릴 때 남는 공간이 버려질 수 있었던 비율 계산 오류를 수정했다. `theme.rs`의 역할별 버튼 글씨 크기, 16pt 주요 섹션 내부 패딩도 기존 계약에 맞춰 정리했다.

**검증 구분**: GitHub 코드 반영 및 소스 참조 확인만 완료. 실제 Windows `cargo check`, 컴파일, 창 이동·드래그·DPI·스크린샷 시각 비교는 아직 완료되지 않았다. 어떤 UI도 운영 DB에 연결되지 않았다.


## 4단계: React 밀도 미세 조정 + 실제 Rust 인식 엔진의 초기 연결

- 공통 다크 테마 역할은 유지하면서 **섹션 안쪽 여백 10pt**, **카드 여백 10pt**, **공통 입력창 높이 34pt**, **레이블 폭 68pt**로 정리했다. 섹션 제목의 높이, 제목 아래 구분선, 입력창 간 기본 간격은 공통 토큰을 사용한다.
- 직접 입력 버튼으로 원문 편집을 열고 발주서 텍스트를 수정하면 자동으로 인식 작업이 실행되며, `egui-app/src/reception_service.rs`가 `BandoGateway`를 통해 기존 Rust 인식 구현을 사용한다. 로컬 Gateway에서는 원본 `src-tauri` 업무 코드를 그대로 재사용한다. TypeScript 분석이나 흉내 낸 제품 인식 로직은 없다.
- 분석은 백그라운드 Rust 스레드에서 실행한다. 원문을 수정하면 이전 결과를 무효화하고 약 250ms 후 자동 분석한다. 응답 순서가 뒤바뀌면 오래된 결과를 반영하지 않는다.
- 인식된 배송 건(수취인), 이름·주소·전화·요청 메시지, 인식된 상품·수량과 Rust가 반환한 검토 후보 수를 표시한다. 여러 수취인 사이를 전환하면 품목 목록도 같은 프레임에서 전환한다.
- 이 단계의 카탈로그는 **배포 소스에 포함된 기본 `state-seed.json`** 이다. 실제 운영 DB의 최근 상품·거래처 데이터가 아니며, 이 점을 안내한다. 카탈로그 JSON 파싱 결과는 한 번만 캐시한다.
- 실제 주문 금액·운임·부가세·상태를 UI가 임의 계산하거나 표시하지 않는다. 가상 자료·샘플 전환 UI는 삭제했다.

**기능 제한:** 실제 Rust 업무 엔진 연결 중 **원문 인식만** 수행했다. 기존 Rust 상품·거래처 변경, 단가, 운임, 작업 단계, 메시지, 이력·결산, SQLite 영속화, 카카오톡 창 연결은 아직 이 egui 바이너리의 실사용 경로에 연결되지 않았다. 전환이 검증되기 전까지 기존 React+Tauri 운영판을 삭제하지 않는다.

**검증 상태:** GitHub 소스 변경은 확인했다. 로컬 Windows에서의 `cargo check`, `cargo run`, DPI·분할선·프레임리스 창·실제 발주원문 동작을 이 환경에서 실행 검증한 것은 아니므로 성공을 주장하지 않는다. 과거의 빌드 실패 화면만으로 신규 커밋의 빌드 성공을 추정하지 않는다.


## 5단계: 기존 Rust 가격·도서산간 규칙의 읽기 전용 연결

- `reception_service.rs`는 Gateway 인터페이스만 참조한다. **LocalGateway**가 기존 `src-tauri/src/business_core/rules/mod.rs`를 재사용한다. **TypeScript 계산이나 유사 규칙 재작성 없이** `resolve_unit_price`와 `detect_remote_delivery_area`를 호출한다.
- 가격: 분석에서 등록 상품 ID와 옵션 ID가 모두 확정된 항목만 **내장 상품 시드의 소매 등급 참고 단가**를 표시한다. 상품 시드 360개, 거래처 시드 0개. 내부적으로 Rust 규칙이 요구하는 비영구 가상 소매 등급 ID로 조회하지만, 주문 거래처로 사용하지 않고 결제 금액에 포함하지 않는다. 값이 없으면 미등록/확인 필요로 남긴다. **도매·반도매·특수 단가, VAT, 청구금액은 계산하지 않는다.**
- 배송지: 인식된 주소를 Rust 도서산간 판정 규칙에 전달한다. 자동 체크 권장 / 직원 검토 필요 / 자동 판정 없음으로 표시한다. '자동 판정 없음'은 일반 지역 확정이 아니며, 실제 운임 배수나 수취인 저장 상태를 변경하지 않는다.
- 두 참고 결과는 기존 백그라운드 인식 작업에서 한 번 계산하고 수취인·상품 단위로 보관한다. UI 프레임마다 규칙을 재실행하지 않는다.
- `chrono`·`unicode-normalization`은 재사용하는 순수 Rust 규칙 모듈의 기존 의존성이다. Tauri 및 SQLite 커맨드 의존성을 egui 프리뷰에 포함하지 않았다.

**검증 한계:** 현재 도구 환경에 Rust compiler/Cargo가 없어 새 소스를 실제 Windows에서 컴파일·시각 검증하지 못했다. 이 변경은 GitHub 코드 반영 상태이며, 빌드 통과 또는 운영 투입 완료 판정이 아니다. 가격·운임의 실사용 계산은 거래처/할인/운임 저장 데이터를 갖춘 **독립 테스트 DB를 연결한 이후** 진행해야 한다. React/Tauri 운영용 파일과 기존 복구 브랜치는 유지한다.

## 6단계: 공통 BandoGateway 호출 계층 (2026-11-19)

기존 egui -> native_engine -> Rust 알고리즘 직접 호출을 **egui UI -> reception_service -> BandoGateway -> LocalGateway 또는 HttpGateway**로 바꿨다.

- `src/main.rs`: Gateway 인스턴스 생성·주입, 백그라운드 분석 결과만 수신. HTTP/SQL/Rust 비즈니스 모듈 직접 참조 없음
- `src/reception_service.rs`: 인식·수취인·가격 참고·도서산간 참고 결과 조합. 비즈니스 판단을 재작성하지 않음
- `src/gateway.rs`: 공통 trait과 명시적으로 제한된 읽기 전용 operation, 기존 Rust recognition/rules를 사용하는 LocalGateway
- `src/http_gateway.rs`: **명시적 선택 시에만** Bearer 인증된 HTTPS JSON API 호출. 서버는 아직 구축하지 않았음
- `API-CONTRACT.md`: HTTP 요청·응답·보안·서버 구현 조건 명시
- 카탈로그 조회는 상품·별칭·브랜드로 제한한다. 주문 내역·거래처 개인정보 전체를 첫 조회에 포함하지 않는다.

실행 환경변수 미설정이면 기본값은 **로컬 Rust + 내장 상품 시드**이고 서버 통신은 발생하지 않는다. `BANDO_HUB_GATEWAY=http`를 선택한 경우에만 `BANDO_HUB_API_BASE_URL`과 `BANDO_HUB_API_TOKEN`이 필요하다. 서버 연결 오류가 생겨도 **암묵적으로 로컬 결과로 대체하지 않는다.**

기존 React/Tauri/실운영 SQLite의 변경은 없으며, egui 바이너리에는 아직 주문 저장·승인·거래처 권한 관리가 없다. 서버의 실제 인증·라우터·거래처/주문 동기화 구현도 없다.

**빌드 상태:** GitHub 소스 구조 및 호출 참조만 확인했다. 현재 도구 환경에 Rust compiler/Cargo가 없어 Windows `cargo check`나 실제 UI 동작을 확인했다고 주장하지 않는다. 기존 전체 회귀 테스트를 새로 실행하지 않았다.

## 7단계: 격리 SQLite + 편집 원문 자동저장

- 로컬 실행 시 `LocalGateway`가 `PreviewStore::initialize()`로 **전용 SQLite**를 만든다. Windows 경로: `%LOCALAPPDATA%\\BANDO-HUB-egui-preview\\egui-preview.sqlite3`. SQLite WAL, `preview_meta` 식별자 확인, 읽기 전용 카탈로그 시드가 있다.
- 파일이 이미 있는데 PreviewStore의 식별자가 아니면 **재설정·덮어쓰기·운영 DB 자동 가져오기 없이 오류 종료**한다.
- **카탈로그:** `catalog_snapshot`에 빌드 내장 상품·별칭·브랜드가 저장된다. 현재 egui가 운영 DB의 최신 재고/거래처를 읽는 것은 아니다. 서버 모드에서는 `GET /api/v1/catalog`을 대신 사용하도록 인터페이스가 분리돼 있다.
- **원문:** `working_source`에 프리뷰 편집기의 원문·접수 유형·revision과 독립 ID를 가진 여러 미확정 발주서 목록(`drafts_json`), 현재 선택 ID(`active_id`)를 저장한다. 별도 작업 스레드에서 180ms debounce, 최신 스냅샷을 한 트랜잭션으로 저장, 중복 실행 충돌 시 revision 검사, 종료 시 대기 저장 마무리.
- **안전:** 위 테이블은 접수 중인 실제 주문·배송·결제 상태와 무관하다. 실제 반도허브의 `reception_working_orders`, `app_state`, `core_*` 등을 직접 가져오거나 수정하지 않는다. `+ 새 주문`은 egui 격리 저장소에 새 미확정 원문 ID만 생성하고, 운영 주문 확정이나 송장 전달은 수행하지 않는다.
- `BandoGateway`의 `load_working_source`와 `save_working_source`에 동일한 revision 계약을 만들고 `HttpGateway`에도 `GET/PUT /api/v1/working-source` 클라이언트를 추가했다. **서버 라우트 자체는 아직 구현되지 않았다.**

**검증 상태:** GitHub 소스 반영/정적 호출 확인만 수행했다. Rust toolchain이 없는 실행 환경이므로 Windows `cargo check` 성공이나 DB 생성·재시작 복원의 실제 동작은 아직 확인되지 않았다. 운영용 React·Tauri 파일과 원본 백업 브랜치는 그대로 유지한다.

## 6px 분할 영역 중앙 정렬 (2026-11-19)

사용자가 제공한 경계 확대 캡처 `image(20261119-124029).png`에서 6px 세로 조작 영역은 사진 기준 x=27..32였지만 표시선은 x=30에만 있어 오른쪽으로 한 픽셀 치우쳐 보였다. 동시에 가로선은 인접 세로 분할바의 **중앙선까지 이어지지 않고 패널 경계에서 중단**됐다.

- **실제 픽셀 대칭:** 짝수 개의 물리 픽셀(예: 6px)로 이루어진 분할 영역에서는 중앙이 두 픽셀 사이에 있으므로 평상시 가운데 두 픽셀(예: x=29..30)을 사용한다. 홀수 픽셀 분할 영역에서는 가운데 한 픽셀을 사용한다. 호버 때는 공통 2pt 두께 토큰과 강조 색상을 사용하되, 6px 구간에서는 대칭을 위해 평소와 같은 중앙 2px을 유지한다. 별도의 UI 설명이나 버튼은 추가하지 않는다.
- **교차점:** `reception()`의 공통 작업 영역 좌표를 기준으로 2열 가운데 가로선, 3열 위쪽·가운데 가로선을 인접 **세로 분할선의 중심**까지 이어 그린다. 세로선은 마지막에 다시 그려 T자 접합부를 끊김 없이 보인다.
- **단일 기준 계산:** 높이는 이미 공통화한 `LayoutState::vertical_heights()` 및 `detail_upper_heights()`에서 계산해 두 열의 실제 구분선을 같은 Y 좌표로 배치한다. 패널 너비, 분할바 6pt 조작영역, 기존 드래그/저장 기능은 수정하지 않았다.
- **검증:** 확대 캡처 픽셀 확인 및 GitHub 소스 수준 정적 검토만 수행했다. Windows 재실행 캡처나 Rust 컴파일 성공은 아직 확인하지 못했다.

- **기능 이전 시 규칙**: 업무 데이터 표시·인식·운임·가격·카카오톡 구현은 `LayoutState`의 비율·최소폭·경계 좌표를 임의 변경하지 않는다. 화면 내용은 사전에 고정된 pane Rect와 clip 안에서만 갱신한다. 레이아웃 변경이 필요하다면 기준 캡처와 차이를 정량 비교하고 별도 승인 후 적용한다.
- `layout.rs`에 화면 비율, 저장된 사용자 비율, 가운데 두 열의 경계 일치를 확인하는 **작은 geometry-contract 테스트 3개**를 두었다. 외부 CI·전체 회귀 테스트는 추가하거나 실행하지 않았다. 테스트 코드는 작성했지만 이 실행 환경에서 Cargo/Rust 컴파일을 수행하지 못했다.
- 1920×1080보다 작은 창에서는 최소폭과 가로 스크롤로 인해 **보이는 비율이 달라질 수 있다**. 이는 내용 손실을 막기 위한 기존 최소 크기 정책이며, 기존 기준 화면과 같은 비율을 보장한다는 뜻은 아니다.

## 접수 편집기 영역 보호 및 변경 충돌 처리 (2026-11-19)

사용자 확정 원칙은 Layout 비율 고정, Typography 3계열 유지, Theme/Components 재사용, Gateway/Service의 기존 Rust 판단 재사용, 승인 없는 UI 기능/문구 추가 금지, **원칙 충돌 시 임의 타협·구현 금지와 사용자 질문**의 6가지다. 상세 계약은 `docs/egui-ui-design-contract.md` 17절을 따른다.

- 수정 전: 발주원문 입력창은 `ui.available_height()`에 `.max(120.0)`을 적용해 고정된 원문 섹션의 본문 공간이 부족하더라도 높이를 추가 요구할 수 있었다.
- 수정 후: `components::docked_section_body_height(height)`에서 고정 패딩·제목·구분선·상하 간격을 제외한 본문 예산을 계산한다. 실제 `ui.available_height()`와 비교해 더 작은 높이만 사용한다.
- 발주원문은 기존 `source_rect` 내부에서 별도 clip과 최대 높이의 세로 스크롤 영역으로 한정한다. 긴 텍스트를 입력해도 입력 영역이 아래 `복사용 자동 메시지` 패널 위로 자라나지 않도록 구성한다.
- 아래 자동 메시지의 빈 메시지 영역 역시 `.max(48.0)` 강제 확장을 제거하고 버튼 높이 및 간격을 먼저 남겨둔다. 자동 메시지의 내용·복사 기능은 변경하지 않았다.
- **변경하지 않은 것:** 4열 비율, 수직 분할의 비율/드래그/저장, 헤더 높이, 타이포그래피, 카카오톡, 원문 자동저장·분석 호출·입력 전환, 기존 버튼과 문구, Rust 업무 로직 및 운영 DB.
- **상태:** GitHub 소스 수준에서 수정 범위·호출 경로를 대조했다. Windows 실제 빌드·실화면에서 경계 및 스크롤 검증을 수행하지 못했으므로 시각적 완료로 판정하지 않는다. 긴 원문, 최소 원문 높이 및 수직 분할 드래그 상태의 실사용 검증이 남아 있다.

## 클립보드 접수 기능과 헤더 정렬 개선 (2026-11-19)

- 상단 38pt 로고와 34pt BANDO HUB 워드마크는 높이 62pt의 동일 슬롯 중심에 직접 그린다. 이미지 투명 여백과 글꼴의 좌측 여백을 상쇄하기 위해 캔버스 간격을 **-4pt 광학 오버랩**으로 좁혀 한 세트처럼 보이게 한다. 오른쪽 창 제어는 32pt 동일 크기 영역에서 공통 벡터 아이콘을 그린다.
- egui `clipboard_intake.rs`: 시스템 클립보드에 비어 있지 않은 텍스트 또는 이미지가 있을 때만 `대리발송`/`대리점 납품`을 활성화한다. 버튼을 누르면 클립보드를 실제로 읽고 `AGENCY`/`DEALER` 유형을 적용한다.
- 텍스트는 기존 `ReceptionService` → `BandoGateway` → Rust 분석으로 전달하며, 원문과 접수 유형을 격리 SQLite의 단일 활성 작업 원문에 revision 비교로 자동저장한다. 기존 데이터는 삭제 없이 `order_type` 열을 추가한다.
- 이미지는 기존 `src-tauri/resources/ocr/recognize.py`와 PP-OCRv5 한글 모델을 사용하는 별도 작업 스레드에서 인식한다. `OCR 처리 중…`과 기존 `취소` 동작을 표시하고 취소 시 OCR 자식 프로세스를 중단한다. 사용자에게 기존 `OCR 문자 인식 검토`를 보여주고, 수정 및 `원문에 추가`/`원문 교체`를 승인하기 전에는 원문·DB를 수정하지 않는다. 추가는 기존 원문에 이어 붙이며 불필요한 교체 확인을 하지 않고, 교체만 원문이 달라질 때 확인한다.
- 이미지 OCR 런타임은 egui 실행파일 옆 `ocr/runtime/python.exe` 및 `ocr/models`를 사용한다. 기존 다른 OCR 배포의 런타임이 있는 경우 `BANDO_OCR_RUNTIME_DIR`로 그 `ocr` 폴더의 절대 경로를 지정할 수 있다. 외부 PATH·시스템 Python으로 무단 폴백하지 않는다. 런타임이 없으면 기존 `알림`에 실제 오류를 표시한다.
- 저장하지 않은 새 OCR 검토 문구를 버리려면 기존 확인 절차를 거친다. 이미 입력한 원문을 다른 내용으로 바꾸는 작업도 확인을 거친다.
- **적용 범위 주의:** 현재는 egui 프리뷰에서 복수 발주원문을 독립적으로 자동저장·선택하고, 선택한 원문을 Rust 인식 엔진으로 분석할 수 있다. 거래처/카카오톡 매칭·실운영 업무 처리 상태·수취인 수동 분류·영구 주문 확인 및 공장 전송을 완료한 것이 아니다.
- **검증 미완료:** GitHub 코드 연결 경로만 확인했다. 이 환경에서 Windows Cargo 컴파일·로고 실제 위치·클립보드 이미지 OCR 성공은 확인하지 못했다.

## 복수 미확정 발주서 수신 이전 (2026-11-20)

- `+ 새 주문`: 이미 빈 발주서를 선택했다면 중복 생성하지 않고 접수 선택 화면을 유지한다. 기존 발주서에 내용이 있으면 독립 ID를 가진 새 접수를 만든다.
- `처리 중인 주문`: 격리 저장소의 미확정 원문만 나열한다. 목록에서 다른 항목을 선택해 원문을 열고 Rust 재분석을 시작한다. 운영 주문 목록·결제 단계가 아님을 구분한다.
- 기존 `working_source.raw`는 원본 데이터를 삭제하지 않고 `legacy-working-source` 식별자로 승계한다. 다음 수정 시 `drafts_json` 목록과 선택 상태를 동일 SQLite 트랜잭션에서 저장한다.
- `BandoGateway`의 revision-checked 저장 계약이 전체 접수 목록을 받아 저장하도록 바뀌었다. 미래 서버에는 `activeId` 및 `drafts`를 함께 구현해야 하고, 서버 구현 전에는 HTTP 모드를 실제 운영에 사용하지 않는다.
- Windows 실제 빌드·GUI 동작 검증은 아직 수행하지 않았다. 기존 React/Tauri 운영 데이터베이스는 이번 변경 대상에서 제외했다.

## 거래처 자동 매칭 및 발주서별 Rust 근거 연결 (2026-11-20)

- 접수 분석 서비스가 기존 Rust `catalog_clients/title_clients.rs`의 `auto_match_reception_client`, `reception_client_candidates`를 호출한다. egui 화면에 별도 업체명 매칭 로직을 구현하지 않는다.
- 거래처 이름 인덱스는 opt-in `BANDO_EGUI_CLIENT_INDEX` JSON 파일 또는 `BANDO_EGUI_BUSINESS_DB` 경로의 Tauri 관계형 SQLite를 **읽기 전용**으로 조회해 생성하며, 배송·연락처·가격 정보는 프리뷰 DB에 저장하지 않는다. 프로젝트 내장 시드에는 거래처가 0건이므로 연결하지 않으면 자동 인식은 대기 상태다.
- 접수마다 원문에 결합된 `analysisRaw`, `analysisEvidence`, `clientMatch`를 저장한다. 입력이 바뀌면 이전 근거를 무효화하고 분석 완료 응답이 현재 선택 접수에만 붙도록 보장한다.
- `확인할 내용`에는 거래처 명단 미연결, 자동 인식된 거래처, 매칭 충돌 또는 직접 확인 필요 상태를 표시한다. 단순 수취인 주소/학교를 발주 거래처로 간주하지 않는다.
- 이 단계의 기록 당시에는 카카오톡 대화창 제목/HWND 조회만 구현되어 있었다. 49차에서는 별도 Win32 도킹 어댑터를 추가했다. 대화 메시지 수집은 하지 않으며 기존 4열/패널 비율은 유지한다.
- GitHub 코드 업데이트만 완료했다. Windows Cargo 컴파일 및 실제 GUI 동작 검증은 아직 수행하지 않았다.

## 카카오톡 대화창 확인 및 거래처 미확정 적용 (2026-11-20)

- Windows에서는 `KakaoTalk.exe`의 검증된 창 제목과 HWND를 이용한다. 발주처 확인은 원문 접수 시 별도로 판단하며, 카카오톡 메시지 자체를 감시·수집하지 않는다. 49차 도킹 기능은 검증된 카카오톡 창의 화면 위치와 표시 순서를 변경하고 해제 시 복구한다.
- **49차 수정:** 기존 `카카오톡 연결` 영역의 `카카오톡 대화 선택` 목록과 안내 문구는 승인되지 않은 중간 UI라 제거했다. 연결 버튼을 눌렀다는 이유로 발주처를 확정하지 않는다. 발주 원문 접수 시점에 최근 실제 포커스된 검증 대화창 제목(없으면 유일하게 열린 검증 대화창)을 후보 근거로 사용하며, 다중 대화창이 모호하면 임의 선택하지 않는다. 미확정/충돌/수동 정정은 접수 화면의 기존 거래처 찾기·변경 UI에서 처리한다. 49차에 실제 Win32 연결을 추가한 뒤 React `HubShell`의 함께 보기·나누어 보기·카카오톡 연결 해제 버튼을 동일한 위치에 이전했다. Windows 실화면 검증은 Issue #42의 후속 범위다.
- 클립보드 텍스트·OCR 이미지 접수 시작 시 확인한 대화 정보를 접수 승인 단계까지 유지한다. 수동으로 대화를 선택하거나 원문을 변경하면 해당 주문의 Rust 분석 근거를 다시 계산한다.
- Rust 고유 매칭 결과는 격리 발주서의 `clientId`와 `clientSelection=AUTO`로 저장한다. 후보 버튼을 직원이 선택하면 `MANUAL`로 보존하고 Rust 인식을 재실행한다. 미확정 주문의 거래처 ID일 뿐, Tauri 운영 주문의 거래처·가격·송장 정보는 수정하지 않는다.
- 실제 Tauri DB 거래처 명단을 사용하려면 실행 전에 환경변수 `BANDO_EGUI_BUSINESS_DB`에 `bando-hub-v001.sqlite`의 정확한 파일 경로를 지정한다. `SQLITE_OPEN_READ_ONLY` 및 `PRAGMA query_only=ON`으로 읽는다. DB 버전 2가 아니면 변경이나 마이그레이션을 하지 않고 오류를 표시한다. 명시하지 않으면 기존 JSON 인덱스를 쓰거나 빈 명단을 사용한다.
- 기존 4열 레이아웃·업무 상태 전환·영구 주문 DB는 변경하지 않았다. Rust 컴파일/Windows 동작 확인은 아직 미완료다. 별도 전수 회귀 테스트는 실행하지 않았다.

## 거래처 전체 검색 1단계: 격리 접수 수동 선택 (2026-11-20)

- React 원본 `ClientChooser`의 `거래처 변경` UX를 따라 발주원문 제목 아래 82pt 거래처 영역에 `거래처 찾기`/`변경` 버튼을 연결했다.
- Tauri의 원본 Rust `catalog_clients/queries.rs::client_search`를 공유 `client_search.rs`로 추출했다. 상호·표시명·별칭·주소·전화번호·휴대전화·거래처 식별자를 공백/대소문자 무시로 검색하며 삭제 거래처를 제외한다.
- 검색 전체 목록과 검색 결과는 egui 모달에서 표시된다. 거래처 명단 로딩 및 검색은 UI 스레드 밖에서 수행하며, 주문을 바꾸면 열려 있던 검색창을 닫는다.
- 검색 과정에서 가져온 주소·전화번호는 메모리 내 표시/검색에만 사용하고 영구 egui SQLite에 저장하지 않는다.
- 직원을 통한 수동 선택은 egui 전용 접수의 `clientId`, `clientSelection=MANUAL`만 변경하고 기존 Rust 원문 인식을 다시 실행한다. 이미 선택된 거래처를 다시 누르면 자동 매칭 근거를 변경하지 않는다.
- **2단계 미완료:** 실제 Tauri 주문의 거래처 변경은 Rust `order_edit_rules/change_order_client`의 주문 상태·가격·운임 조정과 운영 DB revision 비교 저장을 함께 연결해야 한다. 데이터 전체 권한 없이 `clientId`만 운영 주문에 덮어쓰지 않는다.
- **다음 이후 단계:** 원문 연결 하이라이트 → 수취인 수동 분류. 카카오톡 연결 문제는 별도 GitHub [#42](https://github.com/ThunderStrikerKR/TSBH/issues/42)에서 추적하며 이번 단계에서 수정하지 않는다.
- 코드 반영만 완료했다. Windows 실제 컴파일/화면 검증 및 대규모 회귀 테스트는 수행하지 않았다.

## 거래처 수동 변경 2단계: 기존 Rust 단가·운임 계산 연결 (2026-11-20)

- `native_order_change.rs`: UI의 고객 ID 덮어쓰기를 차단하고, 기존 Rust의 `new_reception → analyze_order(실제 선택 거래처) → change_order_client → merge_reception_analysis → reprice_order → calculate_price` 순서로 업무 판정을 실행한다. Rust가 가격/운임/상태 제한을 판정하며, 실패하면 기존 거래처를 유지한다.
- `business_state.rs`: `BANDO_EGUI_BUSINESS_DB` 경로로 사용자가 명시한 Tauri v2 SQLite를 **한 번의 읽기 전용 트랜잭션**에서 관계형 상품·옵션·거래처·주문·수취인·품목 및 설정/업무 상태로 복원한다. 운영 DB에 쓰기·스키마 변경·마이그레이션을 수행하지 않는다.
- 접수 인식도 운영 DB를 명시한 경우 같은 실제 상품/별칭 마스터 기준으로 수행한다. 단순 이름 인덱스 또는 예전 내장 상품 시드에 근거한 실거래처별 가격 계산은 허용하지 않는다.
- 성공 결과에서 전화번호·주소·계좌·고객 전체 스냅샷·운영 주문내역을 제거하고, 원문/거래처/마스터 revision에 연결된 `pricingPreview`(품목 단가·운임·부가세·총액)만 격리 작업본에 보존한다. `총 주문` 기존 표시 영역은 Rust 계산값이 완성된 경우만 참고액으로 표시하고 **운영 주문 저장 전** 상태를 명시한다.
- 다른 발주서 선택 또는 원문 수정으로 진행 중 계산이 무효화되면 결과를 적용하지 않는다. 원문 수정 시 미확정 견적도 무효화한다.
- **아직 운영 저장은 미완료:** Tauri `write_snapshot/state_save`와 workflow 정합성 검증을 동일 트랜잭션으로 재사용하지 않는 직접 SQL 수정은 금지한다. `core_orders`와 운영 주문 상태를 실제로 변경하지 않았으며, 현재 저장 대상은 `egui-preview.sqlite3`다. 운영 저장 연결은 별도 게이트웨이 과제로 남는다.
- 카카오톡 연결 Issue [#42](https://github.com/ThunderStrikerKR/TSBH/issues/42)는 이번 작업에서 변경하지 않았다. 원문 하이라이트와 수취인 수동 분류도 아직 이전하지 않았다.
- 코드 반영 후 Windows Cargo 컴파일/화면 동작 검증은 아직 수행하지 않았다. 전체 회귀 테스트도 실행하지 않았다.

## 운영 미확정 접수 저장 브리지 — 3단계 (2026-11-20)

**정식 주문 확인 완료가 아니다.** 기존 Tauri의 `reception_working_orders`에 미확정 작업본만 저장한다. `core_orders`, `app_state`, 입금·출고 원장은 변경하지 않는다.

- egui `확인할 내용`의 **운영 작업본 저장** 버튼을 직원이 클릭해야 실행된다. 평소 자동저장은 egui 전용 SQLite만 갱신한다.
- 최신 Tauri 실행 파일을 단발성 `--bando-egui-reception-commit` CLI로 시작하고, 기존 Rust 인식 → 거래처 변경 → 원문 분석 병합 → 재가격·운임 계산을 SQLite `BEGIN IMMEDIATE` 트랜잭션 안에서 재실행한다. 입력 견적 금액을 그대로 믿지 않는다.
- 기존 운영 주문과 중복 ID, 확정 상태, SQLite 관계형 버전 2, 업무 master revision, 작업본 CAS 버전, 작업본 무결성 해시를 검사하고 실패하면 롤백한다.
- 이미 겹쳐 실행 중인 React/Tauri의 전체 발주서 목록 자동저장도 egui에서 추가하거나 변경한 작업본을 오래된 데이터로 삭제/덮어쓰지 못하게 보호했다.
- 성공하면 egui SQLite에 `workingVersion`, `workingSynced`를 기록한다. 이후 원문·거래처·유형을 바꾸면 미반영으로 전환되며 다시 Rust 가격 확인과 명시적 저장이 필요하다.
- **기본적으로 운영 저장이 꺼져 있다.** 실제 운영 DB와 새로 빌드한 Tauri 실행 파일 경로, 허용 플래그를 모두 설정한 경우에만 버튼이 노출된다. 아래 경로는 예시다.

```powershell
$env:BANDO_EGUI_BUSINESS_DB = "C:\실제경로\bando-hub-v001.sqlite"
$env:BANDO_EGUI_TAURI_HELPER = "C:\실제경로\새로빌드한-Tauri.exe"
$env:BANDO_EGUI_ENABLE_WORKING_COMMIT = "1"
```

- 기존 구버전 Tauri EXE는 이 CLI를 지원하지 않는다. 정식 운영 사용 전 Windows 빌드, 격리된 DB 사본에서 저장/재실행 확인 및 백업이 필요하다. **현재 실제 Windows 빌드/GUI 테스트는 하지 않았다.**
- `주문 확인 완료`의 정식 확정, 원문 연결 하이라이트, 수취인 수동 분류는 후속 이전 대상이며 카카오톡 연결 문제는 [#42](https://github.com/ThunderStrikerKR/TSBH/issues/42)에서 별도 추적한다.

## 원문 연결 하이라이트 1단계 (2026-11-20)

- 원본 React `LinkedText`/`sourceDocumentSpans`의 핵심 원칙을 egui에 이전했다: Rust 분석 결과 `recipient.sources` 및 `item.sources`가 선언한 **정확한 원문 위치만** 연결하고, 같은 이름·모델이 반복되어도 단순 문자열 검색으로 소속을 재추정하지 않는다.
- Rust 인식 근거는 JavaScript 호환 UTF-16 위치이므로 `source_highlight.rs`에서 문자·이모지 경계를 검증한 뒤 UTF-8 바이트 범위와 egui 문자 커서로 변환한다. 경계가 맞지 않거나 원문 문자열과 다르면 그 링크는 표시하지 않는다. 변환은 분석 작업 스레드에서 한 번 수행한다.
- 기존 발주원문 입력창은 그대로 수정 가능하며, egui `TextEdit::layouter`로 기존 원문 안에 시각적 배경만 칠한다. 선택된 수취인과 같은 소속 원문은 약한 보조색, 세부 호버 항목은 파란색으로 구분한다.
- 수취인 이름·주소·휴대전화·전화·요청 메시지 또는 상품명·수량에 커서를 올리면 200ms 후 정확히 대응하는 원문이 강조된다. 포인터를 벗어난 뒤에는 250ms 후 하이라이트가 풀린다.
- 세부 필드에 대응한 원문이 현재 스크롤 범위 밖에 있을 때는 `Galley::pos_from_cursor`로 해당 문자 위치를 구해 원문 내부 스크롤만 이동시킨다. 원문을 클릭하면 해당 수취인 탭으로 이동하지만, 근거의 수취인·상품 소유권은 변경하지 않는다.
- `수취인별 주문 정보` 필드와 품목의 현재 활성 링크에는 추가 레이아웃 공간 없이 파란색 외곽선만 그린다.
- 원문이 바뀌면 비동기 인식 결과와 호버 위치를 같이 무효화한다. 원문 화면의 고정 섹션 비율과 제목·버튼·업무 상태는 변경하지 않는다.
- 아직 구현하지 않은 것: 수취인별 항목의 직원 수동 분류, 완성된 시각적 상품 표현식 확장, Windows 실화면 검증. 단위 테스트에는 UTF-16 이모지 경계와 반복 이름의 수취인 소속 분리를 추가했다.
- 카카오톡 연결 문제는 독립 Issue #42에서 추적하며 이번 단계에 수정하지 않았다.

## 수취인 수동 분류 이전 — 1차: Rust 원문 블록과 배송 구성표 연결 (2026-11-20)

- 기존 React `ManualClassification.tsx`의 기본 원문·배송 정보 2열 흐름을 egui `manual_workspace.rs`에 연결했다. 발주 원문 분석 완료 후 `확인할 내용`에서 **수동 분류**를 열 수 있다.
- `initial_manual`은 Rust 인식에서 온 수취인·상품 근거를 기준으로 원문 블록/배정 및 초기 배송 구성표를 생성한다. egui는 원문 블록의 정확한 UTF-16 경계만 버튼으로 표시하고 **미인식 원문도 원래 위치에 표시**한다.
- 직원이 배송 건·필드(이름/주소/휴대전화/전화/배송 요청) 또는 상품·수량 칸을 선택한 뒤 원문 블록을 누르면, 기존 Rust `assign_manual_block`/`release_manual_block`가 배정/해제를 판단한다. 배정된 블록을 다시 클릭하면 해당 입력값도 Rust를 통해 해제한다.
- `배송 추가`, `상품 추가`, 직접 입력의 `set_manual_recipient_field`, `set_manual_product`, 수량의 `set_manual_quantity_draft → confirm_manual_quantity`도 Rust 규칙을 호출한다. 직접 입력은 **입력 반영**을 누르기 전에는 모델을 변경하지 않으며, 다른 셀로 이동해 입력을 조용히 잃지 않도록 막는다.
- **초안에 적용**은 Rust의 `manual_quantity_status` 및 `apply_manual`을 순서대로 실행한다. 처리 도중 원문·접수 유형·거래처·발주서 ID가 바뀌었다면 결과를 버린다. 결과의 `recipients`는 현재 egui 분석 상세 및 원문 하이라이트에 적용된다.
- `manualModel`(`model`, `assignmentOrder`, `sourceRaw`, `orderType`, `clientId`)은 egui SQLite 초안에 보존한다. 화면 재진입 시 Rust로 재적용하며, 별도의 명시적 저장을 누른 경우에만 **검증된 수동 분류 결과**가 Tauri `reception_working_orders`에도 저장된다. 정식 주문 원장은 변경하지 않는다.
- **이전 단계의 제한을 4차에서 해제:** `운영 작업본 저장`은 Rust가 원문 블록·배정·상품 ID를 최신 마스터와 비교하고 분류 변경을 원본 Rust reducer로 재현·재가격한 뒤, SQLite CAS 트랜잭션으로 기록한다. 자동 재인식 결과로 수동 분류를 덮어쓰지 않는다.
- 배송 건수 감소·개별 상품 삭제·전체 초기화·상품 검색창은 후속 2차 패치에서 이식했다. 남은 확인 범위는 키보드 표 이동/되돌리기, 수동 분류 저장을 포함한 최신 Windows 컴파일/DB 실제 작업 흐름, 정식 주문 확인 완료와 실제 UI 화면 검수다.
- 이 작업은 기존 Rust 비즈니스 규칙을 재사용하고 별도 TypeScript 분류 로직이나 새 분류 알고리즘을 만들지 않았다. 대규모 회귀 테스트는 실행하지 않았다. 카카오톡 연결은 Issue #42에서 별도 추적한다.

## 수취인 수동 분류 2차: 상품 검색·행 삭제 및 UI 계약 보정 (2026-11-20)

- 기존 React 수동 분류의 상품 검색과 배송 건수 감소를 egui 화면에 연결했다. 상품 검색은 별도 검색 알고리즘을 만들지 않고 **원본 Rust `catalog_clients/queries.rs::search_products_with_urls`를 직접 재사용**한다. 상품/브랜드/분류/거래처 별칭 필터와 데모 상품 제외 규칙을 유지하고 결과를 최대 100개 보여 준다.
- 검색 결과 선택은 기존 Rust `set_manual_product`로 전달한다. 검색 중 배송 건이나 상품 ID가 변경되면 이전 검색 결과를 적용하지 않는다. 상품명/수량 결정과 상품별 가격은 Rust가 처리한다.
- 상품 행의 `상품 제거`는 원본 Rust `remove_manual_item`, 배송 건수 `−/+`는 `resize_manual_rows`를 호출한다. 마지막 배송 건에 수취인 정보·상품·원문 배정이 있으면 **React 원본과 동일하게 내용 손실 확인창**을 거친다. 비어 있는 배송 건은 별도 확인 없이 줄인다.
- 공통 UI 준수 검토에서 발견한 임의 크기와 50:50 원문/배송표 열을 수정했다. 수동 분류는 실제 React `.manual-workspace .manual-columns`의 **34:66 비율**을 따르고, 창 크기/최소 폭/입력 폭/검색 결과 높이는 `theme.rs` 공통 토큰으로 집중했다. 검색·직접입력은 `components::flexible_text_field`를 사용하고 모든 작업 버튼은 `theme::action`을 사용한다.
- 기존 접수 화면의 4열 비율과 스플리터는 변경하지 않았다. 아직 정밀 Windows 화면 비교, 표 전체 셀의 React 원본 UI 복원 및 실행 컴파일 검증을 마치지 않았으므로 **UI 계약 최종 준수 판정은 보류**한다.
- 대규모 회귀 테스트는 실행하지 않았다. 카카오톡 연결 문제는 Issue #42로 유지한다.

## 수취인 수동 분류 공통 UI 전체 정리 (2026-11-20)

이번 정리는 React `src/orders/ManualClassification.tsx`와 `src/styles/reception-manual.css`의 현재 승인된 구성 및 `docs/egui-ui-design-contract.md`, `docs/modal-design-system.md`를 기준으로 진행했다. 기능을 만들고 난 뒤 임시 CSS에 해당하는 화면별 수치를 덧씌우지 않도록 **공통 소유권을 먼저 분리했다.**

| 공통 UI 소유권 | 구현 |
| --- | --- |
| 글씨 위계/모달 제목 | `typography.rs::modal_title` (18pt 공통 역할) |
| 모달/확인창/버튼 | `components.rs::modal_window`, `decision_window`, `modal_actions` 및 기존 `theme::action` |
| 모달 프레임/원문·표 패널 | `theme.rs::modal_frame`, `modal_nested_frame` |
| 표 헤더/편집 대상 셀 | `components.rs::manual_table_heading`, `manual_table_cell`: 고정 열폭, 36pt 헤더·42pt 행, 선택 테두리로만 상태 강조·본문 줄바꿈에 따른 행 높이 변화 방지 |
| 입력창 | `components.rs::flexible_text_field` 공통 높이/폰트/패딩 |

- **운영 DB 쓰기(명시적 허용):** `BANDO_EGUI_BUSINESS_DB` (DB 경로), `BANDO_EGUI_TAURI_HELPER` (현재 버전의 Tauri EXE), `BANDO_EGUI_ENABLE_SETTINGS_WRITE=1`의 세 조건이 필요하다. Tauri의 기존 `apply_settings_patch`는 React IPC 명령과 egui 원샷 CLI가 공유하므로 같은 설정별 기준값 비교·계좌 참조 검사·revision 체크·저장 경로를 실행한다. 임의 SQL 설정 패치를 하지 않는다. 외부 HTTP 게이트웨이가 지원하지 않으면 실패로 표시하고 로컬로 폴백하지 않는다.
- **데이터 관리:** 기존 `receipt_archive_from_conn` 및 `backup_manager::{manual_backup,list_backups,restore_backup}`를 원샷 Tauri 데이터 CLI로 호출한다. 읽기는 운영 DB RO, 쓰기는 명시적 허용 및 복구 확인창 필수. 복구 시 기존 Rust가 생성하는 복원 전 안전 백업·검증을 그대로 사용하고 egui 캐시를 무효화한다.
- **파일 관리:** Windows 시스템 폴더 선택, 설정된 폴더 열기, Excel 보관함 선택 시 원본의 공장 발송·매장 발송·공장 회신·상품 관리·거래처 관리 5개 하위 폴더 생성을 반영했다. **주의: 독립 egui 프로세스에서 실행되는 자동 수신 감시/파일 가져오기(OCR 및 공장 회신 이벤트)는 이 단계에 아직 이전하지 않았다.** 경로 설정 저장과 자동 파일 감시 실행을 동일한 완료 상태로 보고하지 않는다.
- **잔여 이전:** `HelpTooltip` 원본의 마우스 전용 500ms 진입, 클릭 고정 및 단계별 설명 UI, 파일 자동 수신 watcher/처리, 설정 행 비율·필드 크기의 세부 CSS 동등성. 원본 코드가 포함된 기능과 기능별 실제 실행 동등성 검증은 별도로 남는다. GUI 검증은 사용자 최신 지시로 실시하지 않는다. 기존 React/Tauri 경로는 삭제하지 않았고 전체 회귀 테스트는 실행하지 않는다.
